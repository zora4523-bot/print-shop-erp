## 1. 服务器基础环境

SSH 登录服务器，装 Node 24 / pnpm / PM2 / Nginx / Git。

```bash
# ── Node.js 24 (项目要求 >=24) ──
curl -fsSL https://deb.nodesource.com/setup_24.x | sudo -E bash -
sudo apt-get install -y nodejs git nginx

# ── pnpm 10.33.1（锁定版本，与 package.json packageManager 一致）──
sudo npm install -g pnpm@10.33.1

# ── PM2（进程守护）──
sudo npm install -g pm2

# 验证版本
node -v      # 应 >= v24
pnpm -v      # 应 10.33.1
```

## 2. 数据库准备（Pigsty PostgreSQL）

前提：已有一个独立的 Pigsty PostgreSQL 16 实例。做两件事：

**(1) 建库 + 建应用账号**（在 PG 里执行）：

```sql
CREATE DATABASE print_shop_erp;
CREATE USER erp_app WITH PASSWORD '换成强密码';
GRANT ALL PRIVILEGES ON DATABASE print_shop_erp TO erp_app;
-- Prisma 迁移需要建表/扩展权限，MVP 阶段给够即可
```

**(2) 安装扩展**（重要）：迁移文件里用到 `pg_trgm`、`citext`（Postgres 标准 contrib，任何 PG 都有，`migrate deploy` 会自动 `CREATE EXTENSION`）。但 `pg_pinyin`（拼音搜索）、`pg_bigm`、`pg_ivm`（库存看板增量）、`pg_partman` 等**需要 Pigsty 侧预加载**，迁移里对它们做了「装不上就降级」的条件处理——**不装也能上线**，只是拼音搜索等增强功能退化。

> 生产扩展安装照 **`docs/pigsty-production-activation-runbook.md`** 执行。可以先不装，上线后再补。装完在 `/owner/pigsty` 页看红绿灯就绪状态。

## 4. 环境变量 `.env`

在项目根建 `.env`（Next.js 启动时自动读取）。**这是最容易出错的一步**，逐条对照：

```bash
cp .env.example .env
nano .env   # 或 vim
```

| 变量 | 填什么 | 漏填/填错的后果 |
|---|---|---|
| `DATABASE_URL` | `postgresql://erp_app:密码@PG主机:5432/print_shop_erp` | 应用起不来 |
| `AUTH_SECRET` | **生成新的强随机值**（勿沿用 dev） | 会话签名不安全 |
| `AUTH_TRUST_HOST` | `"true"`（Nginx 反代必填） | 登录跳转失败 |
| `CRON_SECRET` | 生成一个随机串 | 10 个定时任务全 503 |
| `BACKGROUND_JOBS_MODE` | `"durable"` | 留在 inline 会失去任务重试与资源隔离 |
| `APP_PUBLIC_URL` | `https://你的域名`（**无尾斜线**） | **师傅扫码/外协短链变死链** |
| `NOTIFICATION_MOCK_MODE` | 生产显式填 `"false"` | 填 `"true"` → 推送静默 mock；留空虽实际真发，但生产 smoke 会拒绝含糊配置 |
| `CDR_BUNDLE_MOCK_MODE` | 留空 | 填 `"true"` → CDR 下载返回占位链接 |
| `SEED_ADMIN_USERNAME` | 管理员账号，如 `admin` | 见 seed.ts 顶注释 |
| `SEED_ADMIN_PASSWORD` | 管理员初始密码（强密码） | 留空则 seed 打印一次随机密码 |
| `OSS_ACCESS_KEY_ID` 等 5 个 | 子账号 `webhongbao` 的凭证 | 留空 → 设计图上传按钮禁用 |
| `SENTRY_DSN` | Sentry 项目 DSN（选填但强烈建议） | 留空 → 无错误监控 |
| `APP_VERSION` | 当前 Git SHA / 发布号（`deploy/update.sh` 发布时自动设为本次 commit） | 错误、worker 和部署无法对齐 |
| `PDF_ARTIFACT_DIR` | `/var/tmp/print-shop-erp/pdf` | Web 与 HEAVY worker 无共享产物目录时 PDF 失败 |
| `ORDER_EXPORT_ARTIFACT_DIR` | `/var/tmp/print-shop-erp/order-exports` | Web 与 HEAVY worker 必须共享；目录需保持 `0700`，文件为 `0600`，多机前改为共享对象存储 |
| `AGENT_MONTHLY_BILL_EXPORT_ARTIFACT_DIR` | `/var/tmp/print-shop-erp/agent-monthly-bill-exports` | 月账单 XLSX 的 Web/HEAVY 共享私有目录；不得与工单导出目录复用 |

Pigsty 跨主机连接建议在 `DATABASE_URL` 使用 `sslmode=verify-full`，并把
Pigsty CA 安装到 `/usr/local/share/ca-certificates/pigsty-print-shop.crt`。PM2 配置会在
Node 启动时通过 `NODE_EXTRA_CA_CERTS` 加载它；仅把该变量写进 Next.js
`.env` 太晚，不会影响 Node 的 TLS 根证书集。

Debian 主机使用系统 Chromium (`/usr/bin/chromium`)。PM2 通过
`PUPPETEER_EXECUTABLE_PATH` 显式传给 Puppeteer，避免 pnpm 禁用依赖构建脚本时
跳过浏览器下载而导致 PDF 仅在生产失败。

生成随机密钥：

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
```

**配完立刻自检**（专抓 mock-mode 误设、`APP_PUBLIC_URL` 空、OSS 半配等陷阱）：

```bash
NODE_ENV=production pnpm check:env
# 有 ❌ 错误 → 退出码非 0，必须修完再往下
```

> **切勿**把 dev 机的 `AUTH_SECRET` 抄到生产。`.env` 权限设严：`chmod 600 .env`。

## 6. 阿里云 OSS —— 配 CORS（关键，代码改不了）

设计图和 CDR 走**浏览器直传 OSS**（文件不经过服务器）。浏览器跨域 PUT 前会发 CORS 预检，**bucket 不配 CORS 规则就会被浏览器拦死**，签名正常也传不上去。

在**阿里云 OSS 控制台 → bucket `hongbaowebdb` → 数据安全 → 跨域设置 → 创建规则**：

| 字段 | 值 |
|---|---|
| 来源 Origin | `https://你的域名`（split-origin 部署则内网 staff 域也加一行） |
| 允许 Methods | `PUT`, `GET`, `HEAD` |
| 允许 Headers | `*` |
| 暴露 Headers | `ETag` |
| 缓存时间 | `600` |

本地调试使用的 `http://localhost:3000` 与 `http://127.0.0.1:3000` 是两个不同来源；需要直传的地址必须分别加入来源列表。不要以修改页面请求为 `no-cors` 或关闭浏览器安全检查代替配置。

配置后，分别对实际来源执行无凭证、无文件写入的预检：

```sh
curl -i -X OPTIONS 'https://hongbaowebdb.oss-cn-guangzhou.aliyuncs.com/__cors_preflight__' \
  -H 'Origin: http://127.0.0.1:3000' \
  -H 'Access-Control-Request-Method: PUT' \
  -H 'Access-Control-Request-Headers: content-type'
```

应返回 200、对应的 `Access-Control-Allow-Origin`，以及允许 PUT 和 Content-Type 的响应头；再将 Origin 替换为实际域名或 localhost 检查。预检通过只证明跨域设置匹配，不证明 STS 写入、文件读取或登记已经通过。

RAM 子账号与 `erp-oss-upload` 角色的策略需分别核对：签发上传凭证需要 AssumeRole，上传临时会话仅允许目标对象写入；当前应用登记文件使用服务端账号 HEAD 检查，需要对应设计文件的读取权限。当前业务“删除设计文件”只删除数据库关联并记录日志，不调用 OSS 物理删除，不需要为此增加 DeleteObject 权限。对象物理清理是独立运维任务，不作为上传验收前置。只给目标 bucket 的业务对象范围，不因此授予 bucket 管理权限。缺少 GetBucketCors 权限的应用账号不能代替运维账号查看配置。

修改前保留已有规则。OSS 的 PutBucketCors 会替换整组规则，添加来源时应保留已有规则和来源，参见 [阿里云官方说明](https://www.alibabacloud.com/help/en/oss/developer-reference/putbucketcors)。

## 8. 用 PM2 启动应用

```bash
# 日志目录
sudo mkdir -p /var/log/print-shop-erp && sudo chown $USER /var/log/print-shop-erp
sudo mkdir -p /var/tmp/print-shop-erp/pdf && sudo chown $USER /var/tmp/print-shop-erp/pdf

# 复制并按需改配置（cwd / 端口 / 日志路径）
cp deploy/ecosystem.config.cjs .    # 已在仓库，改 cwd 为 /var/www/print-shop-erp

pm2 start deploy/ecosystem.config.cjs
pm2 save            # 保存进程列表
pm2 startup         # 按提示执行输出的命令，实现开机自启

# 日志轮转（防日志无限增长）
pm2 install pm2-logrotate

# 查看状态 / 日志
pm2 status
pm2 logs print-shop-erp
```

配置会启动 3 个进程：`print-shop-erp` Web、LIGHT worker
（通知/定时任务）、HEAVY worker（CDR/PDF，并发固定为 1）。
运行 `pm2 status` 必须三个都是 online；Web 只监听 `127.0.0.1:3000`，由
Nginx 在 443 对外提供。Next 16 默认会监听 `0.0.0.0`，所以 ecosystem 里的
`-H 127.0.0.1` 不能删，否则客户端可直连 3000 绕过登录/PDF限流。

物理内存低于 3 GiB 时，ecosystem 配置会自动启用低内存档（Web 512 MiB、
LIGHT 384 MiB、HEAVY 640 MiB）。这只能作为带 swap 的临时部署方案；
Puppeteer 高峰仍可能换页，生产服务器应尽快升级至至少 4 GiB。

## 9. Nginx 反向代理 + HTTPS

```bash
# 复制示例配置，改域名和证书路径
sudo cp deploy/nginx.conf.example /etc/nginx/conf.d/print-shop-erp.conf
sudo nano /etc/nginx/conf.d/print-shop-erp.conf   # 改 server_name / ssl 证书路径

sudo nginx -t                # 测试配置
sudo systemctl reload nginx
```

配置里**四个关键点**（示例文件已含，务必保留）：
1. `X-Forwarded-Proto $scheme` —— 否则二维码/短链退化成 localhost 死链、登录 cookie Secure 失效
2. `X-Forwarded-Host $host` —— 二维码/短链域名跟随它
3. `location = /login` 上的 `limit_req zone=erp_auth` —— 这才是防登录爆破的那一处。
   本项目登录走 Server Action，浏览器 POST 的是 `/login` 本身，**不会**访问
   `/api/auth/callback/credentials`；后者的块只是纵深防御，共用同一个令牌桶。
   配套的 `map $request_method $erp_auth_limit_key` 不能删 —— 删掉会连 `GET /login`
   一起限流，未登录用户点几下就会被登录页 429 挡在门外。
4. PDF 路由的 `limit_req zone=erp_heavy` —— 防按需 Chromium 被并发压垮

改完务必 `sudo nginx -t`：`map` 与 `limit_req_zone` 都必须在 `http {}` 层，
重复 include 同名 zone 会直接报错。

> **将来在 ECS 前加阿里云 SLB / CDN 时必须先做 real_ip**：`$binary_remote_addr` 会变成
> SLB 的 IP，全站共用一个令牌桶、登录会被自己限死。届时先用 `set_real_ip_from` +
> `real_ip_header X-Forwarded-For` 还原真实客户端 IP 再上线。当前 nginx 直接做边缘，不受影响。

访问 `https://你的域名` 应看到登录页。

如果证书由 Certbot webroot 签发，保留 HTTP server 中的
`/.well-known/acme-challenge/` 例外；示例配置已包含。部署后执行
`sudo certbot renew --dry-run` 验证自动续期链路。

## 10. 定时任务（10 个 cron）

系统有 10 个需要每天/每月自动跑的任务。用系统 crontab 调用仓库内的
`deploy/run-cron.sh`。它只允许已知端点、验证 HTTP 202，并把结果写到
syslog；密钥从 root-only 文件读取，不明文写进 crontab，**也不进 curl 的命令行参数**
（改用 `--header @-` 从 stdin 喂 Authorization 头——否则同机任何用户一句
`ps -efww | grep Bearer` 就能读走完整 `CRON_SECRET`）。

> **环境要求：`curl >= 7.55`**（`--header @-` 是 2017 年的 curl 7.55.0 引入的）。
> Ubuntu 22.04（7.81）/ Debian 12（7.88）/ Alibaba Cloud Linux 3（7.76）都满足。
> 万一系统 curl 更老，它会把 `@-` 当成字面头名发出去 → 服务端 401 → 脚本走 HTTP 401
> 分支 `exit 1` 并写 syslog，是**响的失败**而不是静默失败，用 `curl --version` 一查便知。

```bash
sudo install -m 755 deploy/run-cron.sh /usr/local/sbin/print-shop-erp-cron
sudo install -m 600 deploy/crontab.example /root/print-shop-erp.crontab
sudo nano /root/print-shop-erp.crontab  # 改 APP_PUBLIC_URL 和 CRON_SECRET_FILE
sudo crontab /root/print-shop-erp.crontab
```

默认模板如下（把 `erp.example.com` 换成域名）：


### 12.1 OSS 异地仓库实施（2026-09-17）

配置模板与任务位于 `deploy/backup/`。2026-09-17 已接入生产 pgBackRest 2.58.0、stanza `pg-meta`：杭州数据库主机保留 repo1 `/pg/backup`，新增北京 OSS repo2 `print-shop-erp-pgbackup-20260917/print-shop-erp/production/`。Bucket 为标准存储、同城冗余、私有、阻止公共访问，SSE AES256；repo2 另有 pgBackRest AES-256-CBC 加密，TLS 验证开启。两仓库均使用 30 天 time retention，系统定时器分别在上海时间 01:00、01:30 运行；已移除旧的单仓库 cron。`archive-async=y`、`spool-path=/pg/spool` 保持，移除丢 WAL 队列上限，Patroni 动态 `archive_timeout=60s`。双仓库检查、实际 full、OSS-only 隔离恢复和业务数据校验通过，详见[实施记录](audits/2026-09-17-oss-backup.md#生产接入与真实恢复2026-09-17)。

这不代表完整灾备基线全部达标：独立恢复在同一主机的独立集群进行，尚未演练整机失效；指定时间点恢复、故障注入及外部告警投递尚待完成。30 天历史需要实际积累。

**资源与凭证**

1. 确认数据库 ECS 实际地域，建立不同地域的专用私有 OSS Bucket，标准存储，阻止公共访问，不接业务 CDN/上传 CORS。核对该账号 OSS S3 认证及 endpoint 可用性；不要照搬业务 OSS endpoint。模板 `pgbackrest-oss.conf.example` 的占位符必须全部替换。
2. 创建独立备份 RAM 身份，按 `oss-ram-policy.json.example` 限定 Bucket 和 `print-shop-erp/production/` 前缀。创建 Bucket/RAM 属于管理身份；备份运行身份不需要管理账号或其他 Bucket 权限。验证列举、分片上传、读回、清理权限以及越界拒绝；本次已验证前缀内读写、列举和测试对象清理，前缀外读取返回 403；更换身份或策略后须重验。
3. 凭证和随机加密口令仅写数据库主机 postgres 可读、权限 0600 的配置；独立托管恢复口令，不仅放在同一台数据库机。禁止贴入聊天、Git、应用 `.env`、CLI 参数或日志。repo2 使用 AES-256-CBC 与 HTTPS 校验；现有 repo1 不原地切换加密格式。
4. 活跃仓库不设置 OSS 按对象年龄删除或转冷归档的生命周期，也不直接开启与 pgBackRest 清理冲突的不可变保留。由 pgBackRest 管理完整备份与依赖 WAL 的到期；30 天 time retention 不等同于刚启用就已有 30 天历史。

**配置与首次备份**

1. 保存现有 pgBackRest/Pigsty 配置和 postgres crontab，核对磁盘容量。将模板合并到现有 `/etc/pgbackrest/pgbackrest.conf`，保留 stanza、pg1/socket、日志、repo1 路径。同步 Pigsty 配置源，防止下次自动部署覆盖。先在隔离环境验证 repo2 读写和恢复密钥，再在维护窗口启用。
2. 保留异步归档与持久 spool；移除现有 `archive-push-queue-max=4GiB`，不要将其写成 0（0 也可能触发丢弃）。该上限达到后会丢 WAL；去掉上限后必须监控 PGDATA/spool 磁盘与归档积压，不能以丢数据换健康状态。通过现有 Patroni/Pigsty 配置管理将 `archive_timeout` 调整为 60 秒并 reload，给 5 分钟 RPO 留传输和报警余量，核对实际 SHOW 值。
3. 启用 repo2 会使归档向两个仓库发送；先验证凭证与网络，再以 postgres 执行：

   ```bash
   pgbackrest --stanza=pg-meta stanza-create
   pgbackrest --stanza=pg-meta check
   pgbackrest --stanza=pg-meta --repo=2 --type=full backup
   pgbackrest --stanza=pg-meta --repo=1 --type=full backup
   pgbackrest --stanza=pg-meta info --output=json
   ```

4. pgBackRest 2.58 的 `stanza-create` 作用于全部配置仓库，不接受 `--repo`；已在目标主机核对 help。两个仓库分别执行 backup；默认 backup 只操作高优先级仓库，不会自动备份两个。首次 full 与归档检查失败时保持原本备份任务，排查网络/权限，不能删除 stanza 或忽略归档失败来放行。

**定时任务与监控**

- 将 `run-full-backup.sh` 安装为 root 所有、0755 的 `/usr/local/libexec/erp-backup/run-full-backup.sh`，将 service/timer 模板安装到 `/etc/systemd/system/`。核对 `PGBACKREST_STANZA` 与 psql PATH；脚本要求 postgres、主库，失败返回非零。
- `systemd-analyze verify` 通过后 daemon-reload，先分别手动启动两个 service 并检查成功回执，然后启用 `erp-pgbackrest-full@1.timer` 与 `erp-pgbackrest-full@2.timer`。首次 full 通过后才精确移除 postgres crontab 的旧 `/pg/bin/pg-backup full` 行，其余任务保留。两个定时任务上海时间分别 01:00、01:30，失败间隔 15 分钟重试，4 小时内最多启动 3 次；故障必须报警。

   ```bash
   PGBACKREST_STANZA=pg-meta BACKUP_REQUIRED_REPOS=2 pnpm check:backup --info-file /absolute/path/to/info.json
   ```

  离线输出会明确标记快照，不能当成持续监控。回归命令 `pnpm test:backup` 已接入 CI。

**OSS 独立恢复验收与回退**

在另一台隔离 PostgreSQL 16 环境，从 repo2 单独恢复：配置只包含 repo2 和恢复凭证，不挂载本地 repo1，不用生产 PGDATA；确认恢复目录为空、生产网络与业务推送隔离。执行 pgBackRest restore 时显式指定 repo2、独立 pg1-path，按需要指定 `--type=time`、目标时间与 timeline；这些参数必须在演练记录中给出实际值。启动独立端口前检查恢复配置不会启动生产 Patroni、cron 或应用 worker。核对所有数据库、业务行数、最新工单和工资/账单金额、角色与扩展，验证测试标记前后的时间点恢复，记录 label、WAL、耗时和密钥取回过程。物理备份包含整个 PostgreSQL 集群，也可能含演练库，不只是 ERP 单库。

### 数据库进程预算（2026-09-21 整改）

应用连接池显式设置 web=25、worker=5，借用连接超时 10s；Prisma 默认事务 maxWait=15s、timeout=20s，已有专项事务显式预算优先。`DATABASE_POOL_MAX`、`DATABASE_POOL_CONNECTION_TIMEOUT_MS` 可按进程覆盖；优先级为显式函数参数 → 环境变量 → DATABASE_URL 的 max/connectionTimeoutMillis → 默认值，统一强制 UTC。worker 入口在加载 Prisma 前设置进程角色，启动检查池容量至少为该队列并发数的 2 倍；默认 LIGHT=2 与 worker=5 相容，调到 8 必须同时设置池容量至少 16。心跳继续使用事务外连接。
