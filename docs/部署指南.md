## 1. 服务器基础环境

SSH 登录服务器，装 Node 24 / pnpm / PM2 / Nginx / Git。

```bash

# ── pnpm 10.33.1（锁定版本，与 package.json packageManager 一致）──
sudo npm install -g pnpm@10.33.1

# ── PM2（进程守护）──
sudo npm install -g pm2

# 验证版本
node -v      # 应 >= v24
pnpm -v      # 应 10.33.1
```

## 2. 数据库准备（Pigsty PostgreSQL）

前提：已有一个独立的 Pigsty PostgreSQL 16 实例。做两件事：

**(1) 建库 + 建应用账号**（在 PG 里执行）：

```sql
CREATE DATABASE print_shop_erp;
CREATE USER erp_app WITH PASSWORD '换成强密码';
GRANT ALL PRIVILEGES ON DATABASE print_shop_erp TO erp_app;
-- Prisma 迁移需要建表/扩展权限，MVP 阶段给够即可
```

**(2) 安装扩展**（重要）：迁移文件里用到 `pg_trgm`、`citext`（Postgres 标准 contrib，任何 PG 都有，`migrate deploy` 会自动 `CREATE EXTENSION`）。但 `pg_pinyin`（拼音搜索）、`pg_bigm`、`pg_ivm`（库存看板增量）、`pg_partman` 等**需要 Pigsty 侧预加载**，迁移里对它们做了「装不上就降级」的条件处理——**不装也能上线**，只是拼音搜索等增强功能退化。

> 生产扩展安装照 **`docs/pigsty-production-activation-runbook.md`** 执行。可以先不装，上线后再补。装完在 `/owner/pigsty` 页看红绿灯就绪状态。

## 4. 环境变量 `.env`

在项目根建 `.env`（Next.js 启动时自动读取）。**这是最容易出错的一步**，逐条对照：

```bash
cp .env.example .env
nano .env   # 或 vim
```

| 变量 | 填什么 | 漏填/填错的后果 |
|---|---|---|
| `DATABASE_URL` | `postgresql://erp_app:密码@PG主机:5432/print_shop_erp` | 应用起不来 |
| `AUTH_SECRET` | **生成新的强随机值**（勿沿用 dev） | 会话签名不安全 |
| `AUTH_TRUST_HOST` | `"true"`（Nginx 反代必填） | 登录跳转失败 |
| `CRON_SECRET` | 生成一个随机串 | 10 个定时任务全 503 |
| `BACKGROUND_JOBS_MODE` | `"durable"` | 留在 inline 会失去任务重试与资源隔离 |
| `APP_PUBLIC_URL` | `https://你的域名`（**无尾斜线**） | **师傅扫码/外协短链变死链** |
| `NOTIFICATION_MOCK_MODE` | 生产显式填 `"false"` | 填 `"true"` → 推送静默 mock；留空虽实际真发，但生产 smoke 会拒绝含糊配置 |
| `CDR_BUNDLE_MOCK_MODE` | 留空 | 填 `"true"` → CDR 下载返回占位链接 |
| `SEED_ADMIN_USERNAME` | 管理员账号，如 `admin` | 见 seed.ts 顶注释 |
| `SEED_ADMIN_PASSWORD` | 管理员初始密码（强密码） | 留空则 seed 打印一次随机密码 |
| `OSS_ACCESS_KEY_ID` 等 5 个 | 子账号 `webhongbao` 的凭证 | 留空 → 设计图上传按钮禁用 |
| `SENTRY_DSN` | Sentry 项目 DSN（选填但强烈建议） | 留空 → 无错误监控 |
| `APP_VERSION` | 当前 Git SHA / 发布号 | 错误、worker 和部署无法对齐 |
| `PDF_ARTIFACT_DIR` | `/var/tmp/print-shop-erp/pdf` | Web 与 HEAVY worker 无共享产物目录时 PDF 失败 |
| `ORDER_EXPORT_ARTIFACT_DIR` | `/var/tmp/print-shop-erp/order-exports` | Web 与 HEAVY worker 必须共享；目录需保持 `0700`，文件为 `0600`，多机前改为共享对象存储 |
| `AGENT_MONTHLY_BILL_EXPORT_ARTIFACT_DIR` | `/var/tmp/print-shop-erp/agent-monthly-bill-exports` | 月账单 XLSX 的 Web/HEAVY 共享私有目录；不得与工单导出目录复用 |

Pigsty 跨主机连接建议在 `DATABASE_URL` 使用 `sslmode=verify-full`，并把
Pigsty CA 安装到 `/usr/local/share/ca-certificates/pigsty-print-shop.crt`。PM2 配置会在
Node 启动时通过 `NODE_EXTRA_CA_CERTS` 加载它；仅把该变量写进 Next.js
`.env` 太晚，不会影响 Node 的 TLS 根证书集。

Debian 主机使用系统 Chromium (`/usr/bin/chromium`)。PM2 通过
`PUPPETEER_EXECUTABLE_PATH` 显式传给 Puppeteer，避免 pnpm 禁用依赖构建脚本时
跳过浏览器下载而导致 PDF 仅在生产失败。

生成随机密钥：

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
```

**配完立刻自检**（专抓 mock-mode 误设、`APP_PUBLIC_URL` 空、OSS 半配等陷阱）：

```bash
NODE_ENV=production pnpm check:env
# 有 ❌ 错误 → 退出码非 0，必须修完再往下
```

> **切勿**把 dev 机的 `AUTH_SECRET` 抄到生产。`.env` 权限设严：`chmod 600 .env`。

## 6. 阿里云 OSS —— 配 CORS（关键，代码改不了）

设计图和 CDR 走**浏览器直传 OSS**（文件不经过服务器）。浏览器跨域 PUT 前会发 CORS 预检，**bucket 不配 CORS 规则就会被浏览器拦死**，签名正常也传不上去。

在**阿里云 OSS 控制台 → bucket `hongbaowebdb` → 数据安全 → 跨域设置 → 创建规则**：

| 字段 | 值 |
|---|---|
| 来源 Origin | `https://你的域名`（split-origin 部署则内网 staff 域也加一行） |
| 允许 Methods | `PUT`, `GET`, `HEAD` |
| 允许 Headers | `*` |
| 暴露 Headers | `ETag` |
| 缓存时间 | `600` |

> RAM 凭证（角色 `erp-oss-upload`、子账号 `webhongbao` 对象读写策略）之前已配好，这里只补 CORS 这一步。

## 7. Puppeteer Chrome + 中文字体（工单 PDF 打印需要）

生产固定使用 Debian 系统 Chromium，不依赖 pnpm 是否执行 Puppeteer postinstall：

```bash
sudo apt-get install -y chromium
test -x /usr/bin/chromium
```

`deploy/ecosystem.config.cjs` 默认把 `PUPPETEER_EXECUTABLE_PATH=/usr/bin/chromium`
注入 Web 和 HEAVY worker。Puppeteer-managed Chrome 只用于本地/CI；本地没有系统
Chromium 时才运行 `npx puppeteer browsers install chrome`。

**⚠️ 必须装中文字体，否则工单 PDF 全是豆腐块 □□□。**
打印视图的字体栈是 `"PingFang SC", "Microsoft YaHei", sans-serif`
（见 `lib/order/print-layout.tsx`）——苹方只在 macOS、
雅黑只在 Windows，**Debian 服务器两个都没有**，会掉到不含中文字形的
DejaVu Sans。装上 Noto CJK 后 fontconfig 会按字形回退兜住中文：

```bash
sudo apt-get install -y fonts-noto-cjk

fc-list :lang=zh | head     # 应能列出 Noto Sans CJK，空 = 没装上
```

装完后按 §13 先用同一可执行文件实际调用 `page.pdf()`，再真下载一次工单 PDF
肉眼确认中文和设计图正常。接口返回 200、浏览器能启动或缓存目录存在，都不能
单独证明 PDF 运行时正确。2026-08-02 生产已用 `/usr/bin/chromium` 生成
37,646 字节中文测试 PDF；真实 OSS 图片打印仍需作为人工验收保留。

## 8. 用 PM2 启动应用

```bash
# 日志目录
sudo mkdir -p /var/log/print-shop-erp && sudo chown $USER /var/log/print-shop-erp
sudo mkdir -p /var/tmp/print-shop-erp/pdf && sudo chown $USER /var/tmp/print-shop-erp/pdf

# 复制并按需改配置（cwd / 端口 / 日志路径）
cp deploy/ecosystem.config.cjs .    # 已在仓库，改 cwd 为 /var/www/print-shop-erp

pm2 start deploy/ecosystem.config.cjs
pm2 save            # 保存进程列表
pm2 startup         # 按提示执行输出的命令，实现开机自启

# 日志轮转（防日志无限增长）
pm2 install pm2-logrotate

# 查看状态 / 日志
pm2 status
pm2 logs print-shop-erp
```

配置会启动 3 个进程：`print-shop-erp` Web、LIGHT worker
（通知/定时任务）、HEAVY worker（CDR/PDF，并发固定为 1）。
运行 `pm2 status` 必须三个都是 online；Web 只监听 `127.0.0.1:3000`，由
Nginx 在 443 对外提供。Next 16 默认会监听 `0.0.0.0`，所以 ecosystem 里的
`-H 127.0.0.1` 不能删，否则客户端可直连 3000 绕过登录/PDF限流。

物理内存低于 3 GiB 时，ecosystem 配置会自动启用低内存档（Web 512 MiB、
LIGHT 384 MiB、HEAVY 640 MiB）。这只能作为带 swap 的临时部署方案；
Puppeteer 高峰仍可能换页，生产服务器应尽快升级至至少 4 GiB。

## 9. Nginx 反向代理 + HTTPS

```bash
# 复制示例配置，改域名和证书路径
sudo cp deploy/nginx.conf.example /etc/nginx/conf.d/print-shop-erp.conf
sudo nano /etc/nginx/conf.d/print-shop-erp.conf   # 改 server_name / ssl 证书路径

sudo nginx -t                # 测试配置
sudo systemctl reload nginx
```

配置里**四个关键点**（示例文件已含，务必保留）：
1. `X-Forwarded-Proto $scheme` —— 否则二维码/短链退化成 localhost 死链、登录 cookie Secure 失效
2. `X-Forwarded-Host $host` —— 二维码/短链域名跟随它
3. `location = /login` 上的 `limit_req zone=erp_auth` —— 这才是防登录爆破的那一处。
   本项目登录走 Server Action，浏览器 POST 的是 `/login` 本身，**不会**访问
   `/api/auth/callback/credentials`；后者的块只是纵深防御，共用同一个令牌桶。
   配套的 `map $request_method $erp_auth_limit_key` 不能删 —— 删掉会连 `GET /login`
   一起限流，未登录用户点几下就会被登录页 429 挡在门外。
4. PDF 路由的 `limit_req zone=erp_heavy` —— 防按需 Chromium 被并发压垮

改完务必 `sudo nginx -t`：`map` 与 `limit_req_zone` 都必须在 `http {}` 层，
重复 include 同名 zone 会直接报错。

> **将来在 ECS 前加阿里云 SLB / CDN 时必须先做 real_ip**：`$binary_remote_addr` 会变成
> SLB 的 IP，全站共用一个令牌桶、登录会被自己限死。届时先用 `set_real_ip_from` +
> `real_ip_header X-Forwarded-For` 还原真实客户端 IP 再上线。当前 nginx 直接做边缘，不受影响。

访问 `https://你的域名` 应看到登录页。

如果证书由 Certbot webroot 签发，保留 HTTP server 中的
`/.well-known/acme-challenge/` 例外；示例配置已包含。部署后执行
`sudo certbot renew --dry-run` 验证自动续期链路。

## 10. 定时任务（10 个 cron）

系统有 10 个需要每天/每月自动跑的任务。用系统 crontab 调用仓库内的
`deploy/run-cron.sh`。它只允许已知端点、验证 HTTP 202，并把结果写到
syslog；密钥从 root-only 文件读取，不明文写进 crontab，**也不进 curl 的命令行参数**
（改用 `--header @-` 从 stdin 喂 Authorization 头——否则同机任何用户一句
`ps -efww | grep Bearer` 就能读走完整 `CRON_SECRET`）。

> **环境要求：`curl >= 7.55`**（`--header @-` 是 2017 年的 curl 7.55.0 引入的）。
> Ubuntu 22.04（7.81）/ Debian 12（7.88）/ Alibaba Cloud Linux 3（7.76）都满足。
> 万一系统 curl 更老，它会把 `@-` 当成字面头名发出去 → 服务端 401 → 脚本走 HTTP 401
> 分支 `exit 1` 并写 syslog，是**响的失败**而不是静默失败，用 `curl --version` 一查便知。

```bash
sudo install -m 755 deploy/run-cron.sh /usr/local/sbin/print-shop-erp-cron
sudo install -m 600 deploy/crontab.example /root/print-shop-erp.crontab
sudo nano /root/print-shop-erp.crontab  # 改 APP_PUBLIC_URL 和 CRON_SECRET_FILE
sudo crontab /root/print-shop-erp.crontab
```

默认模板如下（把 `erp.example.com` 换成域名）：

```cron
# 师傅日薪结算（每日 00:30）
30 0 * * * /usr/local/sbin/print-shop-erp-cron daily-salary
# 客服周期结算扫描（每日 01:00）
0 1 * * * /usr/local/sbin/print-shop-erp-cron cs-settle
# 客服周期 7 天预警（每日 08:00）
0 8 * * * /usr/local/sbin/print-shop-erp-cron cs-period-ending
# 外协超期推送（每日 08:10）
10 8 * * * /usr/local/sbin/print-shop-erp-cron outsource-overdue
# 承诺交期逾期推送（每日 08:20）
20 8 * * * /usr/local/sbin/print-shop-erp-cron order-overdue
# 待工厂确认积压推送（每日 08:30）
30 8 * * * /usr/local/sbin/print-shop-erp-cron pending-factory-backlog
# 报工超前与下发未认领扫描（每 10 分钟）
*/10 * * * * /usr/local/sbin/print-shop-erp-cron production-alerts
# 工单导出过期产物与筛选隐私清理（每日 02:15）
15 2 * * * /usr/local/sbin/print-shop-erp-cron order-export-cleanup
# 时薪工月结（每月 1 号 00:00）
0 0 1 * * /usr/local/sbin/print-shop-erp-cron hourly-payroll
# 销售应收账单生成（每月 1 号 00:40）
40 0 1 * * /usr/local/sbin/print-shop-erp-cron generate-bills
```

> 不要把这些任务切到 `pg_cron` + `pg_net`。共享 bearer secret 若存成数据库级
> 自定义 GUC，任何能建立数据库会话的角色都能用 `current_setting()` 读取。
> 生产唯一支持的调度路径是本节的系统 crontab + root-only secret file。

**10 个端点的响应码**：正常入队 `202 queued`；`CRON_SECRET` 不匹配 `401`、留空 `503`；
意外异常 `500`（COUNTS ONLY，不带金额/姓名）。

**2026-08-21 起 `daily-salary` 与 `hourly-payroll` 各多一个 `400`**：只在**人工带 body 重跑**
时可能命中 —— `daily-salary` 的 `body.date` 严格晚于上海日历今天时返回
`400 {"error": "future date: <date>"}`，`hourly-payroll` 的 `body.month` 严格晚于上海本月时
返回 `400 {"error": "future month: <month>"}`。上面 crontab 里的调用都不带 body，默认算的是
「昨天 / 上月」，**永远不会**踩到这个分支，`run-cron.sh` 的 202 判定不受影响。
当天 / 当月仍然允许结算（重算今天、重算本月是业主的正常用法）。

## 14. 日常运维

**更新部署（推荐：一键脚本）** —— 首次上线后，每次拉新版本只需一条命令：

```bash
cd /var/www/print-shop-erp
./deploy/update.sh
```

> **当前不能直接照抄这一条**：截至 2026-08-03，生产 SHA `aa42ba0` 位于本地功能分支，`main` 仍是 `245be5c`，且开发仓库没有 Git remote。应先明确合并目标、建立受控远端并确认服务器 tracking branch；否则脚本中的 `git pull` 会失败，或更危险地把旧 `main` 当成发布源。

脚本自动完成：记录当前版本 → `git pull` → 装依赖 → **env 预检** → 生成 Prisma Client → 构建 → **停止 Web 与两个 worker** → `migrate deploy` → 立即启动三个新进程 → **就绪检查**。依赖、预检和构建失败时旧进程仍在线；进入停机窗口后，迁移、启动或探活任一步失败，脚本都会确保三个进程保持停止，避免旧代码继续写入新结构。

> 手动顺序参考（不含脚本的失败 trap，生产仍应优先使用脚本）：
> ```bash
> git pull --ff-only
> CI=true pnpm install --frozen-lockfile
> NODE_ENV=production node scripts/check-env.mjs
> pnpm exec prisma generate
> pnpm build
> pm2 stop print-shop-erp
> pm2 stop print-shop-erp-worker-light
> pm2 stop print-shop-erp-worker-heavy
> pnpm exec prisma migrate deploy
> pm2 startOrReload deploy/ecosystem.config.cjs --update-env
> curl -fsS http://127.0.0.1:3000/api/health/ready
> ```

> **迁移开始后只做前向修复**：数据库迁移可能已提交，禁止直接 `git checkout` 旧 commit 再启动旧进程。先修正当前发布版本或补一条新的前向 migration，再重新运行 `./deploy/update.sh`。当前发布尾部的 `20260802093000`、`20260802100000`、`20260802103000`、`20260802110000`、`20260802113000` 自带显式事务，失败会回滚各自文件内的 DDL/DML；`20260822110000` 则先在事务外做无副作用的只读 preflight（确保 Prisma 能显示真正的核对错误），通过后才把全部 DDL/DML 放入一个显式事务。其他 migration 是否原子必须逐份确认，不能仅凭命令失败就假设数据库没变化。无论哪种情况，进程都会故意保持停止。只有经过批准的整库备份恢复，才可与匹配的旧代码一起回退。

**并发建索引失败恢复**：`20260807170101` 至
`20260807170118` 每份只有一条 `CREATE INDEX CONCURRENTLY`，避免在建索引全程阻塞工单写入。这类 DDL 不在事务里；中断时可能留下同名的 `INVALID` 索引。因为迁移使用 `IF NOT EXISTS`，**不先删除无效索引就重试会跳过重建**。保持 Web/worker 停止，按下面顺序处理：

```sql
-- 只读诊断：正常应返回 0 行。
SELECT
  n.nspname AS schema_name,
  c.relname AS index_name,
  i.indisready,
  i.indisvalid,
  i.indislive
FROM pg_index AS i
JOIN pg_class AS c ON c.oid = i.indexrelid
JOIN pg_namespace AS n ON n.oid = c.relnamespace
WHERE
  n.nspname = 'public'
  AND (NOT i.indisready OR NOT i.indisvalid OR NOT i.indislive)
ORDER BY c.relname;
```

DBA 确认返回的索引就是失败 migration 的目标后，在**非事务会话**中逐个执行
`DROP INDEX CONCURRENTLY public."<index_name>";`，再执行：

```bash
pnpm exec prisma migrate resolve --rolled-back <failed_migration_name>
pnpm exec prisma migrate deploy
pnpm exec prisma migrate status
```

不要对未经确认的索引使用通配删除，也不要把 migration 直接标成
`applied`。`app_ops.search_index_readiness` 同时检查
`indisready / indisvalid / indislive`，无效索引会继续显示为阻断，不会因同名对象存在而假绿。

**Fresh DB 迁移验证（发布候选必跑）**：本仓库的历史 migration 可能已在本地或其他环境应用，修改其源文件不会重放到这些数据库。发布前应由 Pigsty 管理员提供一个**全新、空白、可丢弃且绝非生产/共享开发库**的连接串，在发布候选 commit 上验证完整迁移链：

```bash
# FRESH_DATABASE_URL 只能指向新建的临时空库；本流程不包含 reset/drop。
DATABASE_URL="$FRESH_DATABASE_URL" pnpm exec prisma migrate deploy
DATABASE_URL="$FRESH_DATABASE_URL" pnpm exec prisma migrate status
DATABASE_URL="$FRESH_DATABASE_URL" pnpm db:seed

# 用真实视觉 fixture 验证近期 UI 所依赖的列和约束可写入。
DATABASE_URL="$FRESH_DATABASE_URL" E2E_BASE_URL="http://127.0.0.1:3100" \
  pnpm exec playwright test tests/visual/worker-responsive.spec.ts --workers=1
```

`prisma migrate status` 必须显示当前已 checkout 的 release SHA 中
`prisma/migrations/` **全部 migration** 均已应用；用
`find prisma/migrations -mindepth 1 -maxdepth 1 -type d | wc -l` 动态核对目录数，
不要把旧文档里的固定数量当作发布门禁。上述无效索引诊断还必须返回 0 行。
视觉 fixture 会实际写入并清理近期业务列。历史财务、计价与考勤 migration 的
fail-fast 检查仍必须逐项通过；不能为过迁移而盲改数据。
`20260821090000` 的三条并发索引和
`20260821120100` 的通知幂等唯一索引都必须验证 `indisvalid`，后者是通知重试的
正确性依赖，不是可缺失的优化。`20260822109000` 只为可证明的单款旧外协单预填
快照证据；`20260822110000` 会在任何 DDL 前拒绝缺少逐款历史证据的存量单，并整段
事务回滚，恢复步骤见上线前置清单。不能跳过任何检查。以上命令成功后，再按 smoke
checklist 跑关键业务链。临时库的销毁由 Pigsty 管理员在确认连接目标后单独执行；
若目标生产库已经应用过被修改的历史 migration，必须新增前向 migration 落实等价修复。

**健康检查端点**：`GET /api/health/live` 只检测进程；
`GET /api/health/ready` 检测 DB 与 worker 心跳，决定「能不能接流量」（死信只进 warnings，不改状态码）；
`GET /api/health/jobs` 专门盯队列，有**非通知类**死信 / 卡死 RUNNING / worker 缺失时返回 503。
外部监控两个都要接：ready 采可用性 SLO，jobs 采死信响应 SLO。
**接进监控之前，死信 30 分钟响应目标不生效** —— 代码只是把信号暴露出来了，没有任何东西会自动去拉 `/api/health/jobs`。
ready 的响应体自 2026-08-21 起附带 `jobs` 计数（`pending` / `running` / `staleRunning` / `deadLast24h`），`status` 取值域不变，仍是 `ok | degraded | error`。
`/api/health/jobs` 的 `jobs` 对象在此基础上再多一个 `deadNotificationLast24h`（只加不减），
并且**通知类死信只让它返回 200 `degraded`、不再 503**，告警码为 `dead-notification-jobs-last-24h`；
`/api/health/ready` 的状态码语义完全不变。通知投递失败的处置渠道是 `/owner/notifications`
与 `/owner` 首页的 24 小时推送失败告警条，不是这个探针（见 `docs/production-slo-and-recovery.md`）。
两个健康端点的 `smartBot` 对象还会给出安全的 `required`、`configurationValid`、`identityMatch`、`operational` 状态，不会返回 Bot ID 摘要、群 ID 或 worker 明细。启用智能机器人目标后，身份不一致、目标配置残缺或凭据未配置会让 jobs 探针告警；受控更新还会最多观察 120 秒，只有唯一的当前版本 LIGHT worker 保持 `CONNECTED` 才继续，持续 `CONNECTING` / `DISCONNECTED` 会拒绝发布。历史非通知死信仍只在发布时告警，不会阻断用于修复它的前向版本。

**查日志**：`pm2 logs` / Web 错误 `/var/log/print-shop-erp/web-error.log` / worker 错误 `worker-*-error.log`

**紧急踢掉所有会话**（如密钥泄漏、员工离职要立即失效）：换 `.env` 里的 `AUTH_SECRET` → `pm2 reload`。所有人需重新登录。（注意：管理员给师傅改密码**不会**立即踢掉其已登录会话，最长 30 天；要即时失效只能换 secret。）

**恢复策略**：停机窗口前的失败尚未迁移，可修复构建后重跑；停机窗口后的失败按上面的前向修复流程处理。不要单独回退代码。确需恢复旧版本时，必须由运维同时恢复与其匹配的数据库备份，并重新执行完整 smoke。

## 15. 故障速查

| 现象 | 大概率原因 |
|---|---|
| 登录后又跳回登录页 | `AUTH_TRUST_HOST` 没设 `"true"`，或 Nginx 没转发 `X-Forwarded-Proto` |
| 师傅微信扫码打不开 / 是 localhost 链接 | `APP_PUBLIC_URL` 没配，或 Nginx 漏 `X-Forwarded-Proto` |
| 设计图上传转圈后报错 | OSS bucket **CORS 没配**（§6） |
| 点上传按钮是灰的 | 5 个 `OSS_*` 环境变量没配全 |
| 下载 PDF 报错 | `/usr/bin/chromium` 未安装/不可执行、PM2 未传 `PUPPETEER_EXECUTABLE_PATH`，或缺中文字体/系统库（§7） |
| PDF 一直排队 / CDR 不生成 | HEAVY worker 未 online，查 `/api/health/jobs`（死信/卡死 RUNNING 会让它 503）和 `worker-heavy-error.log` |
| 后台推送日志显示成功但群里没消息 | `NOTIFICATION_MOCK_MODE` 误设 `"true"`，或事件规则没绑群/没启用 |
| 定时任务没跑 | crontab 没配（§10），或 `CRON_SECRET` 不一致导致 401；系统 curl < 7.55 时 `--header @-` 也会退化成 401（`curl --version` 一查便知） |
| 人工重跑日薪/月结返回 400 | 传的 `date` / `month` 是未来的（上海日历），改成今天/本月或更早再试（§10） |
| cron 返回 202 但没结果 | LIGHT worker 未 online，在 `/owner/background-jobs` 查积压/死信 |
| 每个 cron 返回 503 | `.env` 的 `CRON_SECRET` 留空了 |
| 应用起不来 | `DATABASE_URL` 连不上，看 `pm2 logs` |
