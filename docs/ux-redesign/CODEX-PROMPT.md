## 四条已作废的旧建议（照做会修不存在的问题）

1. **不要补侧栏分组。** `lib/navigation/admin-modules.ts` 里 ADMIN 已有 30 个模块，主数据/设置/运维全在导航里。真正要做的是分组可折叠 + 记住折叠状态 + 高频项置顶（执行清单第 12 项）。
2. **不要抽 useListState 改 23 个列表页。** 筛选状态已在 URL：`lib/order/list-query.ts` 的 `OrderListSearchParams` 有 25+ 字段，页面按 `searchParams` 取数。只补两件：滚动位置与选中行入 URL、新增保存视图（第 11 项）。
3. **不要「把分类色从灰阶改成彩色」。** `--chart-1` 是 `oklch(0.532 0.131 244)`，本来有彩度。只需验色相间隔与色盲模拟。
4. **面包屑不是补 key。** `admin-modules.ts` 里每个模块已带 `breadcrumbLabel`，问题是 `AdminBreadcrumb.tsx` 用了自己那张 `SEGMENT_LABELS`，两张表不同步。改法：优先读模块表 → 回落 SEGMENT_LABELS → 回落页面 H1（第 07 项）。

## 必须保持的业务契约（违反即回退）

- **角色与权限**：`lib/auth/permissions.ts` 是准。SALES 与 CS 在工单三页上权限完全相同（`order:create` / `order:update:pre-schedule` / `order:view:self` / `order:mark-urgent` / `design:upload`）——共用页面按 scope 裁数据范围，**不裁动作**。差异只在侧栏：SALES 出「我的账单」，CS 出「我的工资」。
- **状态机不变**：工单 `DRAFT → SUBMITTED → SCHEDULING → IN_PRODUCTION → COMPLETED → SHIPPED → FINISHED`，`CANCELLED` 为终态；生产任务 `PENDING → IN_PROGRESS → COMPLETED`。不新增、不合并、不让界面执行状态机不允许的跳转。
- **通知四态语义不得合并**：`SENDING` / `RETRYING` / `UNKNOWN` / `FAILED`。`UNKNOWN` 不得改成自动重试；`RETRYING + job DEAD` 是合法组合，必须在告警条、徽章、未解决队列三处可见，**禁止为了让红色更整齐把 RETRYING 改写成 FAILED**。
- **外协覆盖保持 max 口径**，不得改 sum，指标名不重命名。
- **金额精度**：服务端权威计算，UI 预览不是唯一计算源；保持精确十进制，不引入浮点取整。加工费 / 快递费 / 打包耗材 / 一次性费用四类分项不得合并成总额。
- **薪资快照**：保留生成时的规则快照，人工调整是追加事实，历史金额不可任意覆盖。
- **登录限流**：成功登录也消耗 GCRA 令牌、非法表单也算一次尝试，均为刻意设计。只优化文案与恢复指引，不动准入语义。
- **打印是生产资产**：`/print/orders/:id` 视觉基线受保护，本轮完全未动。**不要碰它**，也不要让全局 token 改动改糊它。
- **停用 ≠ 删除**：主数据停用后历史工单仍引用。停用属 L3 操作。
- **占位菜单**（`routeBase: '#'`）保持灰态并标「未上线」，不得设计成已上线功能。

## 操作三级阶梯（决定按钮样式、位置、确认方式）

- **L1 常规**：直接执行，描边次要按钮，无确认。
- **L2 需确认**：主按钮，二次确认层**必须列出影响范围**（会创建/更新哪些对象、影响哪些下游），不只是「确定要继续吗」。
- **L3 需理由 / 不可逆**：与常规动作物理分开，必须填理由，确认层逐条列出受影响对象数量，操作留痕可查，**不进批量操作**。属于 L3 的：取消工单、批准/拒绝变更申请、薪资重算与发放、盘点过账、发布价目版本、停用主数据、通知模板改动、账号停用。
