B · 十条交互契约

按骨架分组。每条都写了为什么（对应当前实现的哪个问题）和验收口径（能截图或交互测试验证的结果），不写「更现代」这类无法验收的话。

分组口径的一处修正（2026-08-23）
下方映射表原本有「通知运维」「后台任务与运维」两族，把四类不同的东西归成了「运维」。已按「谁处置、处置的后果是不是业务」重切：Pigsty 是纯基础设施只读，不进侧栏导航，只从告警条进入；后台任务拆开——死信里有业务后果的（通知投递失败、导出失败）并入 Dashboard 的待处理异常队列，worker 心跳与队列深度跟 Pigsty 走；通知配置、系统设置、账号是业务配置，归「设置」组；CDR 是给车间的业务作业，归业务组。因此侧栏不设「运维」组——这也修正了批次一线框里我原来提的建议。
「为什么」里的证据标注
沿用线框文档的口径：观察= 能在指名的截图和视口里指到具体位置；推断= 证据不足，需要材料或你的回答，不当作现状。静态截图无法证明的东西（URL 里有没有筛选参数、返回后状不状态恢复、断网能不能恢复草稿、没打开过的页面长什么样）一律标推断。标推断不等于契约不成立——契约是目标状态；但它意味着「当前实现有没有这个问题」还没核实，落地前要先确认，否则可能在修一个不存在的问题。
