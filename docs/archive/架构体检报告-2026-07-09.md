## 一、架构概述

### 分层与数据流

```
app/（RSC 页面，读路径直调 lib）
  └─ actions/（Server Actions：第一行 requirePermission → Zod safeParse
              → 调 lib → 领域错误翻译成 {success|invalid|error} 三态 → revalidatePath）
       └─ lib/（业务层，Prisma 唯一入口）
            ├─ 纯函数计算层：salary/machine-piecework、hourly-payroll、cs-commission
            │   （零 DB 依赖，100% 单测）
            └─ 编排层：order.ts、production.ts、salary/{daily,cs,hourly-aggregate}
                （事务、advisory 锁、规则解析、快照落库）
```

- **状态机纪律执行得很好**：order / production / bill / cs-period / outsource 五个同构状态机
  文件（转移表 + 专属 Error 类 + transition/can/isTerminal），全库无裸写 status。
- **薪资快照铁律（CLAUDE.md §4.4）四个落账点全部落实**：reportTask、settleCsPeriod、
  computeHourlyPayroll、computeDailyWorkerSalary。
- **并发模型**：所有 Order.status 写入方（手动转换 / 排产 / 报工级联×2 / 外协挂单 / 设计图
  登记）共享同一把 per-order advisory 锁 `print-shop-erp:order-cascade:<id>`，锁内 fresh-read
  再走状态机。薪资侧用 per-(worker,date)/(worker,month)/cs-user 锁保护"已发放拒绝重算"。
  ——设计正确，但此前锁 key 靠 5 处字符串字面量手工维持（本次已收敛，见 §三）。
- **通知管道是全项目分层最好的模块**：index（公开 API）→ notify（永不抛，fan-out+写日志）
  → webhook（重试）/ render（模板）/ events（类型+运行时双保险）/ dispatch（Next 16
  `after()` 防 SIGTERM 丢推送）。
- **Auth 拆分教科书级**：config/config.edge（edge-safe middleware）+ permissions-dict（纯数据）
  / permissions（检查函数）/ order-scope（纯 where 片段）三分，测试无需 mock next-auth。
- **测试安全网**：1272 单测（薪资算法/状态机/权限 100%）、22 E2E、6 张打印视觉基线。

**总体评价**：对独立开发者的 MVP 而言，分层纪律、并发正确性意识和测试覆盖是超水准的。
主要债务不是"写错了"，而是**同一约定的 N 份手工拷贝**——锁 key、tx 类型、状态机模板、
规则查询、表单样板在垂直切片开发中各自复制，正确性靠注释和"别打错字"维持。

## 二、问题区域

### B. 结构性债（按优先级）

1. **lib/auth/schemas.ts 巨石（1597 行）**：17 个业务领域的 50 个 schema 挤在 auth/ 下，
   38 个文件依赖。纯日期工具 `parseStrictYmd` 藏在第 1251 行（前 500 行靠函数提升引用它，
   改成箭头函数即 TDZ 崩），8 个文件为它 import 整个模块。文件内部还有 4 套等价 safe-id
   builder、4 套正整数 builder、2 套逐字相同的 optional-id builder。
   拆分硬约束：**必须保持浏览器安全**（只从 generated/prisma/enums 导入——OrderForm 在
   客户端用 zodResolver），验收必须加 `pnpm build`（单测在 node 里跑，测不出 bundle 回归）。
2. **12 个手写 TxClient 结构类型**把 Prisma 写入的 data/select 全退化为 `unknown`——列名
   拼错编译期不报。Prisma 7 的 `Prisma.TransactionClient` 可替换（需独立验证后实施）。
3. **客户端岛复制粘贴**：8 个 Toggle*ActiveButton（7 份近似 + BOM 漂移版）、约 12 个
   "单发动作按钮"（3 种 pending 写法）、14 份本地 TextField（a11y 属性已漂移：craft 版有
   aria-describedby，bom 版没有）、14 份 selectClass 字符串。
4. **Order.status 写入编排（lock→fresh read→状态机→update→OrderLog）手工重写 4 处**，
   `transitionWithLog` 未复用——历史上 beginTask/reportTask 的 TOCTOU bug 正是复制漏步骤
   的产物。
5. **组件测试为零**：CLAUDE.md §8.2 要求的 Vitest Browser Mode 未落地（注意：Vitest 4 把
   provider 拆成独立包 `@vitest/browser-playwright`，§8.2 的配置片段已失效）。组件层唯一
   兜底是打印视觉基线 + E2E。
6. **audit-log 基建完备但只有 1 个接线点**（owner-parties），投入与覆盖不匹配。
7. **"今天/本月（上海）"日期家族**以 3-4 个名字散落 6 个文件，`lib/dashboard/shanghai-clock.ts`
   已是正源且注释自认此债。
8. actions 层 P2002 唯一约束映射仍有 4 份手写（helpers 的 `mapPrismaUniqueViolation` 已
   覆盖同一逻辑）。

### C. 性能

- ~~createOrder 产品校验 N+1~~（**已修**，见 §三）。

client-server 边界 / import 环 / "貌似重复实则有差异"），验证通过才实施；每切片全量
单测 + lint + tsc；打印路径改动跑视觉基线；批次终点 Codex 复核。
