# 企业微信旧配置入口退役检查

范围：管理后台 `/owner/notifications`、目标新建/编辑页、事件规则、系统设置的管理通知路由。此次只调整配置入口与校验，不更换凭据、不自动迁移真实收件群、不启动 worker，也不发送真实通知。

## 检查结论与已完成修改

原 UI 只完成部分同步：默认选择智能机器人，但仍可切换到 Webhook；旧目标可编辑、测试、加入新路由。编辑页还将完整 Webhook 传给客户端组件，服务端 schema 在省略协议时默认落到旧协议。

- 新建/编辑仅接受 `WECOM_SMART_BOT`，移除旧协议选项、Webhook 输入及对应创建/更新分支。旧请求、省略协议、夹带 Webhook 字段和伪装协议覆盖旧目标均被服务端拒绝。
- 旧目标从操作列表移到折叠的只读记录；直接访问旧编辑 URL 显示迁移说明，不显示表单或密钥。旧测试请求不会发送或排队。
- 规则及系统设置不再显示未选中的旧目标；原已选项仍可保留或取消，避免保存其他设置时静默变更存量收件群。关闭后带旧目标重新启用会被拒绝。
- 托管事件中不参与实际路由的隐藏历史 ID 不再卡住事件启用；实际角色设置仍严格校验，普通规则的旧目标仍不能重新启用。
- 配置查询不再读取 Webhook；移除仅被旧列表消费的 Webhook 脱敏展示函数。智能机器人编辑页仅传脱敏群信息，凭据仍留在服务端。
- 长连接状态面板常驻；补齐启用字段的服务端错误提示，引用数表头改为“配置引用”（包括规则和固定角色路由）。

## 保留依据与迁移边界

本次对当前开发库进行了只读核对：1 个旧 Webhook 目标，2 条历史日志、无配置引用；另有 1 个智能机器人目标。未删除这些数据。

旧发送实现不是死代码：`lib/notification/notify.ts` 的普通投递和历史重放仍按 transport 读取旧目标；投递账本/目的地指纹、UNKNOWN 人工处置、全局限流与 URL 安全校验仍有消费方。因此这些兼容路径、Prisma 历史结构及已应用迁移全部保留。不应把“配置入口已退役”理解为“所有历史协议代码均可删除”。

其他环境若仍有旧路由，应先新建并完成智能机器人群绑定，再逐项替换事件及角色路由。未经管理员确认，不批量改写目标或处理历史未决消息。
