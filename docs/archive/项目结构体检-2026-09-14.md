## 三、缺陷清单（按严重度）

### 缺陷 1 · `pnpm test run` 在本机红灯，根因是测试耦合了开发库业务数据

`lib/order/__tests__/current-create-order-golden-gate.postgres.test.ts` 直接读取**当前开发库里已发布的加工费价目簿**（`readPublishedCreateOrderPriceSnapshot`），再与 42 个黄金用例逐一比对。

本机开发库在 2026-09-13 14:06 发布了第 10 版价目簿（`CustomerPriceBook.version = 10`，来源 `加工费计费规则.md`），其中 `BASE_EXT-CUSTOM-LARGE_Q200` 单价被录成 **¥1**，显然是手工验证价格版本页时留下的测试数据。于是 11 个 `S8-FULL-*` 用例失败。

- **这不是代码回归**：CI 用全新种子库跑，仍是绿的。
- **但它是测试设计缺陷**：任何人在开发库点一次"发布价格版本"，本机全量测试就红，之后所有人都会习惯性忽略这个红灯。CLAUDE.md §6.3 要求每次 commit 前跑 `pnpm test run`，这条规则在本机已经事实失效。
- **建议**（不影响功能）：让该测试在事务内**自己发布一份黄金价目簿再读快照**，然后回滚；或改为只在 `E2E_DATABASE_URL` / CI 专用库上跑（其它 `*.postgres.test.ts` 已有 `describe.skip` 的门槛模式可复用）。开发库的第 10 版测试数据可另行退回，与代码无关。

### 缺陷 2 · `pnpm check:architecture` 红灯，当前分支推上去 CI 会挂

```

```

- 引入提交：`749c3d87 feat(order): 支持默认入袋、不包装与版本化装盒计价`（2026-09-13）。
- 这条门禁在 CI 的 "Static quality gates" 步骤里，排在 lint/typecheck **之前**。当前分支 `codex/gongdanceshi` 尚未推到远端，所以还没被 CI 拦到；一旦开 PR 就红。
- **建议**：二选一，都不改行为。(a) 把 `OrderPricingReviewForm` 里任一段 JSX 或 handler 抽成同文件内的小组件/函数，让主函数回到 ≤ 723 行；(b) 如确认这次增长合理，更新 `config/architecture-debt.json` 该项 `maxLines` 并在 commit message 说明。推荐 (a)，因为债务表的设计意图是"只降不升"。

### 缺陷 3 · 超大文件持续膨胀，已经超出门禁能管的范围

架构门禁只管"函数"长度，不管"文件"长度。以下文件已经大到影响改动安全和 review 质量：

| 文件 | 行数 | 说明 |
|---|---|---|
| `lib/order/change-request.ts` | 6143 | 改单域全部逻辑在一个模块 |
| `lib/order.ts` | 4410 | 与 `lib/order/` 目录并存，职责边界不清 |
| `components/business/order/OrderForm.tsx` | 3991 | 主函数 3106 行，债务表最大项 |
| `lib/price/customer-price-book-admin.ts` | 3852 | 且 knip 报告其中有 3 组重复导出（`parse…Manifest` / `parse…V1Manifest` 等） |
| `lib/auth/schemas.ts` | 3756 | 全站 Zod schema 集中在一个文件（CLAUDE.md §15.3 的约定，但已到极限） |
| `lib/order/export.ts` | 2239 | |
| `app/(admin)/orders/[id]/page.tsx` | 2035 | 页面函数 1673 行，页面层承载了太多编排 |

- **风险**：单文件几千行时，两个并行任务改同一文件几乎必然冲突；测试文件也跟着膨胀（`lib/__tests__/order.test.ts` 216 KB）。
- **建议**：不做大重构，只在**下次触碰某文件时**顺手拆当次改动涉及的那一段。优先级：`change-request.ts`（按"申请 / 审核 / 应用 / 时间线"拆）> `OrderForm.tsx`（按 rail / 款式行 / 费用明细拆）> `schemas.ts`（按域拆到 `lib/auth/schemas/<domain>.ts`，保留 `schemas.ts` 做 re-export，调用方零改动）。

### 缺陷 4 · Vitest Browser Mode 的产物没进 `.gitignore`

工作树里有 5 个未跟踪目录 `components/**/__tests__/__screenshots__/`（共 126 个 PNG，3.7 MB），是 `*.browser.spec.tsx` 运行时的截图产物。它们既不在 `.gitignore`，也没有被任何测试当基线比对（仓库里 `toMatchScreenshot` 用量为 0）。

- **建议**：在 `.gitignore` 追加 `**/__tests__/__screenshots__/`。零功能影响。

## 四、次要观察（不算缺陷，顺手记录）

- **lint warning**：`app/global-error.tsx:43` 与 `OrderForm.tsx:2917` 用 `window.location.assign()` 跳内部页。前者在全局错误边界里是合理的（此时 router 可能已不可用），后者值得换成 `useRouter().push()`。
- **knip**：134 个未使用导出、229 个未使用类型，集中在 `components/ui/dropdown-menu.tsx`、`lib/agent-monthly-billing/export.ts`、`lib/order/list-query.ts`、`lib/price/create-order/index.ts` 等 barrel 文件。CI 已把它当"证据"上传，不是门禁，可以继续不管。
- **`lib/` 根级 38 个散文件**：`bill.ts`、`bom.ts`、`craft.ts`、`material*.ts`（5 个）、`purchase*.ts`、`warehouse.ts`、`party.ts`、`inventory-count*.ts`（3 个）都是独立域，但没有像 `order/`、`price/` 那样归目录。新代码建议按域建目录，旧文件不动。
- **`public/images/order/foil/*.png`**：7 张 1254×1254 的烫金色卡 PNG 共 13 MB，仓库最大的资产。渲染端是 `next/image` + `sizes="3rem"`，浏览器只拿缩略图，所以只影响仓库体积和首次图片优化耗时；可以压到 400px 以内，不影响显示。
- **测试输出噪声**：`[order-pdf] PDF_GENERATION_FAILED` 会在 `pnpm test run` 中打印一行 stderr，是预期的失败路径日志，但会让人误以为有失败。
- **分支状态**：本地 `codex/gongdanceshi` 26 个提交未推远端。按 CLAUDE.md §6.1，`main` 受保护只收 PR；这批改动要走 PR 就得先修缺陷 2。
