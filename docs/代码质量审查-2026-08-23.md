## 一、这批改动实际在做什么

写路径 / 投递路径的加固，不是新业务切片：

- 企业微信 webhook：发送前先占 `SENDING`、fencing token；`UNKNOWN` 走业主人工核对队列
- 持久化 cron / 薪资：每次独立提交的写之前重新证明 job 租约（`ExecutionFence`）
- 外协履约：从「是否有链接」改成创建时的逐款数量账本（`OutsourceOrderItemSnapshot`）
- 登录爆破：Postgres GCRA 桶，而不只靠 nginx
- 退役 pg_cron HTTP 调度，只留主机 cron + 任务账本
- 日薪：冻结 roster + `DailySalaryCronRun` 完成证明，避免 v1 部分通知被当成整批完成

问题选对了。审查标准是：代码现在看起来是否「本该如此」，还是五轮加固叠进了共享模块。

## 二、必须处理（默认阻断合入）

### B1. 领域策略泄漏进通用任务账本

**严重度**：阻断
**位置**：

- `lib/background-jobs/repository.ts:175-305`（claim 热路径里的通知 / CDR / 导出清扫）
- `lib/background-jobs/repository.ts:79-84`（enqueue 拒绝复活 UNKNOWN 通知）
- `lib/background-jobs/repository.ts:598-603`（`retryDeadBackgroundJob` 同样的特判）

`claimNextBackgroundJob` 已经不是 claim。每次轮询（包括 1 秒空转的 `LIMIT 0`）都会：把最后一次 attempt 过期的 job 标 `DEAD`、把 `NotificationLog(SENDING)` 围栏成 `UNKNOWN`、用 **`errorMessage` 文本匹配** 诊断 `NotificationDeliveryUnknownError`、把 `DesignBundle` / `OrderExport` 标失败，然后才可能领到一行。

诊断 SQL 依赖这句拷贝的英文：

```
'worker lease expired after webhook may have been sent; owner confirmation required'
```

改文案，诊断会静默失效。下一种 job type 会再加第六条 `$executeRaw`。`repository.ts` 从 520 行涨到 693 行，就是这样越过 1000 行的。

**规定修法**：

1. 抽出 `reconcileExpiredLeases(tx)`（或同等名字的独立模块），claim 只做 `FOR UPDATE SKIP LOCKED` + 插入 attempt。
2. 子账本按 `job.type` join `terminal_jobs`，不要靠复制的英文 `errorMessage`。
3. 「UNKNOWN 通知不得自动复活」集中在一处终态策略，enqueue / retry / claim 共用，禁止三处 `if (type === 'NOTIFICATION')`。

### B2. `notify` 与人工重放是同一段循环，已经分叉

**严重度**：阻断
**位置**：

- `lib/notification/notify.ts:224-403`（`notify` 发送循环）
- `lib/notification/notify.ts:434-647`（`replayDurableNotificationLogs`）
- `lib/notification/delivery-ledger.ts:77-215`（claim 的双 SQL 路径）

`replayDurableNotificationLogs` 把「claim → 停用频道合成结果 → sender → 状态映射 → finalize / `markUnknown` / 再抛」抄了一遍。两边已经不一致：

| 场景 | `notify` | 重放 |
|---|---|---|
| 频道停用 | `retryable: false`（271–282） | `retryable: true`（546–554） |
| 账本版本不匹配被外层 catch | 不适用 | `retryable: true`（635–646），会烧掉 +3 重试预算 |

业主核对表单过期，应该是带类型的冲突，不是传输层可重试失败。

`claimDurableDelivery` 同样有双路径：带版本的 `UPDATE` vs `INSERT … ON CONFLICT`，再套 3 次重试。

**规定修法**：

1. 抽出一个 `deliverClaimedChannel(...)`，`notify` 与重放共用。
2. 重放只负责读钉死的 log、带 `expectedStateVersion` claim，然后调用 helper。
3. 重放版本冲突抛类型化错误，`handleNotificationJob` 映射为**不重试**的终态，而不是 `outcome.retryable = true`。
4. 人工重放的 claim 应是同一个 upsert，只多 `AND deliveryStateVersion = $n`。

停用频道在「首次投递」与「业主确认未送达后的原频道重放」语义不同，可以保留**一处**显式参数，不要两份循环。

### B5. `RETRYING` + `DEAD` 对业主不可见

**严重度**：阻断（新投递模型的契约缺口；HANDOFF 历史条目 12 的一半）
**位置**：

- `lib/notification/notify.ts:308-316`（最后一次 attempt 仍写 `RETRYING`）
- `lib/background-jobs/repository.ts:193-208`（清扫只围栏 `SENDING`）
- `lib/background-jobs/repository.ts:459-541`（`failBackgroundJob` 不动 log）
- `lib/notification/admin.ts:923-941`（`countRecentFailures` 只数 `FAILED` / `UNKNOWN`）
- `app/(admin)/owner/notifications/page.tsx:369-370`（徽章「重试中」）

最后一次 attempt + 企业微信 `45009` / HTTP `429`：

1. 写成 `RETRYING`（语义是「还会再试」）
2. job 被标 `DEAD`
3. 首页 24h 告警条仍是 0
4. `/owner/notifications` 显示「重试中」

进程在 finalize 之后、`failBackgroundJob` 之前挂掉，结果相同：清扫只处理 `SENDING`。

**禁止的修法（会把能重发的消息焊死）**：把这些行改成 `FAILED`。`claimDurableDelivery` 只回收 `RETRYING`；`FAILED` 是单调终态。`retryDeadBackgroundJob` 已经能复活**普通**通知死信（`lastErrorCode !== NotificationDeliveryUnknownError`）。HANDOFF 旧条目写的「RETRYING → FAILED」在新状态机下是错的。

**规定修法**：

1. 拥有 job 已是 `DEAD` 的 `RETRYING`，并入现有业主可见契约：24h 告警条 / 未解决队列 / 徽章文案（例如「死信，可从任务看板重试」），而不是「重试中」。
2. 不要新增第四种「半失败」状态。
3. 补测试：最后一次 attempt + `retryable: true`（fixture 用 `http 429` / `wecom errcode=45009`，**不要**再用 `http 500`，生产里 500 是 `unknown`）→ job `DEAD` + log 仍 `RETRYING` + 告警条 / UI 能看见。
4. 现有 `notify.test.ts` 里把 `{ errorMessage: 'http 500', retryable: true }` 期望成 `RETRYING` 的用例是错的，改成与 `webhook.ts` 一致。

## 四、明确不要动

这些是审查里评为「值回票价」或「改了会变弱」的部分。复审时若仍成立，**禁止**当问题修：

1. **不要重写投递状态机。** 留下 `SENDING` / `RETRYING` / `UNKNOWN` / `FAILED`。企业微信没有提供方幂等键，`5xx` / 超时 / 网络必须是 `UNKNOWN`，不能改回「再试一次」。
2. **不要把 `RETRYING` 在死信时改成 `FAILED`。** 见 B5。
3. **不要把 `ExecutionFence` 折叠进 `ClaimedBackgroundJob`。** 薪资 / cron 不该 import job 类型。fence 的三行协议（abort → assertLease → abort）留着。CDR / PDF 若仍手搓 `{ signal, assertLease }`，可以改用 helper，但那不是折叠类型。
4. **不要「修」剩余的 `useActionState` 箭头包裹**（CLAUDE.md §15.8 / DECISIONS 2026-08-17）。
5. **不要把 `IntentPrefetchScheduler` 改成 hook**，除非同时把「跳过当前项」的策略从 `AppSidebar` 拿出来。class 存在是为了让延迟可测。
6. **不要改登录限流「成功也消耗令牌」**，除非业主新拍板。
7. **不要**在 `lib/order.ts` / `lib/production.ts` 里继续堆逻辑来「顺便」消化本审查。
8. **不要**引入 Docker / Redis / 新队列 / 新依赖。
9. **不要**部署、不要连生产库、不要发真企业微信。
10. **覆盖判定取 max 不是求和**（`lib/outsource/coverage.ts` 约 97–114 行）：两张冻结 100 的旧单不能把后来加到 200 的款式算成已履约。不要「修」成 sum。
