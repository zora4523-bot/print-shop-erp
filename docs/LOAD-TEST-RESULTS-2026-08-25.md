# 2 核 2GB 服务器压测结果

测试日期：2026-08-24 至 2026-08-25。

## 容量判定

**不通过。** 这台 2 vCPU、实际约 1.6GiB 内存的机器不能同时满足 28 个独立用户、大范围工资导出和 PDF 生成的稳定性要求。内核没有 OOM，但 Web 进程多次超过 512MiB 的 PM2 限额并重启，因此不能通过“无重启、无错误”的验收门槛。

PDF 在修复 worker 启动条件后，短窗口吞吐达标，但还不是 1,000 份 / 3 小时的耐久结论。

## 测试基线

- 30,000 张工单，90,000 个款式，平均 3 款 / 3 工艺 / 3 收货地址。
- 1,000 张不同的可打印工单，每单 3 张真实 PNG，合计约 519KB。
- 28 个独立账号：销售 / 客服 20、主管 3、师傅 5。
- 50 人 × 180 天工资数据，共 9,000 行。
- PostgreSQL 15 与应用同机，HEAVY worker 并发为 1，企微和 CDR 对外操作为 mock。
- 严格体检在测前和清理后均为 `ready=true`。

## 实测结果

| 场景 | 结果 | 判定 |
| --- | --- | --- |
| 28 个共享管理员会话读取，60 秒 | 470 请求，442 个 200、28 个连接错误；p95 6.36s；Web 重启 | 失败，且这仍比 28 个独立会话更乐观 |
| 20+3+5 真实角色、独立登录 | 建立会话时 Web 从 restart 3 变为 4，压测在进入 15 分钟读取前因无 session cookie 终止 | 失败，无法稳定建立 28 会话 |
| 工资导出 50 人 × 180 天 | HTTP 200，有效 XLSX，1,145,905 bytes，3.743s | 响应时间通过；导出后 Web RSS 约 607MiB，随后发生 PM2 重启，稳定性失败 |
| PDF 修复前 4 份 | 4/4 DEAD，每次在 43–233ms 内失败 | 定位为 worker 的 React export condition 冲突，不是容量失败 |
| PDF 修复后 4 份 | 4/4 一次成功，平均 4.489s，p95 5.032s | 路径通过 |
| PDF 30 份，333.33 份 / 小时 | 30/30 一次成功，平均 3.867s，p95 4.727s，最大 5.238s；队列峰值 1 | 短窗口吞吐通过，不代表 3 小时耐久通过 |

PDF 30 份窗口内三个 PM2 进程均无重启；Chromium 合计 PSS 已观测峰值约 529MiB，可用内存最低约 357MiB，swap 从 253.5MiB 增至 454.8MiB。停止 76 秒后 swap 仍约 454.5MiB，表明 2GB 机器的内存余量很窄。

## 发现并修复的 worker 问题

LIGHT 通知处理器需要 `server-only` 的 React Server condition，但 PDF 的 `react-dom/server` 在同一 condition 下会直接拒绝渲染。已将 handler 按队列隔离：

- LIGHT 只加载通知和 cron handler，保留 React Server condition。
- HEAVY 只加载 PDF、CDR 和导出 handler，使用普通 Node `react-dom/server`。

修复后已通过 TypeScript、ESLint、handler / PM2 配置回归测试和远端实际 PDF 渲染。

## 下一轮建议

1. 不建议通过单纯抬高 2GB 机器的 PM2 内存限额上线，这会把可观测的重启变成整机 swap 抖动或 OOM 风险。
2. 下一轮可以用 **4 vCPU / 8GB 应用机 + 独立至少 2 vCPU / 4GB PostgreSQL** 作为候选起点，再实测确认，不把它当作未经验证的最终配置。
3. HEAVY worker 继续保持并发 1；在真实测试 OSS 上重跑 28 独立会话、工资导出和 1,000 PDF / 3 小时。
4. 当前 PDF 图片来自本机静态路径，PostgreSQL 也与应用同机；这一轮不能用于推断真实 OSS 网络耗时和独立数据库拓扑。
