## 🟠 零、历史外协逐款数量：没有证据就阻断迁移

`20260822109000_prepare_outsource_snapshot_reconciliation` 会建立
`app_ops.outsource_snapshot_reconciliation` 证据表和只读 worklist。只有“恰好一个款式且
创建时保存了正数 `totalQty`”的旧单能无歧义自动填入；多款式、`totalQty IS NULL`、链接缺失或
重复的未取消旧单都不能拿今天的 `OrderItem.quantity` 猜历史数量。

紧接着的 `20260822110000_write_path_integrity` 在任何 DDL/DML、也在显式事务开始前先做只读检查。
若证据缺失，它会直接显示 `Cannot backfill outsource snapshots...` 的根因；此时数据库尚未发生该
migration 的任何变更。检查通过后的约束、快照回填和盘点列变更才进入同一个显式事务，后续失败会
整体回滚。`deploy/update.sh` 会始终保持 Web/worker 停止。此时执行：

```sql
SELECT *
FROM app_ops.outsource_snapshot_reconciliation_worklist
WHERE verified_snapshot_quantity IS NULL
ORDER BY outsource_created_at, outsource_order_id, order_item_sequence;
```

由业务负责人依据原始外协单、聊天/纸质记录或同期审计材料逐款确认后，显式写入证据；
`current_quantity` **只能辅助比对，不能当历史证据**：

```sql
INSERT INTO app_ops.outsource_snapshot_reconciliation (
  outsource_order_id, order_item_id, quantity, verified_by, verification_note
) VALUES (
  '<外协单ID>', '<款式ID>', <创建时数量>, '<核对人>', '<证据编号或说明>'
)
ON CONFLICT (outsource_order_id, order_item_id) DO UPDATE
SET quantity = EXCLUDED.quantity,
    verified_by = EXCLUDED.verified_by,
    verification_note = EXCLUDED.verification_note,
    verified_at = clock_timestamp();
```

每张旧单必须覆盖其 `orderItemIds` 的全部且仅有款式；原 `totalQty` 非空时，逐款合计必须与它相等。
完成后让 Prisma 重试已回滚的原子迁移，**不能**把它直接标记为 applied：

```bash
pnpm exec prisma migrate resolve --rolled-back 20260822110000_write_path_integrity
pnpm exec prisma migrate deploy
pnpm exec prisma migrate status
```

验收：最终实际快照逐单逐款与证据表一致，且 worklist 不再有空证据：

```sql
SELECT count(*) AS unresolved
FROM app_ops.outsource_snapshot_reconciliation_worklist
WHERE verified_snapshot_quantity IS NULL;

SELECT count(*) AS mismatch
FROM "OutsourceOrderItemSnapshot" snapshot
FULL JOIN app_ops.outsource_snapshot_reconciliation evidence
  ON evidence.outsource_order_id = snapshot."outsourceOrderId"
 AND evidence.order_item_id = snapshot."orderItemId"
WHERE snapshot.quantity IS DISTINCT FROM evidence.quantity;
```

两项都必须为 `0`。空白新库不含历史外协单，会直接通过。

## 🟠 一、外协完工闸口：部署前必须先跑两段只读 SQL

本批把工单完工闸口从「有外协单且全部已收货」收紧为「**每个含外协工艺的款式**都被至少一张本工单未取消的外协单覆盖」（决策见 `DECISIONS.md` 2026-08-21）。

**上线拆两步，顺序不能反**：

| 步 | 内容 | 前置 |
|---|---|---|
| 2a | 读路径 + 工单详情页「暂不能完工」横幅（`lib/outsource/coverage.ts`、`lib/order.ts`、`app/(admin)/orders/[id]/page.tsx`） | 无。**零行为变更**，闸口还没改 |
| 2b | 闸口收紧（`lib/production-completion.ts` + 五个调用点 + notice 链路） | **查询 1 列出的存量缺口全部补完之后**才能上 |

先上 2a，让主管照着详情页横幅把存量缺口补完；**2b 才是「部署当天可能一批在产工单突然完不了工」的那一步**。

两段 SQL 都是**只读、可反复跑**的，直接在 Pigsty 管的 PG 上执行。

> ⚠️ **先跑这段"底数核对"，再看查询 1 的结果。**
>
> 查询 1 返回 0 行有两种完全不同的含义：真的没有缺口，或者**谓词根本没匹配到任何东西**
> （例如这批数据里压根没有款式用到外协工艺）。两者在结果上长得一模一样。
> 2026-08-21 在开发库上实测就是后者——6 个外协工艺、1 张有效外协单，但"应外协款式数 = 0"，
> 所以那次执行只证明了 SQL 语法可用，**没有证明判定逻辑对**。
>
> ```sql
> SELECT (SELECT count(*) FROM "Craft" WHERE "isOutsource")            AS 外协工艺数,
>        (SELECT count(*) FROM "OrderItem" oi
>          WHERE EXISTS (SELECT 1 FROM "Craft" c
>                         WHERE c."isOutsource" AND c.id = ANY(oi.crafts))) AS 应外协款式数,
>        (SELECT count(*) FROM "OutsourceOrder"
>          WHERE "orderId" IS NOT NULL AND status <> 'CANCELLED')      AS 有效外协单数,
>        (SELECT count(*) FROM "Order" WHERE "requiresOutsource")      AS 标记需外协的工单数,
>        (SELECT count(*) FROM "Order"
>          WHERE status IN ('SCHEDULING','IN_PRODUCTION'))             AS 在产工单数;
> ```
>
> **怎么读**：
> - `应外协款式数 = 0` → 查询 1 的 0 行**没有信息量**，别当作"已确认无缺口"。
>   先确认生产库里确实有款式挂了外协工艺；没有的话说明外协是用别的方式录的，
>   闸口的前提不成立，**先别上 2b**，回来找我。
> - `标记需外协的工单数 = 0` → 闸口（`outsourceCoverageApplies` 只在 `requiresOutsource=true` 时生效）
>   在存量数据上一次都不会触发，2b 上线是安全的；但也意味着它只对**上线后新排产**的工单起作用。
> - 两个数都 > 0 且查询 1 返回 0 行 → 这才是真正的"无缺口"，可以放心上 2b。

### 查询 1：闸口上线后会被卡住的在产工单

`newly_blocked` 的口径是「**今天的闸口已经放行**（内部任务全完 + 有未取消外协单 + 全部已收货），只有新闸口会拦」——这才是「本次新增卡住」的真实数量。补法很简单：给缺口款式补一张外协单并标记收货即可，**不需要改库、不需要回滚**。

```sql
WITH outsource_craft AS (
  SELECT id FROM "Craft" WHERE "isOutsource" = TRUE
),
required_item AS (            -- 应外协款式
  SELECT oi."orderId", oi.id AS item_id, oi.sequence, oi.name
  FROM "OrderItem" oi
  WHERE EXISTS (
    SELECT 1 FROM outsource_craft oc WHERE oc.id = ANY (oi.crafts)
  )
),
covered_item AS (             -- 已被本工单未取消外协单覆盖的款式
  SELECT DISTINCT oo."orderId", unnest(oo."orderItemIds") AS item_id
  FROM "OutsourceOrder" oo
  WHERE oo."orderId" IS NOT NULL
    AND oo.status <> 'CANCELLED'
)
SELECT
  o."orderNo",
  o.status,
  o."customName",
  count(*) AS uncovered_item_count,
  string_agg(ri.sequence || '#' || ri.name, '、' ORDER BY ri.sequence)
    AS uncovered_items,
  (SELECT count(*) FROM "OutsourceOrder" x
    WHERE x."orderId" = o.id AND x.status <> 'CANCELLED')
    AS live_outsource_count,
  (SELECT count(*) FROM "OutsourceOrder" x
    WHERE x."orderId" = o.id AND x.status NOT IN ('CANCELLED', 'RECEIVED'))
    AS unreceived_count,
  -- 内部任务是否已经全部做完（闸口的第一道早退条件）
  NOT EXISTS (
    SELECT 1 FROM "ProductionTask" pt
    JOIN "OrderItem" poi ON poi.id = pt."orderItemId"
    WHERE poi."orderId" = o.id
      AND pt.status NOT IN ('CANCELLED', 'COMPLETED')
  ) AS internal_ready,
  -- newly_blocked：今天的闸口已经放行（内部全完 + 有外协单 + 全部收货），
  -- 只有新闸口会拦的那批。
  (
    NOT EXISTS (
      SELECT 1 FROM "ProductionTask" pt
      JOIN "OrderItem" poi ON poi.id = pt."orderItemId"
      WHERE poi."orderId" = o.id
        AND pt.status NOT IN ('CANCELLED', 'COMPLETED')
    )
    AND (SELECT count(*) FROM "OutsourceOrder" x
          WHERE x."orderId" = o.id AND x.status <> 'CANCELLED') > 0
    AND (SELECT count(*) FROM "OutsourceOrder" x
          WHERE x."orderId" = o.id
            AND x.status NOT IN ('CANCELLED','RECEIVED')) = 0
  ) AS newly_blocked
FROM "Order" o
JOIN required_item ri ON ri."orderId" = o.id
LEFT JOIN covered_item ci
       ON ci."orderId" = o.id AND ci.item_id = ri.item_id
WHERE o.status IN ('SCHEDULING', 'IN_PRODUCTION')
  AND o."requiresOutsource" = TRUE
  AND ci.item_id IS NULL
GROUP BY o.id, o."orderNo", o.status, o."customName"
ORDER BY newly_blocked DESC, o."orderNo";
```

只要一个数字（把上面整段原样嵌进子查询）：

```sql
SELECT count(*) FROM ( /* 上面整段 */ ) t WHERE t.newly_blocked;
```

**验收标准：这个数为 0 之前，不要上 2b。**

### 查询 2：`requiresOutsource` 快照漂移

**这批是「横幅会误报」而不是「会被卡住」，必须单独成表交给业主，别和查询 1 混在一起报**——查询 1 带 `AND o."requiresOutsource" = TRUE`，恰好把这批全部过滤掉了。

成因：`requiresOutsource` 是排产那一刻的快照且没有重算路径（`scheduleOrder` 对已排产工单必抛），而 `updateCraft` 允许把 `isOutsource` 从 false 翻成 true。本批已让闸口和横幅共用 `outsourceCoverageApplies`，所以两边一致；这条查询是给业主看**数据和快照对不上的存量**。

```sql
SELECT o."orderNo", o.status, o."requiresOutsource",
       EXISTS (
         SELECT 1 FROM "OrderItem" oi
         WHERE oi."orderId" = o.id
           AND EXISTS (SELECT 1 FROM "Craft" c
                       WHERE c."isOutsource" = TRUE AND c.id = ANY (oi.crafts))
       ) AS items_actually_need_outsource
FROM "Order" o
WHERE o.status IN ('SCHEDULING', 'IN_PRODUCTION')
  AND o."requiresOutsource" <> EXISTS (
        SELECT 1 FROM "OrderItem" oi
        WHERE oi."orderId" = o.id
          AND EXISTS (SELECT 1 FROM "Craft" c
                      WHERE c."isOutsource" = TRUE AND c.id = ANY (oi.crafts))
      )
ORDER BY o."orderNo";
```

## 🟠 二、通知幂等唯一索引：migrate 之后必须人工验收

本批新增两个 migration：

| migration | 内容 |
|---|---|
| `20260821120000_notification_log_delivery_key` | `NotificationLog` 加 `deliveryKey TEXT`（可空、无默认，历史行留 NULL，纯加列不重写表） |
| `20260821120100_notification_log_delivery_key_unique` | `CREATE UNIQUE INDEX CONCURRENTLY "NotificationLog_deliveryKey_channelId_key"` |

`migrate deploy` 之后**必须**执行下面这条只读验收：

```sql
SELECT indisvalid FROM pg_index
 WHERE indexrelid = '"NotificationLog_deliveryKey_channelId_key"'::regclass;
```

**必须为 `t`。**

为什么单独拎出来验：CONCURRENTLY 建索引中途失败（死锁 / 连接断开 / 迁移被 Ctrl-C）会在库里留下 `indisvalid = false` 的 INVALID 索引，而 **PostgreSQL 不会拿 INVALID 索引当 `ON CONFLICT` 的 arbiter** —— `notify` 的 upsert 会每次进 catch、幂等凭证全丢、重试对所有群**重复推送**。这跟仓库里其它「失败只是少个优化」的 CONCURRENTLY 索引不同，**这一条是正确性依赖**。migration 文件本身已写成「先 `DROP IF EXISTS` 再 `CREATE`、刻意不带 `IF NOT EXISTS`」，重跑能自愈，但需要人确认它确实跑成了。

> 发布前既有的「无效并发索引为 0」检查（`docs/部署指南.md` §14）同样能捕获它；本条是给这一个索引加的定点复核。

## 🟡 三、单向门与知情项

| # | 事项 | 说明 |
|---|---|---|
| 1 | **`ProductionTask.remark` 的写入格式变成对外契约** | 这是这一列全仓第一个写入方。格式固定为 `[超计划报工] YYYY-MM-DD 计划 N / 合计 M（合格 a / 不良 b / 返工 c），报工人 <id>，已勾选确认`，多次写入以 `\n` **追加**（不覆盖）。老板看板「超计划报工」表的「明细」列**原样渲染这个字符串**，改格式要当成改对外契约 |
| 2 | **`OrderLog.action` 新增 `'TASK_OVER_REPORT'`** | `action` 是 String 不是枚举，**无 DDL**，但工单时间线会多出这类条目。同批顺手补上既有缺口 `TASK_REASSIGN` 的中文标签（代码一直在写它、标签表里一直没有），以及 `FIELD_LABELS` 的 `completedQty` / `defectQty` / `reworkQty` |
| 3 | **盘点页部署瞬间 fail-closed** | 浏览器里开着**旧版**盘点页的操作员，提交会因缺 `bookQuantity` 被判 invalid，提示「缺少账面数快照，请刷新页面后重新盘点」。这是刻意的；刷新即可，**但已录入的数据会丢**（`counts` 是纯 `useState`）。**建议低峰期发布，或先口头通知盘点岗** |
| 4 | **盘点改为部分过账** | 一次提交现在可能只过账一部分行，`InventoryCount` 单据上只有被接受的那些，冲突行原样退回要求重数。**需业主点头**（风险低：盘点行本来就是逐 (物料, 库位) 独立的） |
| 5 | **师傅超报要多一次提交往返** | 零 JS 下是整页 POST + 重渲染，弱网车间的师傅会感知到延迟。**这是拍板方案的固有成本，不是实现缺陷**，上线前跟业主对一次预期 |
| 6 | **首页「24 小时推送失败」告警条的计数语义变了** | durable 路径的**瞬时**投递失败现在写 `RETRYING` 而不是 `FAILED`：抖动不再点红，重试成功还会把历史 `FAILED` 行**就地翻成 `SUCCESS`**。上线前告知业主，别让人以为数据丢了 |
| 7 | **`/api/health/jobs` 的通知类死信不再 503** | `jobs` 对象新增 `deadNotificationLast24h`（只加不减），通知类死信只让该端点返回 200 `degraded`，新告警码 `dead-notification-jobs-last-24h`。`/api/health/ready` 的状态码语义**完全不变**。相应地「死信 30 分钟响应」SLO 的采样点只覆盖非通知类死信，通知投递失败改看 `/owner/notifications` 与首页告警条（见 `docs/production-slo-and-recovery.md`） |

## 🔮 六、未来实施时的前置项（OSS 直传重放加固，**本批不做**）

「临时 key + 服务端 copy」本批**没有实施**，现有缓解是 STS session policy 收窄到单 objectKey + 15 分钟过期（决策与两个必踩陷阱见 `DECISIONS.md` 2026-08-21）。真要做时，下面四条**全部是阻塞项，且顺序不能反**：

| # | 事项 | 不做的后果 |
|---|---|---|
| 1 | RAM 子账号加 `upload-tmp/*` 的 `oss:GetObject`（HEAD + copy 源）与 `oss:DeleteObject`（清理） | 每一次设计图上传都停在 HEAD 403 |
| 2 | RAM 子账号加 `design/*` 的 `oss:PutObject`（copy 目标） | copy 403，提示「文件转存失败」 |
| 3 | bucket 加 `upload-tmp/` 前缀的生命周期规则（1 天后过期 + 1 天后中止未完成分片） | 不影响功能，但临时对象**无限堆积**，且没有任何告警会提醒 |
| 4 | **RAM / 生命周期必须先于代码上线** | 顺序反了 = 全员上传失败 |

> ⚠️ **`design/` 前缀永远不能挂生命周期规则** —— 它是业务数据。将来有人为了清孤儿顺手挂上去，就是删设计图。

同时记两条**本批不解决的既有 P1**，不要顺手塞进 OSS 那一批：

- 删设计图只删 DB 行，OSS `design/` 对象永久留存。生命周期规则表达不了「只删无引用对象」，只能靠对账 sweeper，单开 backlog。
- 盘点的「净额为零的往返」（先出 20 再进 20，余额回到原值）CAS 检测不到。堵这个口需要逐行 `snapshotAt` + `MaterialTransaction` 复合索引 + ledger scan，已拆出单独设计评审。**别把它当 bug 顺手改回时间戳基线**（那个设计被否的四条理由见 `DECISIONS.md` 2026-08-21）。
