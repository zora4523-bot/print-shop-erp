# 外部销售前端全流程审查（2026-09-12）

审查基线：`ebaeff9`。本轮审查代码、浏览器操作和实际响应，未修改业务实现。
结论：确认 8 项问题/功能缺口，其中 4 项 P1、4 项 P2。此前修复的入口、状态、多地址等功能通过本轮回归，不能据此认为所有流程已经完整。

## 发现与优先级

### 1. P1：建单页把全局客户资料发送给外部销售浏览器

- 证据：[建单页](../../app/(admin)/orders/new/page.tsx) 无条件调用 `listCustomerPartyOptions`，并把结果传给客户端 `OrderForm`。[客户查询](../../lib/party.ts) 返回所有有效 CUSTOMER/BOTH 客户的 ID、名称、收货人、电话和地址，没有销售归属过滤。
- [表单](../../components/business/order/OrderForm.tsx) 通过 `usesExternalSalesPricing` 隐藏客户选择器，但没有阻止这些数据进入页面响应。[编辑页](../../app/(admin)/orders/[id]/edit/page.tsx) 对非管理员也调用相同的全局选项查询。
- 实际验证：以专用外部销售登录，建单响应中匹配到当前有效客户的 ID 和非空联系电话；页面没有客户选择器。报告不记录客户原文或联系方式。
- 影响：隐藏控件没有形成数据访问边界，销售可从响应读取页面操作不需要的客户主数据。
- 验收：外部销售建单不查询、不传递无用客户集合；编辑页仅返回明确授权且必要的数据。使用两个不同归属客户测试 HTML/RSC 响应，不只断言控件不可见。

### 2. P1：编辑页绕过销售详情的数据白名单

- 证据：[编辑页](../../app/(admin)/orders/[id]/edit/page.tsx) 使用通用 `getOrderDetail`，再渲染 `OrderSavedConfiguration`。[通用查询](../../lib/order.ts) 对销售仍返回款式人工报价原因、改价说明、收费项改价原因等；[配置展示](../../components/business/order/OrderSavedConfiguration.tsx) 直接显示这些字段及制版备注。
- 与之相对，[销售详情投影](../../lib/order/sales-detail-query.ts) 排除了上述内部说明。
- 实际验证：同一测试工单的收费说明哨兵“测试历史约定收费”在完整详情中不可见，在 `/edit` 页面中可见。工单归属检查有效，但不能代替字段级限制。
- 影响：同一销售通过两个入口看到不同范围的信息；详情页的商业信息隔离可被编辑入口绕过。本轮没有发现通用查询向销售返回管理员专属 `costEntries`，不将其描述为全部成本泄露。
- 验收：使用销售专用编辑投影和展示范围；详情、编辑及其响应均不得含内部说明哨兵，同时保留销售应见的应付金额、收费名称、备注和配置。

### 3. P1：我的账单仍连接旧账本，新版月账单无法显示

- 证据：[销售账单列表](../../app/(admin)/sales/bills/page.tsx) 与[详情](../../app/(admin)/sales/bills/[id]/page.tsx) 使用 `listBills` / `getSalesBillDetail`，读取旧 `Bill`。[旧账本写入](../../lib/bill.ts) 已通过 `LEGACY_BILL_READ_ONLY_MESSAGE` 永久关闭。
- [旧管理账单入口](../../app/(admin)/owner/bills/page.tsx) 已转向新版；[新版查询](../../lib/agent-monthly-billing/query.ts) 读取 `AgentMonthlyBill`。销售端没有接入这条链路。
- 影响：管理员新生成的月账单不会因为旧销售页面能打开就自动显示；新账单明细和结算状态无法由该入口查阅。此项在上一轮已记录，当前仍未解决。
- 验收：建立按当前销售 ID 限定的新版账单列表/详情，明确草稿可见性，保留冻结金额及状态；旧账单作为历史入口，不合并计算两套余额。覆盖他人账单拒绝访问、作废/调整、确认/付款状态及金额精度。不能直接暴露管理员查询结果。
- 证据等级：调用链确认；未生成或支付真实财务账单。

### 4. P1：驳回工单没有重新提交入口

- 证据：[销售详情](../../components/business/order/SalesOrderDetailView.tsx) 只在 DRAFT 渲染提交按钮；编辑页没有重新提交操作。[状态机](../../lib/order/status-machine.ts) 允许 REJECTED → PENDING_FACTORY，[提交领域入口](../../lib/order.ts) 存在对应能力，但保存普通字段不会自动重新提交。
- 实际验证：草稿详情有提交按钮；REJECTED 测试单没有提交按钮，编辑保存入口也无法完成重新提交。
- 影响：提示销售“修改后重新提交”，但实际无法在销售前端走完流程，需要管理人员介入。
- 验收：提供明确的补正后重提入口，重新确认报价，并保留所有权、当前版本、待审核申请及状态检查；覆盖退回 → 修改 → 重提 → 工厂重新可处理的完整流程。

### 5. P2：驳回、暂停的具体原因没有传给销售

- 证据：[工厂工作流](../../lib/order/admin-workflow.ts) 把 `reasonCode`、`reasonNote`、`affectedFigs` 写入 `OrderWorkflowDecision`；[管理工作台](../../lib/order/admin-workspace.ts) 读取并展示。
- [销售详情](../../lib/order/sales-detail-query.ts) 和[销售列表](../../lib/order/sales-list-query.ts) 未查询这一关系。销售看到的变更申请审核记录是 `OrderChangeRequest`，不能替代工厂驳回或暂停记录。
- 影响：销售能看到状态和通用提示，却不知道哪款、因为什么被驳回或暂停，无法据此补正。“查看原因”指向详情也无法补足数据。
- 验收：返回当前适用决定的销售可见原因、说明、受影响款号和时间；保留内部日志隔离。覆盖驳回、暂停、恢复及再次驳回，避免显示已失效的旧原因。
- 证据等级：写入—读取—展示调用链确认；本轮未操作真实工单生成新的工厂决定。

### 6. P2：驳回后无法补交或替换错误图稿

- 证据：[图稿领域入口](../../lib/order-design.ts) 明确只允许 DRAFT 增删文件；销售详情和编辑页遵循同一限制。[修改申请表单](../../components/business/order/OrderChangeRequestForm.tsx) 不包含图稿替换能力。
- 实际验证：DRAFT 有上传控件，REJECTED 没有。此项是已有设计限制与驳回补正需求之间的功能缺口，不是本次列表改动引入的回归。
- 影响：即使补上重新提交按钮，因图稿错误被驳回的订单仍无法完成纠正。
- 验收：定义有版本记录的补图/换图流程，保留旧图稿和审批依据，校验所有权、版本、状态及并发。不能只删除 DRAFT 限制，否则会改变已确认生产资料而没有对应记录。

### 7. P2：早期订单缺少销售取消入口，暂停订单也不能申请取消

- 证据：[销售详情](../../components/business/order/SalesOrderDetailView.tsx) 与[取消申请领域](../../lib/order/change-request.ts) 仅支持 CONFIRMED / RELEASED / FOILING / PACKING 申请取消。
- [直接取消 action](../../actions/order.ts) 要求 `order:cancel`，[权限字典](../../lib/auth/permissions-dict.ts) 将其限制为 ADMIN。DRAFT / PENDING_FACTORY / REJECTED 的销售没有对应入口；ON_HOLD 也不属于取消申请窗口。
- 实际验证：上述早期状态及 ON_HOLD 详情均无取消按钮。[变更规则](../工单变更与版本规则.md) 的早期直接取消/撤回矩阵与销售实际能力不一致。
- 影响：误建草稿、待工厂处理或已退回订单无法由销售结束；暂停单需先由管理员处理状态才能进入现有申请路径。
- 验收：明确销售可直接取消与必须工厂审批的状态，提供所有权限定、版本检查及审计完整的入口；不能简单把管理员取消权限开放给所有销售。暂停状态的取消规则需要明确是否涉及已生产费用。

### 8. P2：已有包装组的工单仍提供必定失败的“增加款式”操作

- 证据：[修改申请表单](../../components/business/order/OrderChangeRequestForm.tsx) 在 `hasItems` 时显示“本次申请需要新增一款”，未按包装组限制。
- [申请领域](../../lib/order/change-request.ts) 的创建路径调用 `assertPackagingChangeRequestSupported`；当有包装组且包含 ADD 操作时，明确拒绝：“当前工单已有包装组；新增款式必须同时指定每袋组成，当前修改申请暂不支持”。
- 影响：销售填完新增款式后才被拒绝；后端保护包装一致性是必要的，缺失的是前端能力匹配和分袋组成输入。
- 验收：短期按真实能力隐藏/禁用入口并给出简短原因；完整支持需同时提交新增款式、包装组成和分货信息，重新计价并审批。覆盖有/无包装组、混装、每袋数量及多地址分货守恒。
- 证据等级：前端入口与提交校验调用链确认，未创建真实修改申请演示失败。

## 建议修复顺序

1. 收紧建单/编辑数据投影，修复问题1、2，补响应级隔离测试。
2. 完成驳回原因、图稿补正、重新提交闭环（问题4、5、6），避免仅加一个按钮后继续卡住。
3. 接通销售新版账单（问题3），独立验证所有权和冻结金额。
4. 明确早期/暂停取消规则，并让新增款式入口与包装能力一致（问题7、8）。

本报告只提交审查结论，没有实现上述8项修复；本轮通过的测试说明既有覆盖场景正常，不代表这些缺口不存在。
