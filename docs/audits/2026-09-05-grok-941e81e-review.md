## 确认的问题

### 1. [P1] 发货后更改顺丰到付会卡住重新核价和结算

归属：分支前序提交 `165df27`，不是最新 `941e81e` 单独引入。

定位：[lib/order/pricing-review.ts:335–339](https://github.com/zora4523-bot/print-shop-erp/blob/941e81eddf0044dec2bc62a15e34a0c97742dc8e/lib/order/pricing-review.ts#L335)。

触发条件：管理员对已经 `SHIPPED` 的外部销售工单，更改顺丰到付标识，且该更正通过现有费用校验。

证据链：

1. `lib/order/editable-fields.ts:88–93` 与 `lib/order.ts:3323–3338` 明确允许管理员执行该操作；详情页也保留入口。
2. `lib/order.ts:3644–3683` 保留 `SHIPPED`，清空 `confirmedFee`，追加 `PENDING_ADMIN_CONFIRMATION` 价格修订。
3. 新增 `isOrderPricingReviewAllowedStatus` 只允许 `PENDING_FACTORY/SUBMITTED`；预览与提交核价都被拒绝，UI 同时隐藏核价表单。
4. `lib/order/admin-workflow.ts:852–864` 的结算命令又要求 `SHIPPED` 且 `confirmedFee !== null`，因此无法继续结算。

反证核查：工厂确认入口同样只允许待确认状态；商业明细编辑在价格待确认时保留 `confirmedFee=null`；不能通过这些入口恢复。基线核价仅拒绝免费、已完成和已取消工单，允许 `SHIPPED` 重新核价，故这是新增状态限制与既有更正流程之间的回归。

测试缺口：单元测试分别证明“发货后更正到付清空确认费”和“SHIPPED 不允许核价”，但未串联验证更正后的核价、结算闭环。

修复方向：增加受限的履约费用更正/重新确认流程，或在已发货更正时完成专门的终审快照；保留管理员权限、价格版本与结算锁定约束，不应简单移除全部状态限制。

### 2. [P2] 管理路由把可恢复的 Bot 身份错配变成永久通知失败

归属：最新提交 `941e81e`。

定位：[lib/notification/notify.ts:864–865](https://github.com/zora4523-bot/print-shop-erp/blob/941e81eddf0044dec2bc62a15e34a0c97742dc8e/lib/notification/notify.ts#L864)，关联 `754–761`。

触发条件：启用且完整绑定的智能机器人管理通道已有待处理通知；执行 worker 暂时缺少原 Bot ID，或使用与绑定身份不符的 Bot ID。路由本身仍启用，通道并未停用或删除。

证据链：

1. `channelConfigurationFailure`（`notify.ts:231–242`）把身份错配识别为 `retryable:true`，明确允许恢复原 Bot ID 后再尝试。
2. 管理路由把任何配置错误都计入 `managementRouteBlocked`，随后 `!managementRouteBlocked` 强制把重试资格变成 false。
3. 通道账本被写为单调终态 `FAILED`；`lib/background-jobs/notification.ts:157–182` 正常返回，任务进入 `SUCCEEDED`。
4. 恢复原配置不会重新投递：账本只允许 `RETRYING` 重领；人工 UNKNOWN 处置不适用于 FAILED，已成功任务也没有普通重试入口。混合路由里的健康 Webhook 通道同样可能被永久跳过。

前置门禁不能排除触发：worker 不以 Bot 身份健康作为领取任务条件；缺失凭据或鉴权失败时仍继续 LIGHT 工作。发布脚本先启动 worker 再检查门禁，单独重启 worker 也不会自动运行发布门禁。健康接口能告警，但不会阻止消费。

涉及五类管理事件：`ORDER_SUBMITTED`、`ORDER_CHANGE_REQUESTED`、`PRODUCTION_PROGRESS_ANOMALY`、`PRODUCTION_STAGNANT`、`PENDING_FACTORY_BACKLOG`。

测试缺口：身份恢复测试使用非管理事件 `URGENT_ORDER`；管理路由测试覆盖停用/缺失通道，未覆盖“active + 完整绑定 + 临时身份错配”的交叉情形。

修复方向：继续整条路由暂停发送，禁止把旧目标交给新机器人；但当阻塞仅由可恢复身份问题造成时，应保留安全的重试资格。通道停用、删除等永久性原因仍须单独处理。

优先级说明：Grok 专项复核给出 P1；最终按“需要配置异常触发”的前提收敛为 P2，缺陷成立的结论不变。

### 3. [P2] 保留既有规则时漏修迁移写入的四项默认模板换行

归属：分支前序提交 `df812c9`，不是最新 `941e81e` 单独引入。

定位：[prisma/seed.ts:456–464](https://github.com/zora4523-bot/print-shop-erp/blob/941e81eddf0044dec2bc62a15e34a0c97742dc8e/prisma/seed.ts#L456)。

触发条件：全新安装执行全部迁移，再运行 seed。

证据链：

1. 旧迁移 `20260902120000_admin_order_workflow_billing_foundations/migration.sql:1038–1062` 用普通 PostgreSQL 字符串创建四项规则，文本包含字面量反斜线 `\n`。
2. 在默认 `standard_conforming_strings=on` 下，这不是换行。只读 SQL 常量检查结果：普通字符串 `length('a\nb')=4`，转义字符串 `length(E'a\nb')=3`。
3. 基线 seed 的 `upsert.update.messageTemplate` 会把这四项覆盖为 TypeScript 字符串中的真实换行。本分支改成 `createMany(skipDuplicates:true)`，迁移已创建的四行被跳过。
4. 后续模板迁移只处理 `ORDER_SCHEDULED/ORDER_COMPLETED`；运行时无默认模板修复，`renderTemplate` 只替换占位符。默认通知因而持续显示字面量 `\n`。

全新安装确定涉及四项：`ORDER_CHANGE_REQUESTED`、`PRODUCTION_PROGRESS_ANOMALY`、`PRODUCTION_STAGNANT`、`PENDING_FACTORY_BACKLOG`。不要把 `ORDER_SUBMITTED` 也算成全新安装必然受影响的第五项。

新增性说明：旧 SQL 文件与 main 的 blob 相同，旧 SQL 本身不是本分支新增缺陷；回归是 seed 不再纠正它们。保护自定义模板的改动合理，不能通过恢复全量覆盖来修复。

修复方向：新增精确匹配这四项错误默认文本的纠正迁移，将其改为真实换行，保留管理员自定义模板；补充 migrate → seed → render 的默认值测试。

### 4. [P2] 发布门禁超时短于残留心跳窗口，把 worker 自愈升级为整站停机

归属：最新提交 `941e81e`。

定位：[deploy/update.sh:91–94](https://github.com/zora4523-bot/print-shop-erp/blob/941e81eddf0044dec2bc62a15e34a0c97742dc8e/deploy/update.sh#L91)。

触发条件：启用智能机器人通知目标，使用默认门禁时长；新 LIGHT worker 在发布第 8 步启动后、门禁通过前非优雅退出（例如进程崩溃或 SIGKILL），随后由 PM2 自动重启并恢复连接。正常优雅退出会删除心跳，不属于本问题。

证据链：

1. `deploy/ecosystem.config.cjs:26–29` 明确开启自动重启；`scripts/background-worker-runtime.ts:46` 的 worker ID 包含 PID，新进程使用不同的心跳行。
2. `lib/background-jobs/heartbeat.ts:82–93` 只在正常关闭回调删除自己的行；非优雅退出留下旧行，启动清理只删除七天前记录（`53–57`）。
3. `heartbeat-policy.ts:10–11` 的活跃窗口为 180 秒；`health.ts:291–297` 要求活跃 LIGHT 行恰好为一条才判定机器人可用。旧进程虽已死亡，其新鲜心跳仍造成双实例误判。
4. 发布门禁默认只等 120 秒，且需要额外 6 秒稳定连接；因此在门禁期间产生的新鲜残留心跳不会及时过期。新进程即使已连接，门禁仍持续等待。若汇总状态为 CONNECTED，则输出 `WAITING_CONNECTED`；旧行保留 CONNECTING 状态时也可能输出 `WAITING_CONNECTING`。
5. 超时后 `update.sh:34–38` 的失败处理停止 Web、LIGHT、HEAVY。原本已经自动恢复的 worker 故障因此扩大为需要人工恢复的整站停机。

反证核查：`health.ts:405–409` 的 readiness 判断不会因为重复 LIGHT 心跳而提前排除此路径；PM2 的正常优雅停止会删除旧心跳，因此不能推导为“每次发布必然失败”。旧 worker 在发布停机阶段被强杀也可能触发，但还取决于迁移等后续步骤是否耗尽其心跳剩余窗口。

验证：向真实 `scripts/deploy-jobs-gate.mjs --status-only` 输入 `required=true`、`configurationValid=true`、`identityMatch=true`、`status=CONNECTED`、`operational=false`，返回 `WAITING_CONNECTED`。这验证了门禁分支，不等同于实际部署故障注入测试。

修复方向：在保留真实双 worker 冲突检测的前提下，协调心跳过期时间与门禁观察期，预留心跳刷新和稳定观察时间；或通过可靠的进程/租约归属证明清理已死亡实例。不能简单忽略双实例、批量删除心跳或移除发布失败保护。补充“崩溃 → 新 PID 重启 → 旧心跳过期 → 门禁恢复”的时间序列测试。

优先级说明：Grok 主审给出 P1；最终按“启用机器人且发布期间发生非优雅退出”的限定前提收敛为 P2，但其触发后的停机影响需要在上线前修复。
