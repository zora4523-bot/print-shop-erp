## 3. 任务 R1：数量审批与改版、取消形成闭环

覆盖 F2、F3。先修这一项，防止继续产生无法审批的工资记录。

### 3.1 固定处理顺序

采取“先核定已申报生产，再批准改版或取消”的策略：

| 场景 | 处理方式 |
| --- | --- |
| 正常生产，数量申请待审 | 管理员核对申请数量、原生产人、实际工作日后处理 |
| 工单修改/取消申请待审，同时有数量申请 | 允许管理员处理现有数量申请；暂停批准改单/取消，给出具体数量申请入口 |
| 工单已暂停 | 禁止师傅新增完工登记；管理员仍可核定暂停前已经提交的数量申请，工单保持暂停 |
| 存量已取消工单仍有数量申请 | 管理员通过受控历史处理入口核定；只登记真实生产及工资，不恢复工单、不重开物流、不发送待发货通知 |
| 存量旧版本申请曾被改版取消 | 不开放普通旧码登记，进入 R5 的历史核对流程 |

不能只给改单增加 REQUESTED 拦截：当前完工服务会因存在工单变更申请而拒绝审批，必须同时拆开“新增登记”和“处理已提交申请”的校验，否则两边会互相等待。

### 3.2 领域写入

- 在生产领域集中管理申请处置与未决数量检查。管理员批准/驳回不能简单复用师傅 COMPLETE 的全部状态限制，也不能把全局版本/状态检查一并删除。
- 批准使用申请中保留的师傅、任务内容、数量和实际工作日，不使用当前操作者、当前工单数量或当天日期代替。工价依据适用的历史规则；缺价返回具体原因，不能填零或偷偷转人工。
- 管理员驳回必须说明申请不成立的依据并保留原申请快照。已确认实际生产、只是数量填错时，应核对修正并保持待审义务；不得用驳回清空实际工作日来释放日结。核定数量变化须再次展示并核对，不能静默用计划量覆盖申请量。
- 活跃工单核定完成后复用现有完成闸口；暂停/已取消的历史处理不自动推进订单、工序或物流状态。恢复暂停工单时按当前生产事实重新评估，不能恢复为与剩余生产不符的“待打包发货”。
- 在改单和取消的预检、最终批准事务中都检查未决数量；最终事务检查是权威依据。新工单取消时，仅未实际生产的 PENDING 任务转 CANCELLED，已完成任务和工资保持历史事实。
- 改版继承不再将 REQUESTED 批量取消。没有未决申请时才允许取消旧版本尚未生产的 PENDING，并生成/承接新任务。
- 数量核定会影响取消已产数量及参考结算价。补齐新 ProductionJob 在取消已产量下限中的消费，沿用现有款式/工种归并规则，不能把同一件的多个工序相加成多件产量。旧预览在核定后必须失效或重新计算，不能沿用过期 token 批准取消。
- 保存工单状态前后值、任务修订、申请前后值和操作者审计；涉及状态变更通过领域状态机。旧页面提交使用版本或事实指纹检测冲突。

### 3.3 事务、日结与恢复约束

- 申请处置、改单、取消共用工单锁，事务内重读；涉及取消对客结算时保留原结算 cutoff 锁的优先级，不为了新逻辑反转锁序。
- 工资路径继续遵循身份锁、工价共享锁、日期闸口、人员日锁的相对顺序。批准、驳回和修正数量都必须与该人员原工作日的日结串行；重复请求不得重复计产或计薪。
- 日结继续阻止真实未决数量和待补价；不得按“工单已取消”或“旧版本”过滤掉工资义务。任何新增历史待核对状态也必须被应用与数据库相同口径检查。
- 若新增状态/约束或替换 SQL 守卫，只能追加前向迁移；检查工单、任务、工资、触发器和直接 SQL 消费方，不能只修应用层查询。
- 存量取消工单批准历史产量后，既有对客取消结算不得静默重算；记录差异供有权人员按原财务流程处理，生产工资与客户应收分别留痕。

验收：待审数量遇到改单、取消、暂停均有可达的处理入口；原工作日和工资不丢；数量处置与日结并发只有一个合法结果；旧预览和旧页面不能越过新事实。

## 4. 任务 R2：重做单从真实入口进入正确生产流程

覆盖 F1，同时处理重做单二次物化风险。

1. 明确区分新模式源单与历史模式源单。新模式关联重做经已有受控确认/下发流程进入 RELEASED，再继承生产归属、创建必要打印待办；保留重做资格、原单交付、免费重做/收费和工艺预检。
2. 不能仅给真实创建入口加 `targetStatus: RELEASED`：当前入口创建 SUBMITTED，状态机并不允许 SUBMITTED 直接到 RELEASED。应在事务中走受控的确认/下发转换，不能裸写状态，也不能全局改掉历史物化的默认值。
3. 首次关联重做从源单的来源款式继承归属；重做单自身改版只从自己的历史生产承接。两个继承路径互斥，避免同版本同来源键重复创建。
4. 幂等重放必须核对已有任务的订单、版本、来源、归属和生产性质；不可仅用“已存在就跳过”掩盖错误承接。不能唯一确认原归属的新增任务仍由管理员安排，已有真实产出不换人。
5. 重做自身只改文字：已完成量承接，不生成重复工资；确实补做/增量：仅新增真实剩余生产，使用 R3 的计价来源。暂停中的重做改版保持暂停，恢复后根据当前任务与外协事实决定生产状态。
6. 新旧模式扫码、打印、师傅列表、管理员补登和外部销售状态读取一致；历史模式订单不自动转账本。源单发货和已结算工资不变。
7. 明确零内部生产任务的分支：仅重打包不要求再选生产师傅或补造生产工资；纯外协仍等待必需外协验收，不能因为没有内部任务就提前发货。缺少可确认归属时给管理员现有排单入口，不能把整张重做单藏掉。
8. 源单归属可确定但账号已停用时，历史归属仍保留；师傅账号不能继续扫码，管理员可按实际工作日及雇佣范围补登记。新工艺/新任务的安排仍校验工种资格，不能以“重做继承”为由绕过授权。

| 已完成任务仅改文字，不需要新增生产 | 沿用已产数量，无新增工资 |

- 新任务记录服务端确定的计价原因、来源任务和生产批次依据；优先在现有任务快照中使用有类型和版本的字段。若查询/约束需要独立字段，再补 schema 与前向迁移。不得由表单传入 `manualPricing` 决定。
- 排单和改版继承共用判定函数，删除 `workOrderVersion > 1` 作为人工补价的充分条件。检查同订单、款式及工种的真实生产关系，不能把无关任务的历史套到所有新任务，也不能把未决申请视为“无产出”。
- 保持原正常计件工价、过版次数、颜色、小单费和开机费口径；不得在核定完成时改变既有已计薪记录。
- 存量错误标记按 R5 核对。已有工资、流水或结算的任务不批量改价；待核对记录不能自动当零元或重新自动发一笔钱。

### 5.1 生产承接与计价一起修正

不能只修改 `dispatch.ts` 的版本判断：[revision-jobs](../../lib/production/revision-jobs.ts)目前也把所有继承任务设置为人工补价。两条写入必须使用同一个判断来源。

| 子任务 | 必须覆盖的情形 | 结果 |
| --- | --- | --- |
| R3-a 生产性质 | 未生产的普通单首次下发、已排单未生产后改版、真实增量、物理改版、关联重做 | 分别记录首产/承接/增量/重做依据，由服务端决定计价，不只看版本号 |
| R3-b 完成事实承接 | 1,000 个计划经管理员核定实际 990 完成，之后仅修改交期或名称 | 保留真实 990 与既有工资，仍是已完成；不能伪造 1,000 实际量，也不能自动要求补做 10 个 |
| R3-c 新增生产 | 已产 1,000 → 总量 1,300；一个款式改设计、其余不变；多次改版 | 只为真正新增/需重做的生产建任务；前者为 300 待补价，其余按各款/工种识别，不重复累计沿用记录 |
| R3-d 工价回归 | 局部/专版、过版数、颜色、小单费、开机费、已有非自动计价情形 | 首产保持原工价规则；真实增量不重算原批工资；其他合法人工核价原因不被误删 |

R3-b 是本轮补充验收要求，依据“文字改版不重复计产”；浏览器尚未执行“先批准 990 再改交期”的完整路径，不标为已实测缺陷。当前承接计算直接用新需求量减实际量，需保存并区分“原生产要求已经核定完成”和“实际数量”。仅资料变更沿用完成结论；数量/物理变更后按真实生产依据计算新任务，已核定差额和多款量不清的情形须向管理员展示本次量的依据，不能默默沿用不明合计。

主要改动：[dispatch](../../lib/production/dispatch.ts)、[revision-jobs](../../lib/production/revision-jobs.ts)、[completion-registration](../../lib/production/completion-registration.ts)及相关工资快照类型。

验收：未投产普通单改文字/改数量到 v2 后首次完成仍自动计件；真实完成 1000 后新增 300 保留原工资、仅 300 待补价；重放和改版不重复计薪。

## 6. 任务 R4：让管理员能找到并处理数量申请

覆盖 F5，消费 R1 的同一未决数量口径。

- 在现有工单工作台增加“数量待审批”计数、行标记和筛选入口，展示工单、师傅、申请数量及实际工作日；点击直接定位详情内对应生产任务。详情复用既有核对/审批表单，避免再套泛化确认弹窗。
- 扩展现有 query 解析、序列化、筛选、计数、分页和导出契约。跨页、返回、刷新保留筛选；专门的审批入口不能默认被生产中队列过滤掉暂停、取消或历史待处置记录。统计要明确是工单数还是申请数。
- 日结候选来源取旧报告、生产工资与未决数量的并集。仅有申请、尚无工资的师傅/日期也显示待处理项；不生成假的零元工资。
- 日结拒绝返回结构化阻塞项，包含授权范围内的工单号和跳转。示例文案：“工单 ×× 的生产数量待审批，请先处理”；不能只给出找不到对象的通用报错。
- 页面通过领域查询服务取得 DTO，业务组件不新增数据库查询；避免逐行查询、全量拉取后分页和重复计数。

- 首期以站内待办、筛选和定位完成闭环，不依赖新增外部推送。后续如增加提醒，使用现有事务 outbox 并同步事件、模板、路由、去重和载荷权限测试。

主要改动：[admin-workspace](../../lib/order/admin-workspace.ts)、[query](../../lib/order/admin-workspace-query.ts)、[filters](../../lib/order/admin-workspace-filters.ts)、[piecework-settlement](../../lib/salary/piecework-settlement.ts)、[ProductionJobPanel](../../components/business/production/ProductionJobPanel.tsx)、管理工单与工资页面。

遵循[文案与确认](../ui-规范.md#7-文案与确认)：业务文案不展示内部状态名、表名和机制词；失败给出原因与恢复动作。等待、空态、权限失败、重复提交、处理后消失、键盘焦点和长中文均纳入验收。

## 7. 任务 R5：存量恢复、完整验证和交付

### 7.1 存量处置不能遗漏

| 记录类型 | 恢复策略 |
| --- | --- |
| 新模式 SCHEDULING 重做单，无冲突历史 | 校验原单、归属、任务和打印事实后，通过受控修复命令推进到适用状态；记录审计并支持幂等 |
| 取消/暂停单上的 REQUESTED，原日未结算 | 使用 R1 管理员核定入口保留原日期处理；不恢复取消工单、不重新选生产师傅 |
| 旧版被改版取消的申请 | 保留申请及工资核对义务。核对新版产量、承接和后续工资；没有依赖冲突时才受控恢复审批，不能直接批量把 CANCELLED 改回 REQUESTED |
| 错误人工补价的首次生产任务 | 仅未完成且无工资历史、证据充分的任务可审计修正标记；已完成或有账本的任务按历史计价证据核定，不重写旧金额 |
| 原工作日已结算或后续生产/工资存在冲突 | 输出有具体对象的异常清单，进入单独的受控财务修复任务；保留原日期和原账本，不自动挪日、解锁结算或扣回后续真实生产工资 |

恢复脚本先 dry-run，输出计划与跳过原因，再通过受权入口执行；实际操作前备份并核对目标环境。不能在数据库迁移里猜测产量、师傅或补价。若存在未处理异常，交付必须列出并区分“新增路径已修复”和“存量恢复未完成”。

子任务 R5-a 负责扫描与恢复。清单至少含环境、工单/任务、异常分类、原师傅和工作日、申请量、后续版本依赖、工资/结算引用、拟处置与不可自动处理原因。扫描发现旧 CANCELLED 中仍有未核定真实生产时，须先登记可追踪的核对义务，并按同一口径阻止相关原工作日漏结；只写一份离线报告不算闭环。记录本次恢复批次及预期修订，逐单锁内重读，重复执行不重复计产、计薪或恢复通知。

结构迁移只建立必要字段/索引/约束，不能在迁移中直接猜价、改产量；应用层和现有[数据库数量守卫](../../prisma/migrations/20260928123000_production_history_and_approval_guard/migration.sql)对未决义务保持一致，旧迁移不修改。部署顺序须保证新旧应用交替期间不存在工资守卫空窗；如果无法兼容，应在现有运维方式下暂停相关写入后切换。发生问题优先停止受影响写入并向前修复，禁止删除工资流水或回退已应用迁移。
