## 3. 任务 R1：数量审批与改版、取消形成闭环

### 3.1 固定处理顺序

采取“先核清原任务真实生产，再批准会废弃/重建任务的改版或取消”的策略；已提交申请和已做未登记均在范围内：

| 场景 | 处理方式 |
| --- | --- |
| 正常生产，数量申请待审 | 管理员核对申请数量、原生产人、实际工作日后处理 |
| 工单修改/取消申请待审，同时有数量申请 | 允许管理员处理现有数量申请；暂停批准改单/取消，给出具体数量申请入口 |
| 修改/取消待审，实际已做但任务仍为 PENDING | 管理员在受控入口按原归属与日期补登；预览重新核对后才允许批准，师傅权限不全面放开 |
| 工单已暂停 | 禁止师傅新增完工登记；管理员仍可核定已有申请或核实暂停前漏登记生产，工单保持暂停 |
| 存量已取消工单仍有数量申请 | 管理员通过受控历史处理入口核定；只登记真实生产及工资，不恢复工单、不重开物流、不发送待发货通知 |
| 存量旧版本申请曾被改版取消 | 不开放普通旧码登记，进入 R5 的历史核对流程 |
| 存量已取消/改版，真实生产从未提交申请 | 建立关联原任务的核对记录，经事实、归属、日期及后续依赖验证后受控补登；资料不全保留义务，不能直接跳过 |

不能只给改单增加 REQUESTED 拦截：当前完工服务会因存在工单变更申请而拒绝审批，必须拆开师傅新增登记、管理员事实补登与已提交申请处理的校验，否则两边会互相等待。

### 3.2 领域写入

- 在生产领域集中管理申请处置与未决数量检查。管理员批准/驳回不能简单复用师傅 COMPLETE 的全部状态限制，也不能把全局版本/状态检查一并删除。
- 批准使用申请中保留的师傅、任务内容、数量和实际工作日，不使用当前操作者、当前工单数量或当天日期代替。工价依据适用的历史规则；缺价返回具体原因，不能填零或偷偷转人工。
- 管理员驳回必须说明申请不成立的依据并保留原申请快照。已确认实际生产、只是数量填错时，应核对修正并保持待审义务；不得用驳回清空实际工作日来释放日结。核定数量变化须再次展示并核对，不能静默用计划量覆盖申请量。
- 活跃且没有待审变更的工单核定后复用完成闸口。暂停、取消及待审变更中的受控事实处理不自动推进订单或物流；取消/旧版本工序不重新激活。暂停核定可保存任务完成事实，恢复事务再按当前代次任务核对工序/步骤投影并调用完成闸口，不能因旧工序仍为 PENDING 永远卡住，也不能虚报待发货。
- 在改单和取消的预检、最终批准事务中都检查未决数量和已知未登记生产；最终事务检查是权威依据。取消时仅有明确未生产依据的 PENDING 任务可转 CANCELLED；PENDING 本身不作为未生产证明。已完成任务和工资保持历史事实。
- 改版继承不再将 REQUESTED 批量取消。未决申请、已知漏登记和相关历史核对义务均已处理后，才允许废弃旧版未生产任务并生成/承接新任务；仅资料变化不得绕过仍待核实的原生产事实。
- 数量核定会影响取消已产数量及参考结算价。补齐新 ProductionJob 在取消已产量下限中的消费，沿用现有款式/工种归并规则，不能把同一件的多个工序相加成多件产量。旧预览在核定后必须失效或重新计算，不能沿用过期 token 批准取消。
- 保存工单状态前后值、任务修订、申请前后值和操作者审计；涉及状态变更通过领域状态机。旧页面提交使用版本或事实指纹检测冲突。

### 3.3 事务、日结与恢复约束

- 申请处置、改单、取消共用工单锁，事务内重读；涉及取消对客结算时保留原结算 cutoff 锁的优先级，不为了新逻辑反转锁序。
- 工资路径继续遵循身份锁、工价共享锁、日期闸口、人员日锁的相对顺序。批准、驳回和修正数量都必须与该人员原工作日的日结串行；重复请求不得重复计产或计薪。
- 日结继续阻止真实未决数量和待补价；不得按“工单已取消”或“旧版本”过滤掉工资义务。任何新增历史待核对状态也必须被应用与数据库相同口径检查。
- 若新增状态/约束或替换 SQL 守卫，只能追加前向迁移；检查工单、任务、工资、触发器和直接 SQL 消费方，不能只修应用层查询。
- 存量取消工单批准历史产量后，既有对客取消结算不得静默重算；记录差异供有权人员按原财务流程处理，生产工资与客户应收分别留痕。

验收：待审数量遇到改单、取消、暂停均有可达的处理入口；原工作日和工资不丢；数量处置与日结并发只有一个合法结果；旧预览和旧页面不能越过新事实。

| R1-f | 补齐已做未登记入口与批准前对账 | 管理员按原归属、原日补登；最终事务锁内重读、旧预览失效；不能靠取消申请解开登记互锁 |
| R1-g | 固定历史计价与日期证据 | 不从可变当前款式或新版 scheduledAt 推导旧工资；缺证据有可处理的阻塞记录 |
| R1-h | 将历史核对义务纳入新版写入与日结资格 | 新版完工、补登、承接、转派及相关结算不得绕过旧实际生产；范围清楚、重复请求安全 |

原申请数量、核定数量、申请日期、实际工作日、操作者、理由和来源任务需要同时可追溯；不能把修改申请本身覆盖成从未申报过。驳回仅表示核实没有该次真实生产，活跃单仍保留未完成任务，已取消单不重新进入生产；已经做过但填错数量应走核定调整。

现有取消参考价使用总量分配。接入新事实时，逐款可识别的已产下限必须优先校验；多个款式只有合计 990 而无法知道各款数量时，先让管理员核对，不把自动比例分配当作真实生产证据。客户结算上限与工资实际产量冲突（例如超量生产或改版前已产量较大）须返回具体核对项，不压低工资或放宽对客金额约束。

### 3.5 C1/C4：未登记事实和历史义务的闭环

1. 在现有改单/取消复核层展示受影响的原任务、已登记数量和管理员核实的未登记数量；核实为零同样留痕，不把所有 PENDING 自动视为零。只增加能支撑本次判断的信息，不另套泛化确认弹窗。
2. 以原款式、工种、生产批次核对；实际内部生产必须补登记和计提成，外协/打包不得为凑总量伪造工资。多款只知总量、日期或归属不明时建立具体待核对项，并阻止受影响的批准操作。
3. 管理员补登沿用原任务负责人，区分生产人和录入人。每次申请/核定/驳回保留原事实与处理结果；同一生产事件最多产生一份完成事实，重复提交不重复计薪。没有真实生产的驳回保留证据，不能成为消除真实工资的快捷入口。
4. 补登、数量核定、改单/取消共用工单锁并使旧预览失效；日结串行检查原师傅原日。未知日期不能因字段为空漏过守卫，先核清可能的生产期间，未排除前阻止该师傅对应期间结算，不能影响无关人员。
5. 旧版存在未决生产事实时，排单转派、新版默认完工/补登以及继续承接均检查同一义务，不能仅在 UI 禁用。能确认无依赖的其他工单继续处理；同单依赖范围无法明确则保守阻止相关操作并给具体入口。已发货或已产的后续版本只记录冲突，不回滚物流或删除工资。
6. 核清后保存“哪些旧事实被承接、哪些确为新增”的证据再解除阻塞。不能只解除日结阻塞却继续让新版全量再次计产。恢复识别不只看物理指纹相同与否，设计改版前已做过的工资也要保留。

### 3.6 C3：历史生产与计价依据

- 原任务资料、物理标识、实际数量和计价取价依据需要有版本的快照。普通首次生产、补登、数量核定和存量恢复共用历史输入解析；审批时间变化不能改掉同一生产事实的取价依据。
- 局部生产倍数优先使用可信的原 payrollPassCount；缺失时按原版本实物数量和工序计件量核对。专版颜色读取原任务资料。不能读取改版后的 OrderItem 重新解释旧生产。
- [工序计划](../../lib/production/operation-materializer.ts)的 sourceQty 可能已经乘过版次数，不等于实物件数；解析明确单位，不能直接替换计价分母。可用证据来自任务 snapshot、工序/来源事实及历史记录；证据相互矛盾时转待核对，不能以当前字段兜底。
- 原工作日校验使用所属生产版本的可信下发/生产边界与雇佣范围；不使用新版 scheduledAt，也不一律以恢复时新建记录的 createdAt 为下限。保留未来日期、已结算日和账号写入边界；可信原边界缺失则待核对。
- 缺工价或资料不能填零、改生产日期或自动转成另一种工资类型。存量人工核定必须关联原生产事实与依据；遇已结算原日走 D2/R5-d，不绕过现有日结保护。

## 4. 任务 R2：重做单从真实入口进入正确生产流程

覆盖 F1，同时处理重做单二次物化风险。

1. 明确区分新模式源单与历史模式源单。新模式关联重做经已有受控确认/下发流程进入 RELEASED，再继承生产归属、创建必要打印待办；保留重做资格、原单交付、既有免费重做及各类工单核价规则和工艺预检，不新增收费重做。
2. 不能仅给真实创建入口加 `targetStatus: RELEASED`：当前入口创建 SUBMITTED，状态机并不允许 SUBMITTED 直接到 RELEASED。应在事务中走受控的确认/下发转换，不能裸写状态，也不能全局改掉历史物化的默认值。
3. 首次关联重做从源单的来源款式继承归属；重做单自身改版只从自己的历史生产承接。两个继承路径互斥，避免同版本同来源键重复创建。
4. 幂等重放必须核对已有任务的订单、版本、来源、归属和生产性质；不可仅用“已存在就跳过”掩盖错误承接。不能唯一确认原归属的新增任务仍由管理员安排，已有真实产出不换人。
5. 重做自身只改文字：已完成量承接，不生成重复工资；确实补做/增量：仅新增真实剩余生产，使用 R3 的计价来源。暂停中的重做改版保持暂停，恢复后根据当前任务与外协事实决定生产状态。
6. 新旧模式扫码、打印、师傅列表、管理员补登和外部销售状态读取一致；历史模式订单不自动转账本。源单发货和已结算工资不变。
7. 明确零内部生产任务的分支：重做确认/下发、物化与归属处理完成后，在同一工单锁内主动调用共享完成闸口，不等待不存在的报工事件。仅重打包且无外协待办可进入 PACKING，不要求师傅或补造工资；纯外协仍等待验收。返回值、幂等回执、详情和通知采用闸口后的真实状态，不能数据库已待发货而下发响应仍写生产中。缺少应有任务归属与确实零任务分开判断，前者仍给排单入口。
8. 源单归属可确定但账号已停用时，历史归属仍保留；师傅账号不能继续扫码，管理员可按实际工作日及雇佣范围补登记。新工艺/新任务的安排仍校验工种资格，不能以“重做继承”为由绕过授权。

子任务：R2-a 改正新模式创建/确认/下发与打印；R2-b 分离首次重做和重做自身改版的继承；R2-c 接通任务/扫码/补登/发货并补零任务主动完成触发；R2-d 提供第 4.1 节的合法生产状态转换。创建事务失败时整单回滚，成功重试不得重复创建任务、打印或通知；事务提交后的通知失败按原有重试机制处理。

主要改动：[重做创建](../../lib/order/rework.ts)、[工序物化](../../lib/production/operation-materialization-service.ts)、[任务继承](../../lib/production/revision-jobs.ts)、[状态机](../../lib/order/status-machine.ts)、[下发/恢复](../../lib/order/admin-workflow.ts)。

验收必须从 `createReworkOrder` 开始：创建 → 原归属师傅可见 → 登记完成 → 待打包发货 → 填写物流。另测重做单文字改版、增量改版、重复请求和暂停恢复；不能用测试手工改状态替代真实入口。

## 5. 任务 R3：以生产事实判断计价方式

覆盖 F4。把工单资料版本与生产批次的计价性质分开。

| 事实 | 计价方式 |
| --- | --- |
| 普通单首次实际生产，即使下发前已修改到 v2/v3 | 正常计件 |
| 已排单但尚无真实产出、未决申请已处置，再修改后首次生产 | 正常计件，继承负责人 |
| 已有实际产出，后续物理变更、追加数量产生新生产 | 人工补录新增提成，原工资保留 |
| 关联原单的重做生产 | 人工补录本次提成 |
| 已完成任务仅改文字，不需要新增生产 | 沿用已产数量，无新增工资 |

- 新任务记录服务端确定的计价原因、来源任务和生产批次依据；优先在现有任务快照中使用有类型和版本的字段。若查询/约束需要独立字段，再补 schema 与前向迁移。不得由表单传入 `manualPricing` 决定。
- 排单和改版继承共用判定函数，删除 `workOrderVersion > 1` 作为人工补价的充分条件。检查同订单、款式及工种的真实生产关系，不能把无关任务的历史套到所有新任务，也不能把未决申请视为“无产出”。“能确定可承接多少”与“以前是否实际生产过”分别判断；多款合计无法拆分而未承接，不代表首次生产。
- 保持原正常计件工价、过版次数、颜色、小单费和开机费口径；不得在核定完成时改变既有已计薪记录。
- 存量错误标记按 R5 核对。已有工资、流水或结算的任务不批量改价；待核对记录不能自动当零元或重新自动发一笔钱。

### 5.1 生产承接与计价一起修正

不能只修改 `dispatch.ts` 的版本判断：[revision-jobs](../../lib/production/revision-jobs.ts)目前也把所有继承任务设置为人工补价。两条写入必须使用同一个判断来源。

| 子任务 | 必须覆盖的情形 | 结果 |
| --- | --- | --- |
| R3-a 生产性质 | 未生产的普通单首次下发、已排单未生产后改版、真实增量、物理改版、关联重做 | 分别记录首产/承接/增量/重做依据，由服务端决定计价，不只看版本号 |
| R3-b 完成事实承接 | 1,000 个计划经管理员核定实际 990 完成，之后仅修改交期或名称 | 保留真实 990 与既有工资，仍是已完成；不能伪造 1,000 实际量，也不能自动要求补做 10 个 |
| R3-c 新增生产 | 已产 1,000 → 总量 1,300；一个款式改设计、其余不变；多次改版 | 只为真正新增/需重做的生产建任务；前者为 300 待补价，其余按各款/工种识别，不重复累计沿用记录 |
| R3-d 工价回归 | 局部/专版、过版数、颜色、小单费、开机费、已有非自动计价情形 | 首产保持原工价规则；真实增量不重算原批工资；其他合法人工核价原因不被误删 |

R3-b 是本轮补充验收要求，依据“文字改版不重复计产”；浏览器尚未执行“先批准 990 再改交期”的完整路径，不标为已实测缺陷。当前承接计算直接用新需求量减实际量，需保存并区分“原生产要求已经核定完成”和“实际数量”。仅资料变更沿用完成结论；数量/物理变更后按真实生产依据计算新任务，已核定差额和多款量不清的情形须向管理员展示本次量的依据，不能默默沿用不明合计。

发生“原需求与核定实际量不同，后来又增量”的组合时，按 D1 明确后的规则执行 V25；普通已产 1,000 增至 1,300 仍为新增 300。生产量计算、UI 默认值、改版预览和审计依据须共用同一结果。任何数量承接前先检查 R1-h，不能通过人工补价标签掩盖重复实物。

主要改动：[dispatch](../../lib/production/dispatch.ts)、[revision-jobs](../../lib/production/revision-jobs.ts)、[completion-registration](../../lib/production/completion-registration.ts)及相关工资快照类型。

验收：未投产普通单改文字/改数量到 v2 后首次完成仍自动计件；真实完成 1000 后新增 300 保留原工资、仅 300 待补价；重放和改版不重复计薪。

- R4-c：工资页按“原工作日 + 生产师傅”列已知金额、待核定数量、待补价三类事实；未知金额不算零。只有申请还没有工资的人员日也能找到，包含被取消单。阻塞错误提供具体工单和任务链接。

## 7. 任务 R5：存量恢复、完整验证和交付

### 7.1 存量处置不能遗漏

| 记录类型 | 恢复策略 |
| --- | --- |
| 新模式 SCHEDULING 重做单，无冲突历史 | 校验原单、归属、任务和打印事实后，通过受控修复命令推进到适用状态；记录审计并支持幂等 |
| 取消/暂停单上的 REQUESTED，原日未结算 | 使用 R1 管理员核定入口保留原日期处理；不恢复取消工单、不重新选生产师傅 |
| 旧版被改版取消的申请 | 保留申请及工资核对义务。核对新版产量、承接和后续工资；没有依赖冲突时才受控恢复审批，不能直接批量把 CANCELLED 改回 REQUESTED |
| 已取消/旧版任务已实际生产但没有申请记录 | 依据管理员核实及原任务证据建立待核对记录；原人、原日、原内容齐全后受控补登，不能从 PENDING 状态推断未生产 |
| 错误人工补价的首次生产任务 | 仅未完成且无工资历史、证据充分的任务可审计修正标记；已完成或有账本的任务按历史计价证据核定，不重写旧金额 |
| 原工作日已结算或后续生产/工资存在冲突 | 保留可追踪未付义务与冲突证据；已结算补发按 D2/R5-d，其他冲突独立核定；不自动挪日、解锁结算或扣回后续真实生产工资 |

恢复脚本先 dry-run，输出计划与跳过原因，再通过受权入口执行；实际操作前备份并核对目标环境。不能在数据库迁移里猜测产量、师傅或补价。若存在未处理异常，交付必须列出并区分“新增路径已修复”和“存量恢复未完成”。

子任务 R5-a 分为：R5-a1 只读扫描；R5-a2 先持久化核对义务并启用原工资日及关联新版写入保护；R5-a3 受控恢复与对账。R5-a2 随第一批交付，不能拖到全部 UI 完成以后。清单至少含环境、工单/任务、异常分类、原师傅和工作日、申请量、后续版本依赖、工资/结算引用、拟处置与不可自动处理原因。旧 CANCELLED 或未登记生产均按相同标准处理；只写离线报告不算闭环。记录批次与预期修订，逐单锁内重读，重复执行不重复计产、计薪或恢复通知。

恢复前先识别新版是否已完成、人工分配工资、日结或发货。无冲突条目自动化采用可验证的历史依据；有冲突条目隔离并给处理入口，不一键重置状态。核对清单可区分“待调查”“已确认应付但待核价/补发”“已处理”“证据证明无需处理”；原日已结算不等于应付义务已消失。

结构迁移只建立必要字段/索引/约束，不能在迁移中直接猜价、改产量；应用层和现有[数据库数量守卫](../../prisma/migrations/20260928123000_production_history_and_approval_guard/migration.sql)对未决义务保持一致，旧迁移不修改。部署顺序须保证新旧应用交替期间不存在工资守卫空窗；如果无法兼容，应在现有运维方式下暂停相关写入后切换。发生问题优先停止受影响写入并向前修复，禁止删除工资流水或回退已应用迁移。

#### R5-d：已结算日漏登记的补发方案（依赖 D2）

共同要求：先保存原任务/版本、实际生产日、原师傅、实际量、已发工资与旧结算引用，关联待处理义务；不得改写原账或把生产日期挪到未结算日。当前 [production-wages](../../lib/salary/production-wages.ts) 仍受原日已结算保护，不能简单复用其写入并放宽守卫。

若用户选择推荐的独立补差方式，则把以下工作作为本批 R5-d 的完整交付，未完成不得称相应旧数据已恢复：

1. 新增独立补记事实/补差凭据，关联原生产与结算，分别记录原工作日、补差核定时间及后续支付记录；原工资单不改金额。只有实际确认的漏付计入，原自动工资和已人工分配金额全部纳入防重复核对。
2. 待核价不能当零；按可信历史计价依据或既有人工补价原因核定应补金额。金额使用 Decimal，注明差额依据；本次不顺带开发任意扣薪、负差追缴或解锁已付结算。
3. 核定与支付沿用现有管理员工资权限并在服务端重新检查；凭据、审计、余额及支付绑定按固定锁序原子写入。稳定业务标识去重，同一义务的重复提交/双人核定/双次标记支付不能重复入账。
4. 工资待办、师傅个人明细、管理员工资汇总、后续付款清单、工资导出和相关成本查询均纳入消费方清单。生产日归属与支付时间分列，不能把补差算作后一天的新生产量；销售不得读取内部金额。
5. 前向 schema/约束、直接 SQL 防重复/防改历史、空库迁移及旧账不变断言随功能交付。原结算、旧工资/流水逐项对比，补差付清后有可追溯处置回执才解除未付义务。

若用户选择另立补差任务，本批仍完成上述共同要求及有定位入口的未付异常；R5-d 的金额核定/支付保持未实施，不用“已登记异常”冒充“已补发”。选择未回复前，不实现或发布任何放宽已结算日限制的分支。
