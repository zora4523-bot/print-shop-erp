## 1. 复审结论与证据

### A：P2，新增校验阻断未修改的历史颜色

旧版本允许同面保存 `['哑金', '亚金']`。只修改款式名称，本应保留历史生产事实与金额；当前却会报“同一面的烫金颜色不能重复”。这不是推测，也不等于已经发生生产事故。

本轮确认了同一根因的三个入口，必须一起处理：

| 入口 | 当前失败位置 | 实际影响 |
| --- | --- | --- |
| 申请未携带颜色，由领域层继承旧值 | [change-request.ts](../../lib/order/change-request.ts) 的 `assertMergedPricingFactsValid`；调用位置为申请创建、预览、批准 | ADMIN / SALES 纯改名被阻断；待审纯改名申请无法预览或批准 |
| 外部销售当前表单 | [OrderChangeRequestForm.tsx](../../components/business/order/OrderChangeRequestForm.tsx) 的 `buildSelectedOrderItemChanges` 无条件回传两面颜色 | 只改名称也把旧重复别名当成新输入，在命令 schema 处直接失败；只修领域层不能解决 |
| 升级前已保存、包含未变颜色回显的待审申请 | `readProposedChanges` 使用当前 `orderChangeRequestItemsSchema` 读取持久化 JSON | 预览、批准报“申请数据已损坏，无法审核”；拒绝申请仍可执行，不能把它描述为所有处理入口都失效 |

关键位置按审查基线计：`change-request.ts:607,1113,3524,3890,4103,5839`，`shared.ts:172`，`order-create.ts:205`，`OrderChangeRequestForm.tsx:338`。行号会随实施变化，函数名和测试断言为后续定位依据。

### B：P3，管理员编辑选色仍有修复遗漏

[AdminOrderEditor.tsx](../../components/business/order/AdminOrderEditor.tsx) 把已存颜色重新并入目录；[OrderFoilColorPicker.tsx](../../components/business/order/OrderFoilColorPicker.tsx) 仍按字符串判断候选和选中状态。

旧单只选“哑金”时，实际 React SSR 输出选中的“哑金”和可点击、未选中的“亚金”。现有点击逻辑会追加成 `['哑金', '亚金']`，随后被新校验拒绝。重复展示在原版本已存在，属于此次颜色修复未覆盖的编辑入口，不能包装为第二个新增 P2。

## 2. 修复边界

| 场景 | 计划行为 |
| --- | --- |
| 新建、新增款式、实际修改颜色 | 继续按颜色身份严格校验；同面重复拒绝，正反面各一次同色仍合法 |
| UPDATE 只改名称等非计价资料，颜色来自锁内原工单 | 允许保留历史同面别名；不改颜色原名、面别、数量、顺序、聚合字段和已存金额 |
| 当前销售表单未修改颜色 | 不发送两面颜色字段；让领域层读取原值 |
| 旧待审申请回显了与原单完全一致的颜色，实际只改非计价资料 | 先按旧结构读取，再在锁内证明颜色和计价事实未变；可预览、批准，且不回写颜色字段 |
| 数量、包装、规格或颜色实际变化 | 按现行报价、生产、状态与人工确认流程执行，不能借历史兼容沿用旧价；带重复别名时需明确纠正颜色并核对新金额 |
| 旧申请实际引入重复颜色、数据结构损坏或依据不完整 | 不自动批准；给出适用错误和恢复操作，保留拒绝申请入口 |

特别禁止把“没有提交颜色”直接等同于“无需计价”，也不采用“先去重数组再校验”的通用修复。数量或包装变化即使没带颜色，仍可能改变金额；去重还可能掩盖原始色数、上限或工艺矛盾。

权限、账号有效性、资源归属、工单锁、修订号、纸质版本、价格版本、报价确认凭证、生产事实凭证、发货和结算限制全部保持。旧 `IN_PRODUCTION` 工单不能改计价的既有规则不因本批改变。幂等、审计、拒绝和失效处理继续执行。

不新增数据库迁移或清理脚本，不改已应用迁移，不覆盖生产库，不删除旧材料，不重算历史报价/提成，不把颜色身份等同于库存 SKU。

## 3. 实施任务与顺序（T1–T6 已完成，验收见第 6 节）

### T1：先固定失败回归

- 将本轮有效复现转为仓库内正式测试，按现有 fixture 风格整理；不提交整份复制测试或临时测试配置。
- 覆盖领域层三个阶段、销售端真实 payload 构造、旧申请读取两种形态，以及管理员选色控件。
- 先记录当前候选的失败，再以相同断言验收修复；单个别名、跨面同色和新输入拒绝作为对照。

### T2：划分严格输入校验与未变历史事实校验

- 修改范围：[shared.ts](../../lib/auth/schemas/shared.ts)、[order-create.ts](../../lib/auth/schemas/order-create.ts)、[change-request.ts](../../lib/order/change-request.ts)。
- 复用类型、字段形状和路线不变量，只分离颜色唯一性规则：当前输入按语义身份，受控的未变历史事实保留原字符串判重。空值、长度、每面上限、纯彩印哨兵、工艺/路线矛盾及规格身份继续校验。
- 历史路径只能由领域层在锁内选择：必须是 UPDATE，已从原工单取得颜色，原始颜色事实未变化，且 `changeAffectsPricing` 为 false。客户端不得提供“历史兼容”开关或受信任标记。
- 对当前新命令，只有省略颜色并继承原值的非计价修改可以走历史路径；直接提交重复颜色仍拒绝。对旧持久化申请的特殊处理由 T4 控制。
- 不通过中文错误文案筛除 Zod issues，不对整组字段跳过验证，不放宽公共建单、报价或修改 schema，不修改报价引擎来吞掉重复颜色。
- 创建、预览、批准共用同一领域判定，不在 Action 或页面复制规则。
- 成功后沿用现有不计价分支；原始颜色数组和存储标志不回写，价格快照、收费行、工资及库存不改变，正常的名称、版本和审计更新仍执行。

### T3：销售端只发送实际变化的颜色

- 修改 [OrderChangeRequestForm.tsx](../../components/business/order/OrderChangeRequestForm.tsx) 的 UPDATE payload 类型及 `buildSelectedOrderItemChanges`，未改两面颜色时省略这两个字段；ADD 仍携完整事实。
- 沿用现有按原始名称判断是否实际变化的规则，不能因为“哑金”和“亚金”语义相同就吞掉用户明确的换色。显示名还原、草稿续填和整单版本字段继续工作。
- 同步纯函数、契约与浏览器断言；已有测试明确要求回传未改颜色的断言应依据本方案更新，不能直接删除这组测试。
- 管理员 `buildEditorChanges` 已按变化发送颜色，复核其行为并加防回归；不为一致外观进行无关重构。

### T4：恢复旧待审申请的安全读取

- `readProposedChanges` 不再把持久化旧 JSON 直接等同于新命令。复用现有字段定义增加内部读取方式，仍检查操作、ID、类型、边界和可识别结构；这个读取方式不作为 HTTP / Action 输入校验器。
- 区分“没有带颜色”与“旧表单回显未改颜色”。后者必须与锁内原款式的原始颜色事实相符，并通过版本、所有权和非计价修改判定，才允许保留；不能只用语义别名相等作为证据。
- 旧申请含实际改色、新增款式或数量/包装/规格变化时仍走严格校验与现行报价；读取成功不等于允许批准。
- 对证明未变化的旧回显，在应用修改时明确省略颜色写入，避免 `foilFactsProvided=true` 导致聚合字段或旧标志被重新派生写回。
- 不重写历史申请 JSON、`beforeSnapshot` 或已处理日志。保留驳回、版本失效和并发拒绝路径；合法旧记录不再误报为“数据损坏”。

### T5：管理员选色使用统一身份，保留历史事实

- 修改 [OrderFoilColorPicker.tsx](../../components/business/order/OrderFoilColorPicker.tsx)，复用 [foil-color-identity.ts](../../lib/order/foil-color-identity.ts)。保留共享 `Button`、语义样式、焦点和可访问状态，不新增页面专属按钮样式。
- 候选色按身份唯一；已有选中色优先。只保存“哑金”时，不再提供另一个可追加的“亚金”，选中状态对应同一颜色。
- 如果旧单已保存两个别名，不在加载、改名或选择其他字段时自动合并；已保存的每项仍可核对。用户明确删除某一项时只删除该原始项，不能一次清除整组别名。
- 选择候选时按身份防重复，移除已保存项时按原始值定位；不要直接套用会先去重整个 `current` 的建单选择函数来删除历史项。
- 不烫、最少一色、最多三色、更多颜色、禁用、前后面独立、自定义颜色和顺序均须回归。新增颜色操作不能凭别名绕过数量上限。
- 服务端仍是最终守卫；字段错误遵守原因加恢复操作的文案，不加新的泛化确认弹窗或常驻技术说明。

## 4. 必须覆盖的验收矩阵

| 类别 | 用例与必须断言 |
| --- | --- |
| 非计价修改 | ADMIN / SALES：单旧别名、同面双别名、其他已知别名、未知品牌色；创建、预览、批准成功，不调用重新报价，不回写颜色/金额/工资 |
| 历史形态 | 显式正反面、旧 aggregate-only、无颜色字段的待审提案、包含未改颜色回显的旧提案；保留面别和原始事实 |
