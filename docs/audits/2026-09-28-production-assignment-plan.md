# 多选排单、生产归属与计件工资方案

本文件为待实现方案，不代表功能已上线或已通过代码审查。用户已确认：师傅工资沿用实际报工计件规则，不按订单销售金额提成。多人拆量暂按推荐方案设计，是否允许同款同工序拆给多人仍待业务确认；若不允许，保留跨订单批量指派，关闭同工序拆量入口。

## 1. 目标与现状

管理员可以多选工单，按款式、工序或包装组把生产数量分配给师傅；管理端明确显示谁负责、分了多少、完成多少；师傅只对自己的有效分配报工，实际报工对应自己的工资记录。

当前实现把工单释放到工种列表，没有个人派工。首次扫码只是每个工单版本的一条首次扫码事实，不能充当生产负责人。旧 ProductionTask 含人员字段，但新生产和工资使用 ProductionOperation、ProductionProgressStep 与 ProductionReport；本方案在新链路上新增分配层，不恢复旧派工和旧计薪链路。

基线证据：

- [现行下发规则](../../SPEC-v1.2.md)：§3.2 明确当前不做师傅派工，§K 规定现行计件口径。
- [下发服务](../../lib/order/admin-workflow.ts)：releaseFactoryOrder 无师傅入参。
- [师傅工种规则](../../lib/production/reporter-operation-lane.ts)、[非计件工艺资格](../../lib/production/progress-reporter-lane.ts)。
- [工序物化](../../lib/production/operation-materializer.ts)：局部烫金可能汇总多个款式，计划单位为烫次，报工输入为合格个数；包装为袋或盒。
- [报工计薪](../../lib/production/operation-reporting.ts)：报工时选取有效工价并保存工资快照。
- [改版承接](../../lib/production/version-carryover.ts)：承接已产数量不产生新工资。
- [列表多选](../../components/business/order/AdminOrderWorkspaceList.tsx)：已有选择与批量操作框架。

## 2. 业务口径

### 2.1 三种归属分别记录

| 归属 | 依据 | 是否随排单改变 |
| --- | --- | --- |
| 销售归属 | 原业务员/提交人 | 否 |
| 生产归属 | 当前版本的工序分配记录 | 可以改派未完成量，保留历史 |
| 工资归属 | 实际报工人及不可变工资快照 | 不因改派、账号改名或价格变化转移 |

整张工单可以有烫金师傅、打包师傅等多个参与人。列表展示按工序归属，不设置一个会覆盖所有工序的 order.workerId。首期不另设“整单负责人”及负责人额外提成。

### 2.2 分配单位和数量

- 局部/专版烫金：管理员按款式的生产个数分配。局部烫金工资再按现有过版次数及工价规则计算，不把烫次当作个数分配。
- 打包：按包装组的袋/盒数分配，保留包装组和款式组成；不按订单个数直接分配打包量。
- 非计件工艺：按款式及具体工艺步骤分配完成数量，仅记进度，不自动产生工资。
- 同款同工序多人拆量示例：1,000 个分给甲 600 个、乙 400 个；不能给两人各分 1,000 个。不同工序可以分别覆盖该工单的全部数量。
- 不同工序、不同单位不相加为“产能”。师傅负荷按工序及单位分列，不声称数量能推导准确工时。
- 派单形成生产额度，不形成已挣工资；预估工资标明估算，实际报工时沿用现有工价生效、差异确认、质量扣除、补贴与结算规则。

### 2.3 下发与排单

推荐支持“待下发工单排单并下发”和“已下发工单补排/改派”两种操作。新排单模式按版本标记，已发布的分配才对师傅可见。

- 待下发工单可以暂存部分排单草稿；第一次“排单并下发”要求所有必需内制工序有完整分配。缺师傅、资格不符、缺有效工价或资料不完整时显示逐项问题，拒绝整个提交。
- 外协沿用外协单，不分配给内部师傅；寄样等无内制工序的工单显示“不需要排单”。
- 已下发工单允许明确的部分补排，显示“部分已排，剩余 X 待排”；未分配数量不可由任意同工种师傅报工。
- 暂停期间禁止新增分配和报工，恢复后沿用仍有效的分配；已发货、结算、取消及存在阻断性变更申请时禁止排单，具体沿用现行服务端状态限制。
- 已分配、已查看、已开工、已完成是不同事实。扫码/查看不算产出；首期由师傅显式“开始生产”记录开工，首次有效报工可补记开工事实。
- 生产操作列表仍以既有工种/账号资格为前置；分配不能突破工种权限。停用或改岗导致现有分配失去资格时，管理员需改派，系统显示阻塞任务。

## 3. 管理端与师傅端交互

### 3.1 管理员多选排单

1. 工单列表选择多张，批量操作栏出现“排单”；首期沿用当前页选择，页面/筛选变化明确清空，不暗中选中其他页。建议每次最多 50 张、200 条分配明细，服务端同样限制，超限引导分批操作。
2. 打开排单工作区，显示订单、款式/包装组、工序、总量、已产、已分配未完成、可分配、计划日期、师傅。按工种分组，不把混合工种一键派给同一人。
3. 勾选同工种任务行，选择师傅后批量填入草稿；默认填各行剩余可分配量。支持逐行修改、拆量、移除草稿行；草稿操作不发布任务。
4. 师傅选择项展示岗位、该工种待做数量、是否可报工、适用工价是否齐备。无共同兼容师傅时解释具体原因，不自动越权匹配。
5. 核对页明确展示每位师傅的工序与数量、未排量、是否同时下发以及预计工资仅供参考；管理员填写排单说明并提交。
6. 成功后列表和详情立即显示“局部烫金：甲 600 / 乙 400；打包：丙 100 袋”等归属与完成数。失败保留草稿，定位冲突行。

计划日期和师傅内的任务优先顺序可编辑；这只表达作业安排，不作机器小时级排程和自动产能承诺。管理员与师傅列表共享相同排序规则：计划日期、管理员顺序、稳定 ID；急单清晰标记。

### 3.2 列表与详情

- 工单列表增加“未排 / 部分已排 / 已排”筛选、师傅筛选、生产归属摘要和“排单/调整排单”入口；生产状态与分配状态分别显示。
- 详情新增“生产安排”：工序、来源款式/包装组、分配师傅、数量、完成数、计划日期、状态、分配人、改派记录。
- “未扫码”“已开工未报工”“有人报工但仍有工序无人承接”分别提示。停滞判断扩展到分配/工序维度，不能因一个师傅扫码就掩盖其他工序无人处理。
- 姓名来自历史快照或明确标注当前姓名；生产归属、工资实绩和首次扫码信息不混用。
- 改派入口始终可发现；不可操作时解释状态或已完成量限制。

### 3.3 师傅端

- “我的任务”只显示本人已发布的分配，可按计划日期及待做/进行中/完成筛选。历史报工与工资查询仍保留本人历史数据。
- 扫主工单二维码后，只列出本人可操作的分配；多条时让本人选择款式/工序，不再进入全工种公共可报列表。
- 别人的任务显示无操作权限，不暴露别人的工资；需要支援时由管理员改派或追加分配额度。
- 报工界面显示“本次安排 X、本人已完成 Y、剩余 Z”，按分配来源记录数量；服务器拒绝超过本人余额的报工。
- 缺陷/返工单独记录质量事实，不自动计薪，也不自动扩大分配额度。超出既有生产计划的补产走显式、可审计的重做/追加业务流程。

所有新增页面遵循[UI 文案与确认规则](../ui-规范.md)。新增批量排单与改派在服务端持久化说明后使用 L3 确认；确认展示实际影响，不重复叠弹窗。取消仅丢弃未提交草稿。打印确认、收费、物流和发货操作保持原有业务边界。

## 4. 改派、撤销与工资

- 未开工且无报工：可以撤销或把全部未完成量改给其他师傅。
- 已开工：改派需记录交接说明和未报实物核对结果；不能把现场已做但未报的数量假定为零。首期由管理员核对后执行，不自动推测实物状态。
- 已报工：已完成量及对应工资留在原师傅名下，只转移剩余量。例如甲分 600、已报 200，最多转给乙 400。
- 原分配以调整事件减少可做余额或关闭，创建接收方分配；不覆盖原师傅 ID。整个转移同一事务完成。
- 报工更正沿用追加冲销及结算锁规则。冲销会减少有效已产量，但不能悄悄恢复已撤销分配权限；归入待重新分配量或在同一受控更正流程中重新授权。
- 账号停用、改岗、工价调整、跨日结算分别按现有边界校验；已经结算的工资不能通过改派挪给他人。
- 工单改版关闭旧版本的未完成分配，按新版本事实重新核对剩余计划；旧报工仅承接生产数量，不重复计薪。只有来源可唯一对应时才能给出重新分配建议，发布前由管理员核对。

## 5. 数据与并发设计

以下为拟议模型，字段命名以实现审查为准：

- `ProductionAssignmentBatch`：草稿/发布状态、创建人、说明、幂等键、请求摘要、发布时间、排单修订号。
- `ProductionAssignment`：工单版本、目标工序或非计件步骤（必须且仅一个）、师傅、单位、授权数量、状态、计划日期/顺序、版本号、分配时岗位快照。
- `ProductionAssignmentLine`：对应工序来源的款式或包装组及数量。一个汇总工序不能只存总额，否则无法控制各款式多人分产和改版承接。
- 分配事件/审计：发布、开工、调整、撤销、改派前后值和原因；可变投影用于查询，不删除历史分配事实。
- 报工新增可追溯的分配及来源关联。新模式每条报工必须锚定有效分配；历史报工允许没有关联且明确标记历史模式。不同分配拆为不同报工明细，不在一条记录里混合工资归属。
- 使用数据库 CHECK/FK/唯一键约束目标、来源所属工单和版本；跨表余额在领域事务中校验。数量与金额用 Decimal，接口不信任前端合计。

待下发时工序可能尚未物化，草稿使用订单版本及服务端生成的来源/工序稳定键；发布时同一事务校验草稿、物化工序、绑定真实工序 ID、发布分配并下发。不能为保存草稿提前向师傅暴露生产工序，不能接受客户端伪造工序 ID 或跨订单来源。

只有启用 ADMIN 可以创建、发布、改派及撤销分配，师傅只能读取和操作本人分配。所有 action、二维码入口及直接报工接口在服务端重新验证角色、账号、订单版本和资源所有权，列表隐藏不构成权限控制。

每个来源维度维持：`当前版本计划量 = 承接及本版净完成量 + 已发布分配的剩余量 + 未分配量`。多工序分别计算；缺陷、返工不冒充有效完成量；工资冲销与生产数量冲销沿用各自现有事实口径。

提交前展示预览；提交时重新读取真实订单版本、分配修订号、资格、工价和余额。批量发布按稳定顺序锁定订单及工序，复用现有报工/改版锁顺序，再锁定分配，避免另建相反锁序。任意一行发生过量、旧版本、资格失效或订单状态冲突，整个批次不写入，返回逐行原因，禁止静默跳过。

同一幂等键同一请求返回原结果，换载荷拒绝；已提交后通知失败不撤销分配。通知经事务内持久任务派发，重试不重复派单。首期站内任务列表为权威入口，沿用已有共享群通知；个人通知仅在已验证账号绑定及可用路由时发送，不把通知成功当作师傅已接单。

## 6. 迁移与旧工单

- 新增向前迁移，不修改已有迁移或删除 ProductionTask 历史。
- 每个订单版本固定 `POOL_LEGACY` 或 `ASSIGNED` 模式，师傅列表、扫码、报工及完成闸口统一读取；不能仅靠前端开关切换权限。
- 已完成或结算订单保留历史。已有生产中订单默认保持历史模式并标注“历史共享报工”，不凭首次扫码人伪造分配。
- 生产中旧单转新模式必须在订单锁下核对在制数量及历史报工，冻结旧共享报工入口，仅分配剩余量。多个来源的历史汇总产出不能准确拆分时，禁止自动切换，留在历史模式直至完成或完成可审计的来源核对。
- 新模式订单一旦有报工，不允许通过关开关回到任意师傅可报的共享模式。上线故障时可暂停新排单，保留既有分配读取与授权；不能用代码回退绕过新数据约束。
- 数据库新增字段默认值、回填、旧应用兼容窗口和强制约束分阶段部署，先读兼容，再切换写入，最后启用强约束。上线前清点无可用师傅/缺工价工序并完成账号配置。

## 7. 执行任务与验收

| 阶段 | 必须完成的范围 | 验收证据 |
| --- | --- | --- |
| A 业务与模型 | 确认拆量口径、分配状态、来源数量、迁移和锁序；更新待实施决策 | 方案评审，单位/改版/冲销用例 |
| B 领域与迁移 | 分配草稿/发布/改派/撤销、资格/工价检查、批次事务、审计与通知 | fresh DB 全迁移、约束及真实 PostgreSQL 并发测试 |
| C 管理端 | 多选、批量草稿、拆量、归属/负荷摘要、筛选、详情与失败恢复 | 管理端浏览器/E2E、六视口明暗主题与 axe |
| D 师傅端 | 本人任务、扫码选择、开工、按来源报工、历史兼容 | 未分配及他人分配越权测试、重复提交及超量测试 |
| E 工资与版本 | 报工关联、现有计薪复用、改派/冲销/结算/改版承接 | 全量 Vitest、工资端到端、冻结历史前后对比 |
| F 联调发布 | 文档同步、完整回归、存量预检、部署/暂停方案 | typecheck、lint、适用 build/覆盖率/架构与发布门禁 |

不能只发布管理端按钮而保留师傅公共报工写入口。B–E 完成后才对新模式开放，各阶段提交可以独立审查但不得让半成品进入实际计薪。

必须覆盖的业务场景：

1. 多选工单给同一师傅；混合工种分别安排；无兼容账号明确失败。
2. 同款拆 600/400；同一师傅跨多款；多款聚合工序不会串用额度；袋/盒/个/烫次换算正确。
3. 两名管理员同时分配不超量；报工与改派并发只允许一种合法结果；失败无半批次写入。
4. 甲做 200 后改派剩余 400，甲工资不变，乙按本人实际合格报工计算；所有分配与报告可追溯。
5. 幂等重提不重复派单或重复计薪；缺陷、返工及超额补产不自动加工资。
6. 报工冲销、日结锁定、跨日工价、个人适用规则和历史价格快照不被排单改变。
7. 工单改版、暂停恢复、取消、账号停用/改岗、待审批变更均不会留下可越权报工入口。
8. 非计件步骤不进入工资；外协、发货完成闸口、打印、报价、销售与外部销售权限不退化。
9. 旧汇总数据不能唯一拆来源时阻止自动迁移；已有完成量承接不产生重复工资。
10. 数据写入成功但通知失败时可恢复，师傅仍可在“我的任务”看到分配。

实现时同步 SPEC、DECISIONS、API、DATABASE、相关操作/排障文档；不得提前把本方案写成现行 runtime。外部销售保持原工单可见范围，不展示内部师傅工价及工资；如需要显示生产进度，只输出原有授权范围的聚合状态。
