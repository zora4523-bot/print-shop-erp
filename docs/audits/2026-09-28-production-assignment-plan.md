# 多选排单、单人生产归属与人工提成登记方案

本文件为待实现方案。本次根据 8e0df592 的 Claude Code Opus 5.5 对抗审查及用户后续决定修订，不代表功能已上线、已完成测试或本修订已通过再次外部审查。

用户已确认的范围：保留管理员多选工单排单；暂不接入同一生产任务的多人拆量；正常生产沿用实际报工计件工资；多人协作时由管理员登记各人的提成。多人自动分产与自动分摊费用不在首期范围。

## 1. 功能边界与现有依据

- 一个当前版本的 ProductionOperation 或 ProductionProgressStep 同时只有一位生产负责人，指派覆盖该任务全部剩余计划，前端和接口均不提供拆量。烫金与打包属于不同任务，可以分别安排不同师傅。
- 若一个工序汇总多款，同一负责人负责其全部来源。本期不为分配人员而拆开既有工序，否则会改变小单档位、固定费及舍入边界。来源明细用于报工准确性，不作为独立多人派单入口。
- 销售归属保持原业务员；生产归属来自有效分配；正常工资归属来自报工，协作提成归属来自管理员核定流水。三者分别展示，不能互相替代。
- 多人协作保留一名生产负责人和一份产量，不为协作人员制造报工量、扫码权限或机器能力。工资登记可以包含没有报工记录的协作人员。
- 旧 ProductionTask 仅保留历史，新功能建立在当前工序/报工链路上。

已核对的事实源：

- [生产下发](../../lib/order/admin-workflow.ts)与[工序物化](../../lib/production/operation-materializer.ts)：现行下发不指定师傅，局部烫金按过版次数合并款式。
- [师傅计件资格](../../lib/production/reporter-operation-lane.ts)、[非计件工艺资格](../../lib/production/progress-reporter-lane.ts)：工种和账号资格仍是服务端前置。
- [报工](../../lib/production/operation-reporting.ts)与[烫金工资](../../lib/salary/foil-report-wage.ts)：固定费属于工序级，首报计入，多报工人/改价/承接等情形触发核定。
- [人工核定](../../lib/salary/order-wage-review.ts)：当前仅能调整已有 REPORT 锚点的人员，不能直接登记无报工参与人的工资。
- [工资结算](../../lib/salary/piecework-settlement.ts)：当前只取 ProductionReport，且分档烫金未完成或待核定不能结算。
- [进度](../../lib/production/work-order-progress.ts)、[版本承接](../../lib/production/version-carryover.ts)：进度与工资数量独立；承接不产生新工资。
- [现行规格](../../SPEC-v1.2.md)、[决策](../../DECISIONS.md)：存在包装缺价仍可下发但不可计件报工的规则；SPEC §K 对小单费的历史概述与现行分档代码存在差异，实现时应同步核对并更新，不能只引用旧概述推导工资。

## 2. 管理端多选排单

1. 复用工单列表的当前页多选，增加“排单”。首期单批建议最多 20 张工单、100 条任务，服务端同样校验；翻页/换筛选明确清空选择。
2. 按工种展示任务：工单、款式/包装组、工序、计划量、已完成、剩余量、负责人、计划日期、排序。局部烫金显示个数及过版次数，包装显示袋/盒，不混合相加。
3. 勾选同工种任务，选一名兼容师傅，批量填充草稿；单行只选一个人，数量不可自由拆分。可移除尚未提交的任务行。
4. 待下发工单可保存未排完整的草稿；“排单并下发”要求必需内制任务均有负责人。外协走外协单，无内制任务的寄样单显示“不需要排单”。
5. 师傅选择展示工种、分单位的待做任务量及缺工价提示。缺账号/不兼容阻断；缺工价只提示“可排单，下发后需补工价才能计件报工”，不新增下发阻断条件。
6. 核对页展示各师傅的任务、全部剩余量、未排任务、是否同时下发，保存排单说明后发布。价格展示为预估，缺价不显示零价。
7. 整批事务成功才显示成功；失败保留草稿并定位原因，不悄悄跳过部分工单。

新增批量排单、金额核定和报工作废遵循[文案与确认规范](../ui-规范.md)：服务端保存原因后使用对应高影响确认，列明对象、差额和结果；取消不发布草稿，失败保留输入，不叠加确认弹窗。

列表增加“未排 / 部分已排 / 已排”“负责人”“待人工核定”筛选；“部分已排”仅指部分工序未排，不表示同工序拆了部分数量。详情显示负责人、分配人、计划日期、开始时间、完成量、交接及人工提成记录。正常按钮使用“排单”“调整负责人”“登记协作提成”，禁用时解释原因。

计划日期和师傅内的顺序仅表达作业安排，不承诺机器工时产能。管理员生产安排与师傅任务按计划日期、人工顺序、稳定 ID 排序；不改变主工单列表现有排序契约。外部销售不展示内部工价、协作提成和工资明细。

## 3. 师傅端与开工

- 新模式下“我的任务”和主单二维码只返回本人有效分配且工种兼容的任务；师傅不能直接使用旧接口对别人或未指派任务报工。
- 工序有多来源时，负责人逐款/包装来源录入数量，界面显示本任务及各来源剩余量。服务端校验来源属于任务及版本。
- 开工记录使用按分配唯一的独立事件，不复用“工单+版本唯一”的首次扫码认领。第二道工序的负责人可以独立开工；扫码浏览不算开工或产出。
- 开工不直接推进工单生产状态，工单仍由有效报工和完成闸口推进。报工可补记本分配的开工事件。
- 停滞按任务分别判断：待开工、开工未报、缺工价、无人负责、停用账号等；一个人扫码不能解除整单其他任务的停滞提示。
- 当前账号停用或改岗立即失去报工资格，历史报工和工资按原有权限保留。管理员看到阻塞原因及接管入口。
- 缺陷和返工单独记录，不自动增加有效产量或工资；超出原计划的补产走显式重做/变更，不靠重新派单扩大计划。

## 4. 多人协作：管理员登记提成

### 4.1 操作流程

1. 管理员在工单详情选择实际参与多人协作的工序，进入“登记协作提成”，标记该工序进入人工核定。原生产负责人不变，协作人不取得生产写权限。
2. 展示原自动计件及已核定金额、参与人、实际工作日、拟核定金额、总额及差额；支持选择没有报工记录的协作师傅，填写协作说明。实际工作日按上海日期，校验雇佣期间；停用但在该日任职者可作历史登记对象，不恢复其登录权限。
3. 输入的是每人该工序该工作日的“最终应得金额”，不是追加发放金额；未分配差额必须明确处理，不自动按产量比例拆小单费/装板费。
4. 管理员提交时核对整组总额及相对原计件总额的变化，允许显式核定不同总额但必须说明原因。若原自动金额为甲 12 元，最终甲 7、乙 5，则只形成甲 -5 的核定差额及乙 +5 的人工工资，合计仍为 12，不能再另发原来的 12。
5. 工序未结束时允许保存草稿；最终发布要求工序完成或经正常业务流程取消，并完成全部参与人核对。不得为了结算关闭仍需生产的剩余计划。
6. 登记协作后，后续正常报工只形成待核定金额，不自动清除人工核定标记；有新报工或更正使已保存的核定草稿失效。所有相关人暂不能结算这笔工序工资，核定发布后统一放行。

### 4.2 账本与结算方案

新增独立的人工提成批次、参与人明细和追加流水，记录 order/version/operation、受益人、实际工作日、原值、目标值、差额、原因、登记人、修订号和幂等键。没有报工锚点的协作人员写人工提成流水，不伪造零数量 REPORT，不放宽现有 ADJUSTMENT 的锚点规则。

- 已有有效报工的人：沿用现有受控 ADJUSTMENT 记录差额，并关联人工核定批次。
- 无报工参与人：新增人工工资事实及其独立结算明细关系，允许该日只有人工提成也可结算。
- 结算统一汇总有效自动报工、已有核定差额及人工工资事实；每条事实最多被结算一次，使用数据库唯一关系，历史结算快照不回算。
- 人工提成更正只追加差额，不覆盖历史。按“工序+受益人+工作日”计算已有净额，重复保存相同目标不能再次增加金额。
- 所有参与人和原自动工资承载人的工作日必须可调整；任何一方已结算/锁定则整批拒绝，不通过改日期、替换人员或挪到另一天绕过。保留差异处理说明，已结算历史更正不属于首期。
- 管理端费用/成本、工资列表、师傅工资明细、日结、汇总和工资导出统一消费新增事实，既不能漏计也不能在两条查询中重复相加。
- 多人协作的生产数量仍只记录一次。多人提成登记与生产统计完全分开，人工金额修改不会推进工序或发货进度。
- 标记协作与结算共用工单/工序和相关工作日锁，保证不能在核定途中结算其中一人；已有结算的工序拒绝转入会重分该工资的协作核定。

非计件进度步骤继续不自动计薪。本期人工协作提成限定于原本可计件的工序；为非计件工艺新增薪酬规则不夹带在本任务。

## 5. 报工数量与工单进度修复

明确三套量：生产来源完成量（个/袋/盒）、计薪量（可能乘过版次数）、工单阶段进度（个）。界面及服务端不得把它们当成一个字段。

- 新增报工来源明细子表，父 ProductionReport 仍是一笔报工和计薪事实；明细数量合计等于父报工数量，来源单位一致。数据库触发器/事务校验同工序、同版本、来源余额、整数和合计。
- 一笔报工不因多个来源拆成多条工资，以保留现有固定费和累计舍入规则。报工幂等键不因来源多而重复；请求摘要包含所有来源及数量。
- 新模式取消师傅自由填写“整单阶段件数”的入口。服务端依据来源报工计算阶段增量，拒绝客户端提供额外进度；历史模式维持兼容接口。
- 烫金来源按款式的完成个数统计；同款若同时需要局部和专版等多个烫金任务，阶段已完成数取这些必需任务的净完成数最小值，再对不同款式求和，避免一款经过两道烫金计两次。此为数量进度，不作为逐件批次追溯证明。
- 包装按版本冻结的包装组组成换算件数，不使用当前字典。新增可追溯的包装组成/尾包换算事实，累计换算后取差值，不逐批舍入；尾包、混款、分地址包装无法唯一换算时阻止该新模式数据写入，要求先修正包装事实，不开放手填整单进度绕过。
- 进度明细保存报工来源证据及计算规则版本。报工、来源数量、阶段进度及工序状态同一事务写入；全局阶段上限和源级上限同时校验。
- 版本承接新增来源级事实；只有来源明确的新模式记录可逐来源承接，工资仍不随承接重发。旧多来源汇总记录无法唯一分摊时保留旧模式，不按比例猜测。

包装换算及混合工艺进度是 T2 必须先验证的算法，不是完成 UI 后再补的事项。发货仍校验实际工序/外协完成闸口，不能只看进度条。

## 6. 报工更正与改派

### 6.1 报工更正

现有系统没有完整的应用层数量冲销流程，因此本任务需新增受控流程，不能写成“直接沿用”。

- 首期支持管理员作废当前版本的错误报工：仅未发货、未结算、未产生跨版本承接依赖、未进入其他不可逆业务状态的记录可操作。服务端同时检查所有关联人工核定及工资日期。
- 同一事务追加工资 REVERSAL、对应核定差额抵消、来源负向更正事实、阶段进度修正事实，重新计算完成状态及待核定标记。原表保持不可变；新增进度修正账本参与所有读模型与完成闸口，不在只允许正数的旧进度表强写负值。
- 取消的是该次报工事实，不代表实际发生了返工；实际返工/重做走现有质量或重做流程。更正后的重新报工使用新请求，沿用报工时的工价和业务日规则；确认页说明跨日或工价变化，不伪装为原日原价报工。
- 更正不能静默重新授权已关闭的分配。新模式来源净完成量减少后形成“待核对剩余量”，管理员核对后显式恢复原负责人权限；自动更新的只是事实投影。
- 工序曾发出完成通知后被更正，必须留下更正事件，暂停其后续发货资格，并以完成修订号区分重新完成通知，不能被旧幂等键吞掉。
- 首期不支持冲销已承接到新版本、已发货或已结算的报工；按钮说明具体依赖。跨版本需要逐层抵消承接且涉及多账本，另立任务，不通过直接 SQL 或回写快照规避。

### 6.2 改派与已做未报

- 普通“调整负责人”只允许尚无任何有效产出的任务；旧分配关闭、新分配覆盖全部剩余量，同一事务且只保留一个有效负责人。
- 已点击开工但未报工时，管理员必须核实实际未生产并保存交接说明后才可调整。只要有已做未报数量，先报实物数量；不能把它当作零转走。
- 已有生产/报工的任务首期不开放自动改派和剩余量拆派。需要其他人协助完成时，保留生产任务、由管理员登记协作提成，不恢复多人自助报工。
- 原负责人无法登录时，提供管理员受控登记生产记录入口：明确“登记人=管理员、任务负责人=原负责人、实际协作情况=管理员说明”，通过独立 ADMIN 领域命令授权，不冒充 WORKER 会话。只有核实的来源产量入进度，工资须按人工协作核定，不把总产量算成原负责人个人实绩。
- 管理员代登记采用独立的来源生产事实及凭据，明确不是师傅本人报工，不生成原负责人自动工资。来源余额、阶段进度、完成闸口和改版承接统一汇总正常报工与管理员生产事实；不能只更新进度条或给停用账号伪造 REPORT。管理员生产记录的作废同样走前述受控更正，无工资锚点时不伪造工资 REVERSAL。
- 暂停期间允许调整尚未生产任务的负责人和编辑安排，生产写入仍被禁用；发布生效后任务保持暂停，恢复工单才能开工。这样停用账号可被修复，不绕过暂停状态。

## 7. 数据约束、批次与模式切换

拟议结构：排单草稿/发布批次、分配记录及事件、分配开工事件、报工来源明细、管理员生产登记事实、来源承接事实、进度更正事实、人工提成批次/明细/追加流水及结算关联。首期不需要每名师傅的拆量额度子系统。

- 数据库部分唯一索引保证同一个目标及工单版本最多一个有效分配；目标必须且仅能是计件工序或非计件步骤，FK/CHECK/触发器约束来源、订单、版本和模式。
- 新模式报工必须关联有效分配；师傅写入时人员一致且有资格；管理员受控登记另存操作人及依据。不能只有前端限制或仅用自由 JSON 表达授权。
- 首次发布前可能还没有物化工序，草稿锚定服务端生成的版本及稳定任务键；发布在同一事务物化工序、绑定真实 ID、发布分配、下发和写通知任务。
- 将 releaseFactoryOrder 提取可由外层事务调用的领域方法，不能在批量循环中开启独立事务。预览不占生产锁，发布重新核对每张单的版本及全部事实。
- 批次台账先判断重放，再执行逐单操作；已有批次成功结果不依赖打印任务是否仍待处理。同键不同载荷拒绝；原子失败无半批次，失败详情不泄露无权资源。
- 统一锁序：按工单 ID 排序获取全部工单级联锁，再按稳定顺序锁工序和分配，随后沿用报工幂等/薪资身份/工价发布/工作日/结算锁的既有相对顺序。人工工资跨多人多日期按全局稳定顺序取锁；涉及既有结算入口必须一起验证，不能只验证新命令。
- 金额、单价和数量用 Decimal；排单、核定、更正及管理员登记仅 ADMIN 可操作，师傅只对本人授权任务开工报工并读取本人工资，资源所有权在服务端重复验证。
- 通知失败不回滚已成功排单，使用事务内持久任务重试；“我的任务”为分配事实入口，通知成功不表示接单。个人通知仅在已验证的账号路由上启用。

模式入口明确如下：

| 入口 | 首期规则 |
| --- | --- |
| 新单准备待下发 | 只做业务校验，不创建分配或开放报工 |
| 新单原“下发”入口 | 启用新模式后统一转入排单并下发，服务端不得留下裸下发绕过口 |
| 旧 SCHEDULING/内部物化入口 | 按明确兼容分支保留历史模式，禁止借旧接口为新单逃避分配 |
| 已下发旧单 | 默认保持 POOL_LEGACY；无产出且事实完整的单才允许管理员原子切换 |
| 新模式工单改版审批 | 必须继承 ASSIGNED；关闭旧分配，来源承接后进入“改版待重排”，阻止无分配报工并通知管理员 |
| 上线故障暂停新排单 | 只暂停创建/发布，明确新单暂不能下发；已发布任务和结算保持可用，不自动退回共享报工 |

模式持久化在订单版本，新模式不得因改版默认值或回退开关重新开放共享写入。已有生产的旧单首期不转换，避免历史来源不明和跨人固定费的问题。数据库先兼容扩展，再升级读写，最后启用约束；旧应用不能在强约束启用后继续写新模式数据。

## 8. 修复任务与验收顺序

| 任务 | 实现范围 | 关键验收 |
| --- | --- | --- |
| T1 单人分配及批次 | 数据约束、草稿、资格、事务内下发、幂等、模式入口 | 多选跨工种分别指派；同任务第二负责人拒绝；并发发布无双分配；打印后重放仍成功 |
| T2 来源与进度 | 报工明细、自动阶段进度、包装换算、来源承接 | 多款不串量；混合烫金不重复；袋/盒/尾包正确；同次报工不拆工资不改舍入 |
| T3 人工协作提成 | 参与人登记、最终金额、差额流水、管理员登记产量、结算及全部消费方 | 无报工协作人可登记并结算；甲12改甲7乙5净额12；重复提交不加钱；已结算整批拒绝 |
| T4 更正与交接 | 当前版本受控作废、进度修正、核定失效、依赖限制 | 无工资/进度分裂；已做未报不能普通改派；跨版本/已结算更正明确拒绝 |
| T5 管理/师傅 UI | 多选、单人选择、负责人摘要、本人任务、开工、问题恢复入口 | 未指派/他人/旧版本越权失败；多工序分别开工；暂停中改安排不放行报工 |
| T6 联调和迁移 | fresh DB、历史模式、账号/工价预检、通知、文档及部署策略 | 全量 Vitest、相关 E2E、typecheck/lint、适用构建/覆盖率/架构及发布门禁 |

T2/T3/T4 必须与 T1 一起设计完成，不能先上线排单再补工资和数量约束。新模式需 T1–T6 全部完成后启用；原有数据及历史工资保持不变。管理端和师傅端执行六视口明暗主题、溢出、触控和 axe 验证。写入测试只用独立可丢弃数据库；必要真实 PostgreSQL 并发测试覆盖报工/派单、更正/结算、人工核定/结算和改版/扫码竞态。

实现时同步 SPEC、DECISIONS、API、DATABASE、操作与排障文档。明确取代原公共工种报工、订单级首次扫码认领及无分配过滤的适用范围；旧历史模式保留原语义。同步工资导出、成本统计和结算查询的消费方清单，禁止遗漏人工提成。

## 9. 对抗审查处理结果及本次验证

| 原审查问题 | 修订后的处理 |
| --- | --- |
| 多人拆量固定费归属 | 首期取消多人分配；现实协作由管理员登记最终提成，统一差额账本防重复 |
| 缺包装工价阻断下发 | 下发只提示，计件报工仍严格拒绝缺价；不认定目标环境已缺价 |
| 整单进度可被个人占满 | 新模式由来源报工自动推导阶段进度，取消自由填整单进度 |
| 来源报工/承接载体不明 | 指定父报工+来源子表及来源承接事实，保留现有计薪粒度 |
| 冲销缺受控流程 | 新增当前版本有限范围更正；跨版本/已发货/已结算明确不支持 |
| 已做未报被改派 | 普通改派仅限无产出；已有产出进入管理员接管与协作登记 |
| 未排/未完工阻塞结算 | 完成闸口不放宽，显示具体阻塞任务；不靠关闭剩余计划绕过 |
| 改版断档/模式回退 | 新版本继承分配模式，待重排明确可见，禁止自动回到共享模式 |
| 开工、批次重放、锁序 | 独立开工事件；批次台账先重放；外层单事务和明确锁序 |
