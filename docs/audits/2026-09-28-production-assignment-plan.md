# 多选排单、完工登记与提成补录方案

本方案根据用户在 2026-09-28 的业务确认修订，尚待实现。此前 8e0df592 经 Claude Code Opus 5.5 审查，fc4a50f7 为上一稿；本稿取代其中“独立开工、逐批进度、打包扫码、改版待重排”等首期要求，未声称本稿已再次通过外部审查。

## 1. 用户已确认的业务规则

| 事项 | 确认口径 |
| --- | --- |
| 生产流转 | 生产中 → 待打包发货 → 已发货；不增加其他生产进度环节 |
| 排单 | 管理员多选工单安排师傅，生产归属在此确定；不接入同任务多人拆量 |
| 师傅报工 | 实际生产完成后扫码登记，默认工单对应的生产数量 |
| 数量修改 | 需管理员审批；批准前保留生产中，不形成正式计薪记录 |
| 打包 | 独立工种，暂时不用登记，不影响生产师傅的完成状态或提成 |
| 发货 | 管理员填写工单物流信息并发货，完成业务流转 |
| 外部销售 | 后台同步生产中、待打包发货、已发货及授权范围的物流信息 |
| 忘记扫码 | 管理员可补登记，自动使用已有生产归属，不再选择师傅 |
| 提成依据 | 实际生产过就应计提成，不是工单或改版记录一生成就计薪 |
| 改版/增量 | 既有真实产出及提成保留，新增生产另记；改版新增提成打标签，由管理员补录金额 |
| 多人协作 | 管理员登记各人的提成，不增加多人扫码分产流程 |

这里的三态仅指下发后的生产发货流程；录单、核价、取消、暂停、审批和财务结算仍保留必要业务记录，不把它们增加为师傅必须逐项操作的生产步骤。

## 2. 管理员排单与归属

- 复用工单列表多选。建议每次最多 20 张、100 条生产任务；服务端同限，翻页/筛选变更清空选择并明确提示。
- 选择师傅后一次发布，同一生产任务只允许一位负责人，覆盖全部计划量。工序若合并多款，保持已有计薪分组，不为派单改变小单费及装板费边界。
- 混合生产工种按已有资格匹配；多个必需生产任务仍需分别完成，但对用户只展示统一“生产中”。打包不纳入本次必需排单或扫码清单。
- 草稿只保存安排；发布在同一事务核对订单版本、资格、数量并下发。整批失败保留输入和逐单原因，不静默跳过。
- 工单列表、详情和打印/二维码展示已有生产师傅；销售归属、生产归属、工资受益人分别记录。
- 原有生产归属不能从首次扫码、当前登录人或业务员推测。旧单确实没有归属时，由管理员在排单入口先补齐；补登记界面不承担选人职责。
- 普通调整负责人仅允许尚未实际生产的任务；已有产出不转移历史归属。实际多人协作只登记人工提成，不重新开放多位师傅对同任务报工。
- 改版保留对应任务原生产师傅及历史快照，不自动清空归属，不要求重复排单。新增工种与原师傅资格不兼容时提示管理员处理该新增任务，不重写已经发生的生产。

## 3. 扫码完成与数量审批

正常流程：扫码 → 显示工单、本人归属、生产内容及默认数量 → “登记完成”。取消独立“开始生产”、认领确认、百分比进度、逐批完成数和另外填写整单件数的输入。

- 默认数量取服务端当前有效生产任务的工单数量，多款明细自动带出。原单 1,000 个、后续仅新增 200 个时，新增任务默认 200，不能再次把总数 1,200 当作新增产量。
- 扫码人必须是已分配的生产师傅；二维码不授予权限。重复扫码显示已有完成记录，幂等重试不重复产出或计薪。
- 按默认数量登记时，同一事务保存完成事实、实际生产归属、数量和适用规则快照，并推进工单状态。
- 修改默认数量时创建申请，保存计划数、申报数、原因和任务修订号；只提示“数量待审批”，不增加一种生产阶段。待审批期间不计薪、不进入待打包发货、不允许另一笔完成绕过申请。
- 管理员批准时重新校验归属、任务版本、状态和是否已登记，按核定数量落正式完成事实；批准、计薪/待补价登记、状态推进同一事务。驳回保留原因，允许修正后重新提交，不自动按原默认数登记。
- 审批数量变化不默默修改客户订单金额、报价、物流费或销售原单数量；发货界面展示核定产量与订单数量差异，管理员核对交付明细，相关对客变更仍走原有受控入口。
- 所有必需生产任务均完成后进入“待打包发货”；打包未登记、内部提成待补录不是生产未完成。暂停、取消、待审数量和其他既有授权/资源边界仍由服务端执行。
- 实际生产数量、计薪倍率和客户订购数量分别存储，不再让师傅维护两套互相矛盾的进度。

管理员补登记：展示已有生产师傅并锁定，默认对应工单数量，填写补登说明及实际生产日期；记录操作人、来源 ADMIN_BACKFILL、归属快照和登记时间。按独立管理员命令授权，不冒充师傅登录；本人扫码与补登竞争时只能有一笔成功。管理员更改数量也必须保存核定依据，可在同一受控提交中审批并登记，不绕过审核记录。

## 4. 打包、发货与外部销售同步

打包保留独立工种和既有历史工资，不生成本流程必须完成的打包扫码步骤，不以“包 0”阻止进入待打包发货或发货，不伪造打包完成记录或工资。

- 新流程的完成条件明确排除打包登记。数据库中的既有 PACKING 工序不能被一律标为 COMPLETED/CANCELLED 来绕过校验；以明确流程策略区分“是否要求报工完成”，历史记录保留。
- 统一修改生产完成服务、发货服务端校验、列表能力、详情按钮、打印提示及外部销售状态映射，不能只改按钮文案。外协回收、地址、对客价格及合法状态校验按原业务规则保留。
- 管理员在工单填写承运商/物流方式、运单等必要信息并提交发货；校验沿用现有物流方式要求。工单进入“已发货”，重复提交不能重复出库/发货/通知。
- 已有多地址或部分发货功能保留：各票物流按原记录呈现，整体未发完时不误标整单已发货，不额外引入“部分打包”状态。
- 外部销售列表、详情、筛选计数和物流区从同一权威工单事实读取；完成审批、正常/补登记及发货后失效相关缓存，使下一次页面读取一致，不依赖单独复制一份状态或通知投递成功。
- 外部销售只看本人的授权工单；状态同步不开放内部工价、提成或其他业务员数据。通知失败可重试，不撤销真实完成/发货事实。

## 5. 已生产提成、改版及增量补录

### 5.1 保留真实生产与原提成

- 正常生产沿用现有计件规则及快照；实际生产完成才产生计薪依据，生成订单/改版/打印任务不计薪。
- 改版不能作废已经真实发生的生产，不能冲掉原工资后用新价格重算，也不能把旧工资转给后来参与的人。
- 区分“实际做过后又要重做”和“报工录错”：前者保留原提成并增加本次生产记录，后者才允许进入报工更正。
- 普通文字/资料修改且无需再次生产时，仅增加修改记录，保留完成状态和工资，不生成补做任务。

### 5.2 改版/增量的新增生产

- 对需要补做的改版、追加数量建立关联原工单的新增生产批次，冻结本次内容、数量、原因及生产归属，不复用原完成记录来计薪。
- 沿用已确定的生产师傅，不重新选人。原单未发货且新增生产尚未完成时，当前生产流转回到“生产中”，历史完成记录仍保留；已经发货的原单不倒退或改写历史物流，新增生产沿用关联补做单的交付范围。
- 普通“生产内容记录版本”与“计薪生产批次”分开。旧二维码/旧页面不能把旧完成记录再次提交成新生产，必须明确显示本次版本和数量。
- 新批次显示“改版补做”或“增量生产”，提成字段标“待补录提成”。生产完成后保留待补录金额，金额为空，不是 0，也不凭新旧总量差自动套计件价。
- 管理员按本次生产批次录入提成总金额、生产师傅及依据；已有归属师傅自动带出并锁定，补录金额对应本次生产，不覆盖旧单提成。允许先存草稿，但实际生产完成后才可正式计入工资。
- 本方案把改版引起的增量一并走人工补录，避免同一改版一部分重复自动计薪。正常新单仍走正常计件；独立新订单不因与旧单有关就自动视为改版。
- 待补录标签显示在管理员列表、详情及工资待办，可按该标签筛选；师傅工资显示“待管理员补录”。补录后显示金额、登记人和时间，并解除对应待办。
- 待补录不阻止真实生产完成、待打包发货或管理员发货；只阻止包含这笔未定工资的相关人员/实际工作日结算，防止漏发。不得将内部工资待补录混同为对客价格未确认。

例：原单 1,000 个已完成并计薪，改版再生产 300 个。原 1,000 个的生产师傅与提成保持不变；新增 300 个完成后显示“改版补做 · 待补录提成”，管理员填写本次金额后单独入账。两次都实际生产过，两次都有计薪依据，互不抵消。

### 5.3 多人协作与人工账本

- 多人协作保留单一生产归属和一份生产数量，管理员选择实际参与人登记最终应得金额；参与人选择只出现在协作提成登记，不出现在正常补登记或改版补价中。
- 现有人工核定只能调整有 REPORT 锚点的人，因此需补充无报工参与人的人工工资事实及结算关联，不能伪造报工数量或零数量 REPORT。
- 普通自动计件转为人工协作核定时，按已有净额记录差额，避免自动金额和手工金额双发。例如原甲 12 元，核定甲 7、乙 5，追加甲 -5、乙 +5，净总额仍为 12。这是该次工资分配核定，不是因后续改版扣回已经挣得的工资。
- 改版补做批次不先自动计件再补一笔全额；生产事实与待定人工金额分开，正式发布的人工金额只入账一次。
- 每笔人工工资记录生产批次、受益人、实际工作日、数量依据、金额/差额、原因、操作者、修订号和幂等键；金额 Decimal，修改只追加修订差额。
- 工资结算、人工费用/成本、师傅工资、汇总和导出统一消费新增事实；支持某人某日只有人工提成也能结算，每条事实最多结算一次。
- 已结算原单可以有后来真实发生的新生产及新工作日工资，不重开原结算。不得在已锁定的旧工作日偷偷追加历史补价或移到另一日规避，未及时补录的旧日工资显示具体阻塞原因并进入受控财务处理范围。
- 多人核定涉及的人员/日期均须可调整；存在已锁定部分时整批拒绝。标记待补录与日结共用锁和前置查询，未形成金额流水的待办也必须参与结算检查。

## 6. 数据、权限与异常边界

拟议新增/扩展：排单及归属快照、完成登记与来源明细、数量变更申请、补做生产批次及版本关系、待补录工资义务、人工工资流水/结算关联、业务审计。取消上一稿的独立开工事件、多人分配额度、包装进度换算和逐批进度管理。

- 工单归属用于确定生产人，操作人单独记录。完成事实需区分本人扫码、管理员补登、批准数量变更；管理员无须重新选择受益师傅。
- 明细保存本次实际完成数量与冻结的任务来源，以后可以说明某次生产对应哪些款式；同次正常报工保持现有计薪边界，不因多款拆行重复固定费。
- 数据库唯一约束防同任务多位有效负责人、同生产批次重复完成、同数量申请重复批准和同工资事实重复结算。所有写入事务重读状态/版本，不信任页面缓存和客户端合计。
- 事务内一致完成：审批/完成事实、待补录或正常工资、工单状态和通知任务。正常计件缺价不以零价放行；改版人工计价模式须有明确待补录事实，不能借此绕过正常单的工资规则。
- 现行 ProductionReport 写入绑定有效工价及工资快照，改版人工待价不能往该表写虚构零价。新增可独立存在的生产完成事实，既有正常工资报告关联该事实，改版待价工资另行补录；同步升级完成闸口、读模型和工资结算，禁止两边分别累计同次产量。
- 批量发布提取事务内下发方法，整批一事务；先检查批次重放，再调用逐单逻辑，重试结果不依赖打印任务是否仍待处理。按稳定顺序获取工单/生产任务锁，并保持薪资身份、工价、日期、结算锁的既有相对顺序，验证和结算的竞态。
- 已有产出归属不自动转移；账号停用不改历史身份，管理员可以按原归属补登真实生产。补登保留实际生产日和录入时间，不冒充本人操作。
- 真实产出被改版淘汰也不属于错误报工。真正重复/误登记的更正需管理员原因、追加审计和同步数量/工资处理；首期只支持未发货、未结算且无后续承接依赖的错误记录，不能用作扣回真实已生产工资。
- 暂停/取消、外协、对客金额、已发货单修改及历史结算限制继续执行；新增补做不通过修改原已发货订单数量绕过这些限制。

## 7. 迁移、受影响代码与验收

现有依据及必须同步的入口：

- [生产下发](../../lib/order/admin-workflow.ts)、[工序物化](../../lib/production/operation-materializer.ts)：加入批量归属及简单流程策略，保留打印和幂等。
- [报工](../../lib/production/operation-reporting.ts)、[生产进度/扫码](../../lib/production/work-order-progress.ts)：改为完成登记/审批，不保留新模式可绕过归属的旧报工写入口。
- [生产完成闸口](../../lib/production-completion.ts)、[管理列表](../../lib/order/admin-workspace.ts)、[发货能力](../../lib/order/shipping-availability.ts)：统一去掉新流程对打包扫码的依赖；发货实际写入口同步校验。
- [烫金工资](../../lib/salary/foil-report-wage.ts)、[人工核定](../../lib/salary/order-wage-review.ts)、[结算](../../lib/salary/piecework-settlement.ts)：保留正常单规则，接入改版待补价、协作人工工资及结算防漏。
- [改版承接](../../lib/production/version-carryover.ts)：保留真实历史产出和提成，新增补做批次不把旧工资抵掉或重复计入。
- 实现前列全外部销售列表/详情/状态计数、工资/成本/导出、通知、SQL 触发器和历史模式消费方；按[贡献规范](../../CONTRIBUTING.md)验证，同步 SPEC、DECISIONS、API、DATABASE 和[文案规范](../ui-规范.md)。

新流程策略按生产批次/订单版本明确记录，改版继承策略和生产归属，不能默认退回公共报工或变成“待重排”。历史生产/打包/工资/物流事实不删除、不伪造完成；迁移只新增前向 SQL。旧单无明确归属须管理员先核实，不能从首次扫码猜测。上线先兼容读写，切换新流程后再启用强约束；暂停新排单不重新开放共享报工。

| 任务 | 范围 | 关键验收 |
| --- | --- | --- |
| T1 批量排单及归属 | 单负责人、幂等、资格、归属继承 | 并发无重复指派，旧二维码不越权，补登记不出现选师傅 |
| T2 完成登记及审批 | 默认数量、申请/批准/驳回、管理员补登 | 默认一键完成；变数量待批准；本人/补登/审批并发只记一次 |
| T3 三态及发货同步 | 打包免登记、物流、管理端与外部销售 | 师傅完成即待打包发货；打包未登记不阻断发货；各端状态及计数一致；部分发货不误完成 |
