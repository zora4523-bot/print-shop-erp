# analytics 经营概览重构方案（待实现）

用户要求：规划 analytics 页面重构，学习 `/Users/zhixing/历史订单` 的看板实现，不影响其他功能。本文是可审查的实施方案；本次仅新增此文档，没有修改页面、查询、数据库或业务流程。

## 1. 目标与现状证据

目标是让管理员在同一分析页面回答：选定期间接了多少工单、向客户收取哪些费用、收到多少货款、哪些客户和工艺贡献较多、已记录哪些成本，以及采购与库存是什么情况。

当前实现：

- [页面入口](../../app/(admin)/owner/analytics/page.tsx) 执行 `requirePermission('report:all')`，沿用管理员页面壳，标题为“经营概览”。
- [页面组合](../../components/business/dashboard/OwnerAnalytics.tsx) 只有近 30 天产量、本月销售 Top 10、本月产品分布；每块独立加载与失败反馈。
- [现有统计查询](../../lib/dashboard/owner-charts.ts) 把时间窗口固定在近 30 天或本月，没有可选年月、客户/销售筛选、逐单明细或导出。
- 2026-10-03 已读取用户浏览器中 `/owner/analytics` 的页面结构并查看浅色桌面实屏。固定时间窗口和缺少筛选与源码一致；当前筛选期间没有记录不能说明全库没有数据。没有执行交互回归或完整 UI QA。
- 产品分布按“每个类目内不同工单”计数；跨类目工单会进入多个类目，不能把各类目计数之和当作唯一工单总数。

参考项目为 `/Users/zhixing/历史订单/finance-dashboard`。已审阅其 `README.md`、`dist/index.html`、`dist/app.js`、`dist/advanced.js`、`dist/profitability.js` 及收费核对的实现结构。它用整理脚本生成静态数据，浏览器统一筛选后渲染汇总、分类图、分页明细和 CSV；点击分类进入明细，并可追溯原文件、工作表与行号。

借鉴其“选范围 → 看汇总 → 看分类 → 核对明细”的分析路径，以及缺失金额、成本覆盖和来源区分。ERP 继续使用实时业务查询、已有设计系统和业务记录；参考项目的静态金额、浮点累加、全量浏览器过滤、试算参数及客户专页不直接移植。参考项目的视觉实屏未查看，本次依据为本地源码与文档。

## 3. 页面组织

保留一个经营概览入口，建议在页内组织五个视图，避免复制参考项目的十三个导航项。

| 视图 | 主要内容 | 用户可继续核对的记录 |
| --- | --- | --- |
| 经营总览 | 提交工单数、加工费金额、已出账、已收款、当前待收款；提交/完工趋势；销售排行与产品分布摘要 | 对应工单、账单与收款记录 |
| 订单与收费 | 销售与客户维度、工单数量和加工费、收费构成、待核价与已结算分别查看 | 分页工单及收费明细 |
| 成本与差额 | 同批工单的计件、外协、手工成本、重做成本；已记成本后的差额及覆盖情况 | 成本来源、原工单与重做单 |
| 工艺与纸张 | 工艺、纸张、规格的工单数与数量；原有产品分布的完整分析 | 对应款式、纸张与数量明细 |
| 采购与库存 | 采购与实际收货数量、原采购单价、供应商分布、当前库存与缺料 | 采购单、收货单、物料及库存流水 |

页面纵向顺序固定为：标题和操作 → 时间/销售筛选 → 视图切换 → 当前范围与汇总 → 图表和分类表 → 分页明细。汇总优先，图表以便于比较的折线与横向条形为主，精确值保留在文字和表格中。页头不新增与面包屑重复的返回按钮。

默认仍为本月；提供上月、近 30 天、本年和自定义区间，方便在月初查看已有月份。保留“近 30 天产量”快速入口，不静默跳到某个有数据月份。长区间按月展示，短区间按日展示。

手机上筛选可换行、指标分行、图表单列；分类图保留完整文字与数值。明细复用已有响应式表格/卡片能力，不用整页横滚承载桌面布局。

## 4. 筛选与核对交互

- 时间区间与视图写入 URL，刷新、复制链接及浏览器前进/后退能恢复；每次读取重新验证权限和筛选参数。
- 时间、外部销售可用于相应事实源。客户、工艺、纸张、产品与供应商按视图提供，不把某款纸张筛选强行用于整张月账单收款。
- 账单收款未分配到逐客户或逐款式时，不按工单占比推算。界面明确该区块适用的范围；“当前待收款”和“当前库存”明确为当前余额，不跟随历史日期伪装成当时余额。
- 点击销售/分类后显示选中条件，明细回到第一页；清除局部条件保留时间范围。搜索和分页不会让汇总悄悄变成“本页合计”。
- 图表、汇总、明细及导出共用同一已校验筛选对象。切换期间标记正在更新，不将旧结果标为新范围；慢请求不能覆盖较新的选择。
- 每块继续有加载、空态、失败原因与重试。真实无记录、待核价和读取失败分别呈现，不用全零数组掩盖失败。
- 从明细打开已有工单、账单、采购或物料详情。首期不在看板内增加录成本、确认账单、标记收款、改价或调整库存按钮。
- CSV 导出放在后续批次，导出当前筛选的完整结果，不只导出当前页；使用已有 CSV 安全处理和金额格式，服务端再次验证权限，超限必须明确提示而非静默截断。

## 5. 数据映射与口径

以下是已经核对到的模型/代码能力，不代表已读取实际数据库或证明数据齐全。

| 指标 | 已有事实源 | 实施口径 |
| --- | --- | --- |
| 提交工单数 | `Order.submittedAt` | 按上海业务日归属；与原排行一致排除取消，收费、免费和重做的数量分别可核对 |
| 加工费与销售排行 | `Order.processingAmount`、`submitterId` | 保留原按提交时间、正加工费、非取消的销售排行口径；标为加工费，不冒称实际收款；销售归属使用工单记录，不取代建管理员 |
| 已结算金额 | `Order.settledFee`、`settledAt` | 与提交加工费分开呈现；包含不同日期与收费范围的事实不得直接相加。已确认账单对账使用保存的工单金额与跨月调整 |
| 已出账金额 | `AgentMonthlyBill` | 按确认日期，状态为已确认或已收；草稿不计。沿用工作台现行定义 |
| 已收款金额 | `AgentMonthlyBillReceipt` | 按实际登记的收款日期，独立于账期和工单提交日期 |
| 当前待收款 | 已确认未收款的 `AgentMonthlyBill` | 不限账期；与现有账单列表一致，不用“本期出账 − 本期收款”计算 |
| 收费构成 | `OrderItem`、包装组、`OrderCustomerCharge`、价格修订与账单结算明细 | 优先已有公开收费分解；加工费内包含的入袋费不得再加一次。不同代际收费无法可靠拆分时保留未覆盖金额 |
| 已记成本 | 生产账本、外协金额、`OrderCostEntry`、重做关系 | 复用 [现有成本分解](../../lib/bill/costing.ts) 的代际优先、历史回退和去重规则，不能简单相加所有成本表 |
| 工艺/纸张/数量 | `OrderItem.craft`、`crafts`、`paperType`、规格及 `quantity` | 使用实际工艺和材料维度，不用旧计价路由代替工艺；同一工单跨类别允许出现多次，明确此类工单数不可相加 |
| 采购与收货 | `PurchaseOrderItem`、`PurchaseReceiptItem` | 下单与有效收货分别统计；有原单价才算已知金额，保留空单价及取消收货的边界 |
| 当前库存 | `Material`、库位库存及 `MaterialTransaction` | 使用现有库存事实与单位；不同单位、材料、规格不混算。仅在数量和成本均已知的覆盖范围展示库存参考金额 |

依据：[现有图表查询](../../lib/dashboard/owner-charts.ts)、[工作台账单统计](../../lib/dashboard/owner-stats.ts)、[结算分解校验](../../lib/agent-monthly-billing/settlement-detail.ts)、[Prisma schema](../../prisma/schema.prisma)，以及 [DECISIONS](../../DECISIONS.md) 中 2026-04-26 排行归属、2026-09-24 月账单/销售角色、2026-10-01 结算更正的现行决策。

必须保留的财务边界：

1. 金额在数据库/Decimal 中聚合，跨服务端边界传十进制字符串。图表几何可转换为 number，最终金额、合计、排序与比率不依赖前端浮点累加。
2. 时间统一用上海日历与起止边界；已结算、已出账、已收款分别使用自己的事实日期。未结束的本月不能直接与完整上月计算增长率，上一期为零时不显示无意义百分比。
3. 客户所付的快递费、材料费和包装费是收费事实，不能直接当工厂成本。采购金额、领用成本和手工记账如有重叠，遵循既有来源去重；工序计件、完工提成与工资发放不再次累计成多份成本。
4. 成本比较先选定同一批工单。重做成本归入原单时，不能又把重做单成本作为独立工单加一次；取消单的成本不得因收入筛选而静默丢失，应另列可核对记录。
5. 没有成本记录不等于全部成本为零。展示哪些成本有记录、哪些金额待核；在完整成本尚无可靠证明时使用“已记成本后差额”，不标“毛利”或“净利润”，不把采购与客户收费简单相减。
6. 收费占比优先在可可靠分解的范围计算，并同时显示覆盖情况；多工艺和跨产品工单不任意分摊整单收费。缺旧明细时保留整单已知金额，分项保持未知，不用今天的价目补算。
7. 已确认账单保留其保存金额与分解，抵扣/补收独立反映；旧 `Bill`/`BillPayment` 不与新月账单直接混合或重新解释。

用户说明参考看板的数据在当前项目已有。订单、收费、成本、生产、采购与库存已有明确代码入口；淘宝平台交易、推广实际消耗、报销状态和“大表哥”客户专页在本次检查的当前模型中尚未定位到明确映射。此处记录为“待核对数据入口”，不据此断言用户没有数据，也不把现有 CUSTOM 成本或收款备注猜作平台交易。找到稳定来源与关联键后可纳入相应视图，暂不建立虚假指标或新增导入流程。
