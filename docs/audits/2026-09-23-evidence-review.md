## 1. 审查方法与边界

- **只读审查**：基线为 `92901fd9`，审查期间工作区推进到 `1b6c5219`。审查先建立攻击面与业务流地图，再按风险切成 20 个切片，完整性评审后又补查 5 个空白切片。每条发现都由独立验证者尝试推翻，高危项用两个不同视角各验证一次，有分歧时加一轮裁决。3798 条命令记录经复核，全部为只读命令；例外只有两条纯 decimal.js 算术 `node -e` 和一条 `node --version`。依赖公告只从官方公告页查询。
- **覆盖面**：生产相关源码 978 个文件中实际阅读了 526 个，另外对全部页面、Server Action 和 Route Handler 的鉴权闸口做了机械核对。组件层（`components/business` 43/278、`components/ui-business` 0/31）只做了抽查，约 160 条迁移没有逐行阅读（触发器已补查）。审查没有做运行时复现，也没有核对生产配置。
- **整改流程**：8 条修复流各用一个独立 worktree（最多 4 条并行），逐条执行：复核 → 先写失败的回归测试 → 最小修复 → 目标测试、eslint、typecheck → 按明确路径提交 → Codex 只读审查。Codex 在审查途中触达用量上限（恢复日期 2026-09-28），之后的提交改由人工复核。集成阶段由另一组只读对抗审查（8 个审查代理加验证者）覆盖全部提交，只确认了 1 项问题，即 L-11 只做到部分修复，见 §4。
- **工作区隔离**：审查和整改都没有写主检出。主检出 `git status` 和 `git diff HEAD` 的哈希在整改前后一致，并行会话的在制改动保持原样。

## 4. 未处理与待业主拍板

- **H-3 / B8：取消费是否进代理商月账单。**`docs/工单变更与版本规则.md:103` 规定有 `settledFee` 就要收。HEAD 上 `86603e71` 的对账闸口会让含取消单的代理商整月出不了账，而工作区的未提交改动把 CANCELLED 从候选中剔除，取消费会被静默漏收。两种状态都未发布，业主本轮决定暂不动。
- **H-2 冲销金额口径。**现按 DECISIONS 2026-08-02 冲销全额。有产量的取消单里保留的 settledFee 是否仍算客服业绩，需要业主确认。
- **M-4：「部分发货后取消剩余」的结算口径（N-2）**尚未实现，目前一律拒绝。申请入口仍按工单状态显示，用户提交后才看到拒绝提示，没有提前隐藏。
- **L-11 剩余缺口。**周期结束次日 00:00 到 cs-settle 实际执行完之间（约 1 分钟加上排队时间），内部客服单的提交、取消、改单和核价会失败。另外，当天结算失败时这段窗口会持续一整天，可由管理员手动结算恢复。彻底消除需要预建下一周期，但预建有两个副作用需业主定：`ensureInitialCsPeriodInTx` 可能取到未来周期；复用预建周期时不会比对 monthlyBase。生产主机的 crontab 需要运维按部署指南重新安装。
- **M-6 附带问题**：直营单确认后如何取消、SUBMITTED 能否驳回，均需业主定规则。
- **M-7**：只处理修复上线后发生的升版；在此之前已经卡住的旧代次，要等该工单下一次升版才会终止。
- **N-3** 客服离职闭环；**N-4** SQL 冲正后进度不可更正；**N-6** 工单级只读视图是否按车道收紧；**L-16** 推送摘要口径。以上均需业主决策。
- **在制改动的缺陷（交给作者）**：
  - **M-15**：发货闸口和改单承接仍把 CLEANING 当作未完成步骤。
  - **L-17**：时薪月结 cron 仍为在职的退役账号生成月结；编辑账号会删除未发月结。
  - **N-5**：退役账号显示为「活跃」却无法登录。
  - H-3 中工作区剔除 CANCELLED 的改动也属于同一批在制改动。
- **既有 E2E 失败**：`inventory-flow`（首笔出入库）、`owner-dashboard`（夹具写旧 Bill 表），需要另立任务处理。
- **仍未决的旧审计项**：生产无外部告警、P0-7/B2、P1-1/B5、P1-2、P1-8/B3、B7 等，见 09-21 首次使用就绪审查（`docs/audits/2026-09-21-first-use-readiness.md`，该文件目前只在主检出中、未提交）。
