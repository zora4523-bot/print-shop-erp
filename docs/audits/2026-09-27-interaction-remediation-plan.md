## 4. 批次 B：采购/BOM 补资料的输入恢复

### B1 · 推荐交互与范围

继续使用现有独立资料新建页，给来源表单增加**当前浏览器标签页内的录入暂存**。这比为多种资料表单新建嵌套弹层范围更可控。用户在采购/BOM 内“新建物料”“新建供应商”时，先保存原表单，再进入资料页；创建成功、取消、浏览器返回，都回到原录入并保持字段。

同一 BOM 内现有“新建分类”等补资料链接一并纳入来源保护；批次 A 新增的“管理供应商”也不能绕开。物料、纸张、分类的专用创建权限与类别限制不合并、不绕过。

有明确且匹配的返回上下文时自动继续原录入；普通再次打开新建页时显示一次“继续上次录入 / 重新填写”，不悄悄填入旧内容。不同标签页的改动不得相互覆盖，不跨账号或跨设备自动恢复。保留新建页独立使用时原有返回详情/列表行为。

### B2 · 状态与返回协议

1. 采购和 BOM 采用可序列化的完整表单模型，金额/数量以原始字符串保存，允许保留用户尚未填完的 `0.` 等内容。BOM 保存适用对象、全部目标字段、名称、版本、基准产量、每行物料/用量/备注及稳定行标识；不能只存当前可见行，也不能把数组下标当永久身份。采购按完整字段清单覆盖供应商、物料、数量、单价、日期、备注等。
2. 存储采用 `sessionStorage`，键由当前登录用户 ID、表单类型、随机 draftId 组成；记录 schemaVersion、保存时间、payload、目标行/字段和一次性返回 nonce。暂存上限建议 24 小时，条数和容量有界；只保留白名单业务字段，不存凭据、action token、内部报价结果或完整服务端对象。
3. 表单输入变化更新内存并暂存；离开补资料入口前必须同步完成最后一次写入。首次挂载先解析合法草稿再启用写回，避免空默认值覆盖草稿。浏览器后退/前进和刷新恢复不依赖 Link 事件或 `beforeunload` 是否触发。
4. 身份由服务端提供，客户端不能自行声称所属用户。保持原生登出表单和 `signOutAction`，不把退出登录改成依赖 JS 的回调。**登录页不删除草稿**，未登录时不展示或恢复内容。只有在管理端外壳拿到当前已认证身份和授权后，才由独立清理组件删除非当前用户、无对应操作权限及过期草稿。无 JS 登出只保证注销成功，存储清理延后到下一次有 JS 的已认证挂载；任何用户不匹配的内容都不允许恢复。同一用户会话过期后重新登录只能经显式确认继续未过期内容，不能把旧返回 nonce 当作免确认依据。落实方式：在现有认证 JWT 回调的成功新登录分支生成非凭据的 `draftSessionScope`，普通 token 刷新保留它，通过 session 类型和服务端表单上下文传递；草稿/返回关联保存同一标识。恢复先取得当前已认证上下文，scope 缺失或变化时旧 nonce 不自动消费，只能显式续填；确认后绑定新 scope，但保留原创建请求键，避免重复建单。该标识仅决定恢复提示，不替代授权。恢复前校验 TTL、schema、行数/字段上限和 shape；旧 schema 只做明确受支持的迁移，否则提示重新录入。
5. 来源协议只接受枚举化的 `purchase-new` / `bom-new` 及被允许的资料类型，映射为固定本地路径；draftId/nonce 只关联当前标签页，不构成权限凭证。服务端拒绝绝对 URL、协议相对 URL、未知路径和伪造类型。涉及管理列表时也只能返回白名单来源。
6. 创建成功只回传新对象 ID、资料类型及关联上下文，不把表单内容放进 URL。返回页重新读取有权限且当前启用的对象；供应商须 SUPPLIER/BOTH，物料类别/分类目标须适用。只有匹配 nonce 和稳定目标字段时回填一次，再消费返回参数；普通后退或旧链接不能反复覆盖用户后来选的对象。
7. 资料新建失败保留该资料页输入和来源草稿；取消创建回原单但不覆盖选择。BOM 删除目标行后收到旧返回结果时，不插到别的行，只提示重新选择；新增、删除其他行也不能错位。
8. 来源单据保存成功后清除草稿；校验失败、权限失败、网络失败、提交结果未知时保留。当前 action 成功会 redirect，不能指望来源组件收到 success：表单提交合法 draftId 与创建请求键，action 跳到详情时带不含表单内容的回执标识，详情页经授权查询创建请求记录，将“本用户、本类型、本 draftId 对应实体已创建”的确认传给清理组件。回执通过现有 `lib/admin/receipt.ts` 的 `appendReceipt` 生成，在 `RECEIPT_KEYS` 中登记受限新键。单凭 `created=1` 不清草稿；清理后写完成标记，阻止旧 effect 或后退页复活草稿。
9. 存储写入失败不能继续静默跳走。保留原页面，显示“无法暂存当前内容，请在新标签页补充资料”；提供 `noopener` 的新标签页入口和显式“更新可选资料”动作，仅更新选项，不重置表单。无 JS 时补资料入口默认新标签页，保留普通表单提交能力，不宣称提供 JS 草稿恢复。

10. 浏览器复制标签页可能复制 sessionStorage，因此“不串单”不能依赖其初始内容一定为空。本功能各页面持有内存 documentId 并通过同源 BroadcastChannel 声明活跃 flow 所有者；新打开/复制标签检测冲突后不得自动消费返回 nonce，只能显式选择另建独立草稿，或回原标签页。返回上下文在来源页与资料页交接所有权：等待一个有限探测窗口，未收到冲突声明且来源、当前会话、服务端回填验证均匹配时可以自动继续；交接未完成、服务端查询超时或收到冲突均不能确认，要手动选择对象。探测用于防误填，不充当授权或创建去重保证，后台标签未及时应答也不能绕过服务器请求键保护。复制页在服务端查询原请求状态前沿用旧请求键；状态未知时不换键。确认原结果后，只有用户明确选择“另建一单”才同时生成新 draftId/新请求键；“继续原录入”始终沿用旧键。相关查询与在途提交按同一请求锁协调，不能把尚未提交可见的记录当成确定失败。

### B3 · 提交结果未知与重复创建保护

恢复草稿不能诱导重复采购。针对本批采购和 BOM 创建增加小范围的请求记录，不用“检查最近单据”代替去重：

- 建议新增 `FormCreationRequest`，包含 actorId、kind（采购/BOM）、clientRequestId、draftId、规范化业务载荷 hash，以及 PurchaseOrder / BillOfMaterial 的唯一目标引用。`(actorId, kind, clientRequestId)` 唯一，DB CHECK 要求恰有一种目标且与 kind 匹配；记录与业务实体在同一事务完成，不提交孤立的处理中记录。
- 服务端给首次页面生成请求 ID（无 JS 也有隐藏字段），浏览器恢复草稿时沿用同一 ID；另开一张新单才生成新 ID。领域层先授权，在请求键锁内查旧记录；同键同事实返回原实体，同键不同事实明确冲突。hash 取用户明确录入且规范化的业务事实，不含生成单号、当前时间或可变化的资料显示名。
- `createPurchaseOrder`、`createBom` 的创建、请求记录、必要审计保持同事务；SQL 唯一约束兜底并发。提供经权限检查的请求状态查询，页面重新出现时优先核对是否已创建。已确认成功即给“查看已创建单据”并清理对应草稿；未知时保留并允许使用原键重试，不能默认换键再创建。
- 请求已成功但浏览器后来改了草稿：先展示原单据和差异，不能把新内容伪装成旧请求重放；明确选择“另建一单”才分配新键。请求记录保留期间不能清理到失去去重保证；初版不自动清理，记录量/保留策略在后续运维设计中明确。
- 新协议要覆盖无 JS 提交和升级前旧表单：带本功能 draftId 的提交必须有合法请求键；旧无草稿表单可以保持兼容，但不能被纳入自动恢复/重试承诺。给旧表单清楚的刷新恢复路径，不静默丢弃已填内容。

本批因此包含一个前向迁移、创建领域服务的小范围事务整理和真实 PostgreSQL 并发/响应丢失验证，不再视为纯客户端 UI 改动。

**主要改动**：[采购表单](../../components/business/purchase/PurchaseOrderForm.tsx)、[BOM 表单](../../components/business/bom/BomForm.tsx)，对应 new/详情页面；`actions/owner-parties.ts`、`actions/owner-materials.ts`、相关分类创建 action 的受限返回处理；`actions/owner-purchases.ts`、`actions/owner-boms.ts`、`lib/purchase.ts`、`lib/bom.ts` 的创建请求去重；资料页返回按钮、外壳身份清理组件、`lib/auth/config.edge.ts` 及 session 类型的草稿会话标识、新 schema/迁移。新增仅供这些业务复用的草稿序列化/存储/返回协议模块，不重构工单已有本地草稿系统或改变认证授权策略。

### B4 · 验收矩阵

- 原问题三条路径必须复跑：采购 123 / 2.5 / 备注→新建物料→返回；采购→创建供应商→自动返回；BOM 两行 11/22→删除首行→补物料→返回，保留名称和 22。
- 补分类、打开供应商管理、创建失败、取消、刷新、后退/前进、二次返回、目标行删除、多个标签页、草稿过期/损坏/存储不可用；特别覆盖同用户会话过期→重新登录→显式续填，以及换账号后旧草稿不可恢复且挂载时清理。
- 新对象已停用/不适用/无权访问：保留其余录入、拒绝无效回填并定位字段。伪造 returnTo、draftId、nonce、对象类型不可越权、不可开放重定向。
- 保存失败不清草稿，保存成功不复活旧草稿；提交成功但响应丢失→重进/刷新/重试只创建一份；同键异内容拒绝、跨用户请求键不可访问、复制页不能无提示重复建单；缺 JS 登出仍可用。新登录 scope 变化、普通 token 刷新 scope 不变、旧 token 无标识、会话过期后带旧 nonce 返回都须覆盖；认证回归不得减少。新建字段恢复后真实提交到独立数据库，核对存入的数值及物料行关系，不能只测存储 helper。新迁移验证 fresh DB 和升级，记录 PostgreSQL 测试实际执行数。

## 5. 批次 C：仓库与库位的维护闭环

### C1 · 业务行为

每个仓库/库位提供“改名”，以及随状态切换的“停用 / 恢复使用”。仅修改名称；业务编码、所属仓库、默认标记本批不可改，不提供物理删除。启用与停用记录都能在设置区找到，避免停用后失去恢复入口。

仓库停用不批量改写子库位的独立 isActive 标记；有效可用性仍是“仓库启用且库位启用”。恢复仓库只恢复此前自身启用的库位，不把用户单独停用的库位一起启用。停用仓库下的库位恢复前，先提示恢复所属仓库。

默认仓库/默认库位不允许停用，明确显示原因。存在任一物料非零库存时拒绝停用，不同物料数量不相加抵消；停用仓库检查全部子库位。库存已清零且只有历史流水的非默认位置可以停用；历史单据继续显示并保留引用。改名会让引用该基础资料的页面显示新名称，审计保存旧名称，不改历史库存数量/金额/单据 ID。

当前采购单没有预选库位，调拨与盘点在提交事务中完成；因此不能因为“系统里存在未完成采购单”就禁止所有仓库停用。实现前核对所有实际 locationId 消费方，只有真实绑定目标库位且尚未结束的预约/单据才成为阻碍，并给到该单据的链接。现有历史收货撤销若命中已停用位置，提示先恢复库位；不借此允许普通写入绕过停用。

### C2 · 服务端与并发

- `warehouse:manage` action 做 Zod 校验；领域事务再次校验管理员权限、目标状态、默认标志及库存。带 expectedUpdatedAt 并严格单调推进（同毫秒也至少递增 1ms），避免改名/启停覆盖别人刚做的修改；重复设置同一状态且请求事实一致返回已完成，审计不重复。
- 新增仓储配置读写协调锁：仓库/库位维护事务先取得独占锁；**所有**库存业务写入事务先取得同一共享锁，再按现有顺序获取幂等、采购单、物料等锁。共享锁允许普通库存写入互相并发，配置变更期间等待。
- 接入点包括手工出入库、调拨、采购入库/取消入库、盘点过账，以及创建库位、初始化默认库位等配置写入。顶层事务入场取锁，先于现有物料价格协调锁、请求幂等锁、采购行锁和物料行锁；不能在持有其他锁后才补锁，也不能在同一事务从共享锁升级独占锁。列出所有 `applyMaterialStockMovement` 调用方及盘点直接写库存的分支，核对后才交付，并覆盖已有 `material-price-snapshot-lock.postgres.test.ts` 的顺序契约。
- 停用在独占锁内检查所有关联库存与实际未完成引用，再更新状态并写同事务审计；库存写入在共享锁内重新检查仓库和库位状态，不能只相信下拉框旧选项。维护等待锁后重新读取，不沿用旧预览。
- 审计记录操作者、对象、名称/状态前后值；事务失败不写成功记录。沿用现有 isActive、updatedAt，原则上无需表结构迁移。若检查发现 DB 约束必须扩展，只加前向迁移并纳入 C 的验收，不修改旧迁移。
- 失效仓库页、库存页、物料详情、采购收货选择器等实际消费路径；禁用的当前选项不能被静默替换为默认库位。

**主要位置**：[仓库领域](../../lib/warehouse.ts)、[仓库动作](../../actions/owner-warehouses.ts)、[仓库表单](../../components/business/warehouse/WarehouseForms.tsx)、仓库页面、`lib/material.ts`、`lib/stock-transfer.ts`、`lib/purchase.ts`、`lib/inventory-count-posting.ts`、相关 schema/审计与 action 类型。

### C3 · 验收

错名创建→改名→选择器显示新名→空库存停用→旧表单提交拒绝→恢复后可选；默认、有库存、多物料、多库位、父子状态组合、历史流水均覆盖。

真实 PostgreSQL 双事务屏障测试：停用与入库/调拨/盘点/创建库位竞争；至少验证两种锁先后顺序及超时回滚。必须得到“写入先完成则停用按新库存拒绝”或“停用先完成则写入拒绝”，不能出现停用后新增库存。审计、库存总量与分库位总量一致，权限拒绝不改数据。

## 6. 批次 D：尚未生效的工价计划可取消

### D1 · 采用的业务方案

统一工价与个人工价都提供“取消调价计划”，**仅取消用户选中的一版未生效计划**。设当前或前一版 P 的结束时间等于 S 的开始时间：取消 S 后，将 P 的结束时间改为 S 原结束时间；S 是尾版时恢复为 null。后面的 S2 等计划保持原费率、模式、生效时间和身份，不需要用户记下再重建。

这是基于真实约束的单版撤回，不引入任意重排或中间插入发布：现行 successor 约束允许 P 的结束时间连接同范围、版本号更大的 S2；客户价计划已有同类区间衔接做法。复核只展示 S、其原生效窗口、恢复使用的 P/统一价，以及下一版 S2 的时间，不把 S2 列为取消对象。

取消成功后保留历史版本并显示“已取消”，提供继续编辑现有草稿或新建调价草稿的入口。已有草稿不覆盖、不删除、不自动发布；差异基准按拟生效时间重新读取。**取消最后一版且没有其他未来计划后**可立即发布纠正价，覆盖原问题的“错误未来个人价→取消→立即恢复统一价”。如果仍保留其他未来计划，沿用现行只能追加发布的限制，明确提示其生效时间和查看入口，不再使用模糊“晚于上一版”；本批不承诺保留未来计划时仍能插入一版立即调价。草稿“放弃”能力暂不扩展。

### D2 · 状态、迁移与历史不变量

建议扩展 `PieceworkPriceBookStatus` 的终态 `CANCELLED`，增加 cancelledAt、cancelledById、cancelReason、cancellationId。新增不可变的 `PieceworkCancellation` 操作记录：唯一请求键、操作者、范围、目标版本、目标原始起止时间、前一版 ID/原止期/新止期、后继 ID 和规范化请求 hash。目标一版只对应一次取消，目标及前版有实际外键；记录与被取消行的对应关系在提交时校验。保留原 effectiveFrom/effectiveTo、规则、哈希、发布证据、版本号，不复用版本号或物理删除规则。

当前 [schema](../../prisma/schema.prisma) 及迁移中的约束，实施必须一起处理：

1. `protect_piecework_price_book_history`：仅放行受操作记录约束的 PUBLISHED→CANCELLED，以及 P 的结束时间从 S.effectiveFrom 改成 S 原 effectiveTo（包括 null）；目标的其他原始字段不变，前版除 effectiveTo/updatedAt 不变。DB 与应用都以锁后 `clock_timestamp()` 判断 S 尚未生效，不沿用 `CURRENT_TIMESTAMP`。取消版禁止更新、删除和回到任何其他状态；不得只在应用检查。
2. `publication_shape_check` 新增第三分支：DRAFT/PUBLISHED 的取消字段全为空；CANCELLED 保留完整发布证据且取消人、时刻、2～500 字原因、操作 ID 全非空。原有两分支其余校验不削弱。规则保护同时检查 UPDATE 的 OLD/NEW 所属工价，任一为 PUBLISHED 或 CANCELLED 就禁止改动；INSERT/DELETE 同样保护。
3. 保留按 workerId 范围的 PUBLISHED 无重叠排斥约束。增加与取消操作关联的**延迟约束触发器**，覆盖目标状态变化、前版窗口变化及操作记录插入，在 COMMIT 时同时校验：目标未生效且无报工/个人政策引用；有前版时前版唯一、同 scope、旧结束=S 开始、新结束=S 原结束；有后继时它仍 PUBLISHED 且从 S 原结束开始；无后继时恢复为 null。只有目标取消而未修复前版、只有前版延长却没有对应取消、伪造前版/窗口/操作记录均拒绝；无前版的允许情形见 D3.5。禁止修改或删除取消操作事实。
4. `PieceworkPriceBook_require_successor` 对有限的新结束时间仍要求真实同 scope 后继；新结束为 null 的恢复只允许对应的有效尾版取消事务。不能全局跳过 successor 检查。报工取价及个人政策触发器继续只接受有效 PUBLISHED 区间，取消版本不得新建任何引用。最后的延迟校验再次用 `clock_timestamp()` 检查未生效，防止事务中途跨过边界。

扩展 enum 与后续使用新值的 SQL 按 PostgreSQL/Prisma 的实际事务边界拆分前向迁移，避免同事务新 enum 值不可用；先加值，后重建 shape/保护/延迟约束及操作表。升级不修改已有价目、区间或报工；同事务写审计。更新 schema 注释、数据库文档和业务决策，注明只新增未来计划撤回例外。

状态转换仅允许：DRAFT→PUBLISHED 沿用原规则；PUBLISHED 且未生效→CANCELLED；CANCELLED 为终态。统一范围 workerId=null；个人范围必须匹配该 workerId。不能取消当前生效、过去生效或含任何报工引用的版本。

### D3 · 原子操作与并发

1. 输入包括范围、目标版本、原因、幂等键及复核时目标/前版/后继的 ID、窗口和 updatedAt；action 使用 `salary:rule:manage`，领域重新核对管理员身份与个人账号归属。个人账号后来被停用也应允许取消尚未生效的错误计划，不能机械复用只接受启用计件岗位的 `lockPersonal`；新建/发布仍保留原岗位检查。现有 publication 触发器只在 INSERT / UPDATE OF status 时执行，因此前版只恢复 effectiveTo 不触发岗位重验；实现不得无意扩大触发时机。
2. 个人取消沿用“salaryIdentityLockKey(workerId) → 全局工价发布独占锁”，统一取消使用全局工价发布独占锁；不反转既有报工“身份锁 → 发布共享锁”的顺序。锁后再取数据库真实当前时刻，提交前再次检查界限，不能使用事务开始时刻、页面 now 或客户端时钟。
3. 锁内重新读取目标、同一范围的相邻 PUBLISHED 前版/后继、引用及草稿。相邻集合/时间/updatedAt 与复核不一致则拒绝并重新复核，不能悄悄扩大或改变衔接范围。目标 `effectiveFrom > now`，等于 now 也拒绝；多个匹配前版/非法空洞不猜测修复。
4. 除 `ProductionReport.priceBookId` 外，还检查个人跟随统一时保存在 `snapshot.payroll.policyBookId` 的政策引用；已有结算/报工金额和哈希必须逐项保持。采用共用发布锁协调正常报工；数据库约束与直接 SQL 负向用例继续防止绕开历史保护。
5. 事务内登记取消操作，先将 S 标为 CANCELLED（保留原始窗口），再将同范围 P.effectiveTo 从 S.effectiveFrom 改为 S 原 effectiveTo。顺序不可反过来，否则非延迟排斥约束会拒绝重叠。个人无前一版时，这个区间自然跟随统一价，后继个人政策保持；DB 必须核实它确实是该范围第一版、不存在本应衔接却遗漏的前版。统一无前版时允许取消其首版，区间成为未配置，复核明确显示“取消后该时段无法报工”，之后报工拒绝，绝不补零。此例外不允许取消中间版制造空洞。
6. 所有取消与区间恢复、操作记录、审计一并提交；中途失败全部回滚。重复相同键与相同事实返回原结果，重用键但对象/原因不同拒绝；重复点击不能新增多条审计或再次修改前一版。
7. 创建下一草稿优先返回该范围已有 DRAFT；无草稿从最新未取消 PUBLISHED 版本复制，当前仍保留未来版本时明确标识复制来源；没有个人前版/后版按统一模式初始化。不能从最大的 CANCELLED 版本复制。新版本仍取全局最大版本+1（包含取消号）；不同账号与统一版本号不得冲突。差异基准按拟生效时间的有效版本确定，不能简单取最大版本。
8. 必改消费方点名：`piecework-price-book-admin.ts` 的预览约 331～334 行及 CLI 发布约 432～434 行，分离“全局最高版本号”和“该范围最新可用已发布价”；`piecework-admin.ts:41～48` 与 `personal-piecework-admin.ts:33～39` 排除取消模板；`PieceworkPriceBookForm.tsx:26～28,51` 增加“已取消”映射并修正差异基准，已取消行保留历史展示。旧标签页再次发布取消版明确提示“该调价计划已取消，请新建调价草稿”，不能重新发布或用笼统并发错误掩盖。
9. 继续扫描 seed/导入/发布 CLI、统一参考价、取价与报工校验、审计导出、其他枚举 switch 和测试 fixture；不能仅修以上点名位置。已取消版本只用于历史展示，不进入可选当前价、模板或发布路径。

**主要位置**：[统一工价管理](../../lib/salary/piecework-price-book-admin.ts)、[个人工价管理](../../lib/salary/personal-piecework-admin.ts)、[草稿服务](../../lib/salary/piecework-admin.ts)、[取价](../../lib/salary/piecework-rate-selection.ts)、[共用工价表单](../../components/business/salary/PieceworkPriceBookForm.tsx)、两类 action、`lib/production/operation-reporting.ts` 的协调契约，以及新迁移。

### D4 · 必须通过的验证

- 单一未来个人价取消后立即恢复统一；单一未来统一价取消后立即发布纠正价；无前版、已有草稿、停用账号、跨账号版本、缺有效统一价。
- 多未来版本：取消中间一版后 P 接到 S2、S2 费率/时间/身份不变；取消尾版恢复 null；相邻取消串行与并发；复核后追加新计划须重新复核；当前生效版不可取消、跨 scope 不受影响。仍有未来价时“立即追加调价”按明确限制拒绝，不能连带取消正确版本。
- 临界时间：锁等待越过生效时间、等于生效时刻、并发发布、并发取消、并发报工。应用单测可注入时钟测严格等号；PostgreSQL 测试用两个连接和锁屏障，在 DB 时钟确认越界后释放持锁连接，不用任意 sleep 或客户端时钟掩盖竞态；另测延迟约束在提交时越界回滚。
- 历史报工直接引用和个人 policyBookId 引用、已结算金额、规则/发布哈希不变；恢复区间不能造成重叠或空洞。
- DB 直接 SQL 负向验证：取消已生效/有 priceBookId 或 policyBookId 引用的版本、只取消中间版却不衔接、只延长前版没有取消、伪造 scope/前版/操作记录、篡改/转移/删除取消规则、取消状态改回 DRAFT/PUBLISHED、改历史生效时间、删除历史行全部失败。正向 SQL 原子取消则验证形状、邻接、审计与取消事实完整。
- fresh DB 完整迁移链及含“当前价+多个未来价+个人跟随统一+历史结算”的升级夹具；重试、回滚和故障注入保持数据不变量。

新增服务端环境开关 `PIECEWORK_SCHEDULE_CANCEL_ENABLED`，默认关闭；菜单与 action/领域都检查，不能只藏按钮。先应用前向迁移并部署能识别 CANCELLED 的兼容版本，确认 Web、LIGHT、HEAVY、定时任务和发布 CLI 均无旧代码在运行，再统一启用开关。开关须有 `.env.example` 和部署说明，mock/E2E 显式开启。取消实际发生后不得回退到不认识该状态及区间恢复规则的旧应用；回退仅关闭入口并使用兼容版本，不删除取消记录。

## 7. 库存失败用例与分批验证门禁

审查基线 Chromium 为 190 通过/1 失败，`inventory-flow` 在并发重放 Server Action 后进入页面错误边界；单独复跑仍失败。本批方案不把它写为已解决，也不跳过它宣布 C 完成。
