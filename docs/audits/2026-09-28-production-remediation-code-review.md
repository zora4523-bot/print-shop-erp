## 一、P1（条件性）：CONFLICT 没有关闭入口

**触发链**（以浏览器验收库里的 GD-260928-003 为例：v1 申请 990 后因交期改版被取消，v2 按 1,000 完成并已计薪）：

1. 迁移 `20260928130000.../migration.sql:39-50` 给所有旧版本或已关闭工单上、状态为 PENDING/REQUESTED/CANCELLED 的任务都建了 OPEN 核对记录。v1 任务因此有了 OPEN 记录，核对期间就是原工作日 9/28。
2. 管理员在面板点"核定历史生产"（RECOVER）。`completion-registration.ts:82-89` 发现 v2 已经 COMPLETED，把核对记录改成 CONFLICT，提交后抛错。这一步是设计如此，本身没问题。
3. 之后所有能关闭这条记录的路都走不通：
   - 再次 RECOVER：后续版本仍然存在，还是冲突。
   - 驳回（REJECT）：只接受 OPEN 状态的记录（`completion-registration.ts:93`），而且要求勾选"确实没有生产"，这与事实不符。
   - 标记未生产（`fact-review.ts:33`）：该任务带有申请数量，被拒绝。
   - 据证关闭（DISMISS_WAGE）：只适用于"工资待补发"（`fact-review.ts:35`）。
   - 重新建立核对：面板只在任务还没有核对记录时显示这个表单（`ProductionJobPanel.tsx:347`）。
4. 同时有另一条堵死的路：如果这张工单之前做过一次历史恢复，而且后续任务已经完成，那么之后任何一条核对被标记为未生产或驳回，都会进入重核函数（`recovery-projection.ts:38-40`）。它会对"最早恢复过的那个版本"重新调整后续任务；只要后续任务已有生产事实，就在第 13 行抛错，整个事务回滚。

**后果**（未关闭的记录会同时触发以下保护）：
- 该工单不能进入待发货（`production-completion.ts` 新增的核对计数），也不能发货（`lib/order.ts` 发货闸口里新增的 `assertNoHistoricalProductionReview`）。
- 当前版本的任务不能再写入（SQL 触发器 `20260928131000.../migration.sql:45-49`），也不能排单或再次改版。
- 原师傅在核对期间内的每一天都不能日结（`piecework-settlement.ts` 新增的核对检查，外加 SQL 触发器）。以 GD-003 为例，9/28 当天 v2 的 ¥40、¥200 也跟着被冻结。
- 如果核对日期未知，期间是"下发日到今天"，冻结范围更大。

**触发条件**：执行记录显示本地开发库 `ProductionJob` 为 0 条，生产环境按 HANDOFF 早于 830c7ae7。所以新数据经界面基本到不了这里，只有带存量的环境会触发。但方案 §7.1 要求"有冲突条目隔离并给处理入口"，现在只做了隔离，没有处理入口，恢复流程没闭合。

**最小修复**：
1. 在 `fact-review.ts` 增加两种凭证据关闭冲突的方式，都不改动后续版本的任务和工资：
   - "旧产量已含在后续登记中"：关闭为已处理，并记下关联的后续任务。
   - "确属额外生产"：用原人原日登记 v1 的事实。原日未结算就正常计薪；已结算就进入"工资待补发"。
2. 修改 `reconcileResolvedHistoryInTx`：只对本次刚恢复的来源做重核；遇到已有生产事实的后续任务就跳过并留痕，不要抛错。

**验收**：用 GD-003 形态的数据（v1 取消、申请 990；v2 完成 1,000）加上迁移自动建的 OPEN 记录，两种关闭方式都要做到：
- 工单能发货，9/28 能日结；
- v2 的工资和流水逐项不变；
- 重复提交不重复记账。

## 二、P2：生产进行中遇到改单，只能虚报未生产或按部分数量完工

**触发输入**：工单已下发，师傅已做 400/1,000，还在继续做。销售申请只改交期，管理员预览或批准。

**代码链**：
1. 改单预览、改单批准和取消预览都会调用 `assertProductionFactsReadyForChange`（`change-request.ts:3871/5818/4886`）。它要求当前版本每个待生产任务都有"未生产"核对记录（`fact-guards.ts:14-17`），否则拒绝。
2. 管理员只剩两个选择，都不对：
   - **勾选"已核实该次任务没有实际生产"**：这是虚假证据。它能放行，但违背了方案"待生产状态不等于未生产"的原则。
   - **按表单提示"已做的部分应补登记"补登 400**（`ProductionFactReviewForm.tsx:17`）：补登会把任务直接标为已完成。新的承接逻辑把完成任务快照里的原需求 1,000 记为"已满足"（`revision-jobs.ts:36,40`）。于是改版后新任务数量为 0，只沿用已产量，工单随即进入待发货。剩下 600 个再也没有任务可以登记，发货也会按"已完成"放行。
3. 唯一的退路是驳回交期修改，等全部做完再改。

**后果**：生产中常见的交期或资料修改被阻断，或者被迫留下错误证据、丢失剩余任务。修复前（B12 路径），同一场景是 v1 作废、v2 由同一位师傅继续做 1,000 个。

**最小修复**（二选一）：
- 对只改资料、不改实物的变更，如果后续任务仍是同一工序、同一负责人，并且继承了全部剩余量，就免掉"逐个任务核实未生产"这一步，直接沿用。计价按首产自动计件，这一点 `revision-jobs.ts:70` 已经能判断。
- 或者新增一种核对状态"部分已产、继续生产"：不把任务标为完成，也不写入"需求已满足"。

**验收**：已产 400 未扫码 → 只改交期 → 批准成功 → v2 仍由原师傅做 1,000 个且自动计件 → 登记后工资只算一次。取消和实物改版仍然要求逐个任务核对。

## 三、已核对、未发现可达缺陷的链路

- **数量审批与取消、暂停、待审补登**：
  - 撤回、两类驳回、三处失效都已接上重核（`recheckClosedChangeInTx`）。
  - 完成检查函数在有待审申请或未决核对时不会宣告完成。
  - 暂停期间可以核定，恢复时才推进，并且会检查是否还有待审申请。
  - 驳回必须勾选并留下"未生产"证据，SQL 同步校验（`131000:29-41`）。
- **原人原日计价与已结算原账**：
  - 申请时就冻结计价依据（`completion-pricing.ts:20`），计价取原任务快照里的款式、颜色和原工序。
  - 日期下限改为原工序的创建时间。
  - 提成分配和误登记更正仍然检查原日是否已结算（`lockProductionWageDay`）。
  - 已结算日只登记事实，并生成"工资待补发"义务；延迟触发器保证两者同时存在（`131000:57-70`），数据库也禁止把已结算日的完成事实改回。
- **重做**：
  - 原单是新模式时，重做单经状态机确认后走统一下发，首次重做继承和改版继承已互斥（`operation-materialization-service.ts` 的 else-if）。
  - 只有打包、没有内部任务的重做单，下发时就会判定完成，并且没有假工资。
- **990 核定满足 1,000 后改到 1,300 只增 310**：`revisionProductionQuantities` 分别记录实际产量和已满足需求量。改成 995 或 1,000 时新增为 0；改成 1,001 时新增 11；连续改版时，已满足结论经已完成的任务一直保留。
- **资料改版**：价格没变时保留原完成时间，只沿用已产量，不重复发完成通知（有测试覆盖）。
- **历史核对阻止日结和新版重复计产**：日结已经先取身份锁；应用层和 SQL 两层都校验核对期间；排单、完成、改版继承、发货都统一接入检查。
- **定位入口与销售隔离**：
  - 生产数量待核对的筛选会跳过默认队列；列表和工资页的链接直达具体任务。
  - 新的查询都要求管理员身份；销售端查询没有改动；核对证据没有写进变更申请的审核备注（`reviewRemark`）。

## 四、P3 与未验证风险

1. **寄样工单下发时的通知变了**（`admin-workflow.ts:646-651`）。下发流程现在对所有工单都跑一遍完成检查。寄样单下发即处于待发货、又没有工序，所以会被判定完成：写入"全部生产步骤完成"日志，发出 ORDER_COMPLETED，并提前返回，不再发 ORDER_SCHEDULED。
   - 修复：只在重做单或新模式无内部任务时调用，或者保留下发通知。
2. **价格有变但没有新增生产时，会重复发完成通知**（`change-request.ts:5322` 与 `:5997`）。例如 990 满足 1,000 后改成 995，或者只改包装计价：此时 `projected` 不为空，完成时间被清空；全部任务又只是沿用，于是再次判定完成，发出新版本的 ORDER_COMPLETED。V28 要求只改资料不重复通知，这个情形没有覆盖。
3. **身份锁可能顺序不一致**。改版继承建任务、取消时批量作废任务，都会经 SQL 触发器按行的顺序加身份锁（`131000:12-14`）。另外几处（RECOVER、核对服务、排单）是先排序再加锁。两边并发时可能形成锁等待环，PostgreSQL 会检测到并中止其中一个事务，结果是报错需要重试，不会一直卡住。
   - 修复：在改版继承和取消事务写任务之前，先按排序取齐相关人员的身份锁。
4. **实物改版后的工单永远取消不了**（`cancellation-production.ts:17-24`，加上取消参考价的校验）。例如同一款先做了 v1 1,000 个，改设计后又做了 v2 1,000 个：已产下限算成 2,000，超过当前数量 1,000，取消预览和批准都会报错，而且没有出路。方案只要求"返回核对项"，没有定义怎么处理，需要业主定规则。
5. **误标"未生产"后，界面上无法重开核对**（`ProductionJobPanel.tsx:347` 只在没有核对记录时显示表单）。服务端允许重新建立核对，界面没给入口，真实工资会因此进不来。
6. **销售撤回申请时，重核产生的日志记在销售账号名下**（`withdrawOrderChangeRequest` 把 `actor.id` 传进去）。这只是审计归属不准确，不泄露数据。
7. **未验证**：列表和工资页的 `#production-job-…` 链接指向详情页"生产、用料与计件记录"补充区块里的元素。这个区块如果默认是折叠的，链接能否自动展开并聚焦，要等浏览器验收确认。另外恢复扫描生成的链接带 `?tab=production`，这个参数在详情页可能不起作用。
8. **工资页显示**：原日已结算、带"工资待补发"的师傅，还会以"待核定"的候选行出现在当天列表里；批量日结也会把他当作已锁定的重放计入。这只是展示问题，不会重复记账。

## 一、P1：多工序工单的历史恢复仍然走不通

**触发数据**（迁移前的存量，或者新版本里管理员把"未生产"重新打开为待核对后，都能出现）：
- v1 有两个工序：
  - 工序 A：师傅 X 申请了 990，旧代码改版时把这个申请直接作废了，任务状态 CANCELLED，但申请数量还在。
  - 工序 B：师傅 Y 已经完成 1,000。
- v2 是只改交期的版本：A2 待生产 1,000；B2 是"沿用已产数量"（CARRIED，数量 0）。
- 迁移给 A1 建了一条待核对记录（OPEN）。

**逐条出路都走不通：**

| 管理员的操作 | 结果 | 原因（文件:行） |
| --- | --- | --- |
| 正常"核定历史生产" | 进入冲突 | 检查依赖时看的是**整张工单**的所有后续任务，CARRIED 也算依赖（`completion-registration.ts:84-86`）。所以跟 A 无关的 B2 会触发冲突。 |
| 勾选"确属额外生产" | 被拒 | 要求后续至少有一个已完成任务，而且所有后续任务都已结束（`:83`）。这里 B2 是 CARRIED、A2 还在待生产，两个条件都不满足。 |
| "已计入后续登记" | 被拒 | 需要一条实物相同、已完成的后续登记（`conflict-resolution.ts:15-18`）。A2 还没完成。 |
| 先把 A2 登记完成，再来处理 | 写不进去 | SQL 触发器在旧版本有 OPEN/CONFLICT 记录时，禁止写当前版本的任务（`20260928132000.../migration.sql:51-55`）；应用层也会拦截（`fact-guards.ts:22-31`）。 |
| 就算放宽依赖检查 | 仍会失败 | 重核函数要求当前版本每个任务都必须是"待生产且已核实未生产"，否则抛错（`recovery-projection.ts:11-13`）。B2 是 CARRIED，照样抛错。 |

## 四、P3 与需要确认的口径

1. **"确属额外生产"会被当成可用实物量**（`revision-jobs.ts:31-37`）。实物指纹相同的旧版 990 登记完成后，会算进实际产量，可能出现以下两种情况：
   - 之后把总量改到 1,300，新任务数量为 0（1,300 − 1,990）；
   - 取消时已产量超过当前数量，取消会被卡住。

   如果业务上"额外"的意思是报废或返工，而不是可以交付的货，就需要另外标注，不计入可承接的产量。
2. **不影响价格的实物改版会在批准时才失败。** "只改资料"是按"价格是否变化"判断的（`change-request.ts:3886/5826`）。只改设计稿、价格不变时，预览能过，要到批准阶段在 `revision-jobs.ts:102` 才报"请先核实"。这样做仍然是安全失败，只是提示来得晚。
3. **需要外协的工单，改价后仍会重复发完成通知。** 恢复完成标记的函数会跳过需要外协的工单（`order-state.ts:9`）。所以内部生产和外协都已结束的混合工单，改价时会再发一次 ORDER_COMPLETED。
4. **部分已产时加量，剩余量会整体转为人工补价。** 例如做了 400、未满 1,000 时加到 1,300：先补登 400 让任务完工，改版后新增 900 全部转为人工补价（其中包括原需求剩下的 600）。按业务口径，这 600 应属首产计件，这一点需要确认。
5. **多次改版后实际量超过当前数量时的取消规则仍待你答复**，代码保持报"核对"错误。D2 补差支付也没有实现，只保存了"工资待补发"义务。这两项都没有当作已完成。
