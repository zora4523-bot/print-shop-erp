## 2. 第一优先级：专门的履约费用确认流程

### 当前证据

- `lib/order/editable-fields.ts:88` 允许履约阶段更正到付；`lib/order.ts:3332` 仅将已发货外部销售单限制为管理员更正。
- `lib/order.ts:3660/3673` 对外部销售单一律清空 `confirmedFee`、设为 `PENDING_ADMIN_CONFIRMATION`。
- `lib/order/pricing-review.ts:394` 与 `lib/order/pricing-status.ts:38` 仍只允许 `PENDING_FACTORY/SUBMITTED` 进行工厂核价。HEAD 中前一个位置为 `pricing-review.ts:335`，工作区改动没有修复该状态冲突。
- `lib/order.ts:1733` 禁止待核价工单发货；`lib/order/admin-workflow.ts:947` 禁止缺少确认费的已发货工单结算。
- 详情页、工厂确认、商业费用编辑、再次切换到付均没有有效恢复通路。

### 推荐设计

不放宽通用工厂核价，不重新计算已经生产的款式价格。新增或提取专门的“履约费用更正确认”服务，并让正常更正与历史卡单恢复共用。

1. 范围覆盖 `CONFIRMED / ON_HOLD / RELEASED / FOILING / PACKING / SCHEDULING / IN_PRODUCTION / COMPLETED / SHIPPED`。其他业务限制继续生效，不因支持核价就解除暂停、发货或结算限制。
2. 只确认物流应收差额；保留已审核款式单价、固定费、版费、入袋费、包装材料费及其他独立收费。使用可追溯的原物流计价依据或管理员明确填写的实际费用与原因，不套用最新加工价表重算整单。
3. 推荐业务语义：**管理员明确确认本次履约费用更正，且费用证据完整时，可在同一事务完成该次费用确认**。界面须展示更正前后差额，不能让一个无提示开关隐含财务确认。
4. 销售提交更正或物流金额仍未确定时，仍保持待确认，但必须提供专用管理员复核入口。该入口能够在发货前补齐计费事实并确认，不能再形成“发货要求确认、确认却要求已经发货”的循环。
5. 确认在同一订单锁内完成：重读身份与版本 → 校验物流收费依据 → 更新允许变动的费用 → 一致更新总额、报价/确认金额及对应修订引用 → 写入 `ADMIN_CONFIRMED` 价格修订和操作日志。`settledFee` 留待正式结算，不能提前伪造已结算状态。
6. 业务修订和价格修订按规则递增；生产状态、纸质工单版本与已审核加工数据不变。重复请求须幂等；过期订单/价格版本、错误地址、并发结算须拒绝。
7. `PENDING_FACTORY/SUBMITTED` 继续现有工厂核价；草稿/驳回单走正常提交。`SETTLED/FINISHED/CANCELLED` 保持禁止更正。

建议改动范围：`lib/order.ts`、新的履约费用服务、现有价格修订工具、对应 action/schema、`SfCollectToggleForm`、管理员详情/抽屉及其测试。当前订单相关脏改与此范围有重叠，实施前应先固定集成基线，不能覆盖或夹带这些改动。

### 历史卡单恢复

先做只读清单：外部销售、履约阶段、待核价、确认费为空，并结合 `SF_COLLECT_CHANGED_PENDING` 修订来源和订单日志核验。不能只靠状态认定所有待核价工单都属于这个问题。

复核更正前已确认的加工与非物流金额，显示费用差额，由管理员通过同一服务明确确认。证据缺失、混有其他待审核改动或收费身份不一致的单据转人工处理，禁止批量执行 `confirmedFee = totalAmount`。

预计无需数据库 schema 迁移，现有价格修订和审计字段可支持。历史财务恢复是单独的受控操作，不作为启动时自动数据修补。

### 验收

- 全部履约状态 × 管理员/销售 × 到付开启/取消，验证直接确认或进入专门复核的正确分支。
- 多地址、缺重量/省份、人工运费、已有运费成本、原报价依据缺失等边界。
- 只允许物流差额改变金额；已审核人工款价、版费、包装及其他收费和历史证据保持。
- 已卡 `SHIPPED` 确认后能够结算；已卡生产中/完成未发货单确认后能够按原状态机继续发货。
- 并发结算、陈旧版本、错单/重复地址、重复确认及三种终态防护。

## 3. 管理通知：保留安全重试，不放宽收件人保护

当前证据：`lib/notification/notify.ts:232–238` 将身份错配标为可重试，但 `754–761` 与 `859–865` 在管理路由整体阻塞时取消该资格。`54a4453` 未修改这些代码。

推荐先统一评估路由的阻塞原因：

- 永久阻塞：目标删除、停用、绑定缺失等，继续原有失败策略。
- 临时阻塞：路由完整、通道有效，唯一问题为可恢复的 Bot 身份错配。整条路由仍零发送，但所有因此暂停的现存通道均保持 `RETRYING`，包括健康 Webhook 通道。
- 临时与永久问题同时出现，不能被宽泛的“可重试”覆盖；不要只修错配通道而把健康兄弟通道永久终结。

恢复原 Bot 身份后使用现有 durable 队列重试；沿用唯一投递键、租约/代次检查、成功去重和 UNKNOWN 人工处置保护。不得向新机器人交付旧绑定的收件目标。

重试边界：`lib/background-jobs/notification.ts:50` 默认总共四次，退避间隔为 30/60/120 秒。自动恢复只保证在预算内；耗尽后应保留 `RETRYING + DEAD` 并进入现有管理员待处理队列。身份恢复后可使用现有死信重试入口，不新增无限循环。

历史 `FAILED + SUCCEEDED` 不会被补丁自动恢复，也不能直接重置。先只读列出候选，核验当时收件路由、原消息及未发送证据。旧通用错误文案不能唯一证明错配原因；证据不足的不自动补发。经管理员确认的补发必须单独授权、去重并留审计，不修改 SUCCESS/UNKNOWN 的安全语义。

建议改动范围：`lib/notification/notify.ts` 及通知/任务测试；必要时提取纯路由判定函数。预计无需 schema 迁移。

验收：五类管理事件 × 缺失/错误 Bot ID；纯智能机器人及混合路由全部零发送且可重试；恢复后仅发送未成功的通道；永久错误仍保持永久失败；预算耗尽正确进入待处理队列；UNKNOWN 不自动重发。

## 4. 发布门禁：暂态恢复预算加硬性总上限

当前证据：`heartbeat-policy.ts:10–11` 保留 180 秒活跃心跳，`health.ts:291–297` 要求唯一活跃 LIGHT 行；`deploy/update.sh:91–94` 默认只等 120 秒，另需 6 秒稳定观察。门禁超时会经 `34–38` 停止 Web 和两个 worker。

正常优雅退出删除心跳，不受此问题影响。风险是启用机器人且发布门禁通过前 worker 崩溃/强杀后被 PM2 自动重启：旧 PID 心跳仍新鲜，真实活着的新 worker 被误认为双实例。

推荐方案：

1. 提取可用模拟时钟测试的门禁等待策略；不要只把测试中 `120` 字符串改成更大的值。
2. 暂态恢复预算至少覆盖 180 秒心跳窗口、最长 60 秒刷新、6 秒稳定观察及轮询余量。预算与共享心跳策略保持一致，避免两处独立魔数再次漂移。
3. 对身份匹配、配置完整、状态可恢复的重复心跳，健康读模型可给出安全的重新观察等待时长。根据数据库观察时间及多余心跳的过期边界计算，不把“最新行已连接”等同于其他进程已经死亡。
4. 从实际观察到的可恢复异常计算有限恢复期，同时保留明确的全局硬上限。建议恢复期初值 270 秒、总上限 600 秒，最终以共享时长计算和模拟测试确定，并同步维护窗口说明；这会增加异常发布的最长等待时间。临近原截止时间的一次新重启可获得受限延期；持续双实例或不断重启最终必须失败。增大固定总超时只算缓解，不能承诺解决任意时点重启。
5. 身份不符、鉴权失败、明确连接冲突和无效配置等现有立即拒绝规则继续保留；真正只有一个健康、版本正确的 worker 且稳定观察通过后才解除发布保护。
6. 不批量删除心跳、不改用会掩盖双进程的固定 worker ID、不移除失败停机保护。硬上限耗尽仍允许失败，这是有意保留的安全边界。

建议改动范围：`deploy/update.sh`、`scripts/deploy-jobs-gate.mjs`、必要的健康状态说明/纯时间策略、部署文档及测试。预计无需 schema 迁移。

验收：模拟正常优雅发布、首次崩溃重启、旧截止前再次重启、旧行过期后稳定通过、两个真实 worker 持续刷新后达到硬上限失败、身份/鉴权异常立即失败、未启用机器人直接通过。测试先使用模拟 sender 和心跳快照，不在本地业务进程或生产环境杀进程试验。
