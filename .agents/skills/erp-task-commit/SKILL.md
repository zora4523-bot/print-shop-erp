# ERP 任务提交

遵守项目 [AGENTS.md](../../../AGENTS.md) 和 [CONTRIBUTING.md](../../../CONTRIBUTING.md)。用户已授权本项目在每个修改任务完成后自动创建本地 commit；无需另问“是否提交”。用户本次明确要求暂不提交时优先遵从。

## 任务边界

- 一个任务以用户可验收的修改结果为边界，不以一次工具调用、一条进度消息或一次回复为边界。任务内继续修正、测试、补文档时先完成这批工作。
- 默认一个任务形成一个可审查的 commit。独立且无关的清理分开提交；实现所必需的重构、测试和文档随功能提交。不补交其他任务的历史积压，除非用户明确纳入本次范围。
- 只有咨询、只读审查、没有持久文件变更或改动已被提交时，不制造空提交。已提交任务的后续修改创建新 commit，不默认 amend。

## 开始修改时

1. 确认仓库根目录、当前分支和 HEAD；读取 `git status --short`、未暂存与已暂存的差异。记录本任务预计涉及的文件及这些文件已有的改动。
2. 对已有改动的文件，在修改前保留可对照的内容或补丁到仓库外的临时目录，以便区分任务增量。不要把整份敏感文件或无关 diff 输出到对话中。中途才加载本技能时，结合操作记录和真实 diff 重建边界，不把所有未提交内容推定为本任务。
3. 沿用当前任务的分支或独立工作树。需要新建分支时遵守 `codex/` 前缀，不为了自动提交切换其他任务正在使用的共享分支。

## 完成实现与验证

- 按 [测试要求](../../../CONTRIBUTING.md#测试要求) 选择与完整变更批次风险相称的验证，完成对应文档同步；不为每个 commit 固定追加全量构建或全量测试，也不降低业务门禁。
- 先修复本次引入的回归，再提交。既存问题或环境故障应记录证据及受影响的验证范围；可替代的检查继续完成。若仍缺少足以证明当前变更正确的必要验证，明确说明未完成项，不把任务报告为已完成。
- 审查将提交的实际内容，包括新增文件、删除、配置、迁移和相关调用方。删除依据、授权、金额、历史快照和已应用迁移的约束继续遵守项目规则。
- 检查 `git diff --check`。分离了混合改动时，还要验证“当前 HEAD + 仅本任务补丁”能够独立成立；不能仅凭含有其他未提交依赖的工作区测试通过，就声称这个 commit 已通过验证。

## 隔离并创建 commit

1. 明确列出本任务的文件或变更块。提交前重新检查 HEAD、工作区和暂存区；如其他任务期间改变了相关文件或 HEAD，重新对照差异和依赖，按影响补做验证。
2. 使用显式文件路径或审查过的分块暂存。禁止用 `git add .`、`git add -A`、`git commit -a` 或通配符收走整个脏工作区。一个文件被本任务修改过，不代表该文件的全部差异都属于本任务。
3. 保留其他任务的未暂存内容和暂存状态。暂存区含其他任务内容时，不直接执行会提交全部暂存内容的普通 `git commit`。整文件差异均属于本任务时，可使用 `git commit --only -- <明确文件列表>` 排除其他路径的暂存内容；新增文件需先按明确路径登记到索引。**该命令会提交所列文件的工作区版本，不能用于只提交文件内已暂存的部分变更。**
4. 同文件混改时按变更块隔离；不要用全文件暂存覆盖他人已暂存的版本。若使用独立索引或独立工作树隔离，提交前后都核对真实工作区和索引，仅处理本任务条目。无法证明归属、无法独立验证或无法保持其他暂存内容时，先继续解决具体依赖；仍无法安全完成时保留改动并明确说明，不猜测、不全量提交。
5. 审查最终候选提交的完整 diff 和文件清单，而非只看统计。正常暂存提交流程使用 `git diff --cached --check`、`git diff --cached --stat` 和 `git diff --cached`；使用 `--only` 时核对其实际将取用的工作区内容及限定路径，并先做对应的 `--dry-run`。确认未遗漏任务必需的新文件，也未包含密钥、`.env`、生成物或测试输出；`.env.example` 只有在本任务需要且不含真实敏感值时才能提交。
6. 创建本地 commit。沿用仓库的 `type(scope): 中文结果描述` 风格，例如 `fix(navigation): 统一侧栏菜单字号与行高`；类型按修改选择 `feat`、`fix`、`refactor`、`docs`、`test` 或 `chore`。正文仅在有必要时说明原因、验证和已知限制。多行正文通过临时文件传给 `git commit -F`。

不自动 push、发布、创建 PR、amend、rebase 或重写历史。不要清空暂存区、stash 他人工作、修改 Git 身份、关闭签名、绕过 hooks 或移除不明的锁来强行提交。缺身份、签名失败或并发锁冲突时，保留状态，核对具体原因；可安全恢复时重试，否则说明实际阻碍。一次提交结果不明时先检查日志和差异，避免重复提交。

## 提交后交付

- 读取本次 commit 的 hash、标题和实际文件清单，确认内容与审查范围一致；核对本任务增量已提交，其他工作区和暂存区改动仍被保留。提交后若发现错误，修正并验证后另建提交，不悄悄改写历史。
- 最终回复简要说明修改结果、验证结论和 `commit: <短 hash> <标题>`。本任务有实际变更却未能提交时，明确说“未提交”，并给出具体原因与缺少的条件；不要仅说“已完成”。
